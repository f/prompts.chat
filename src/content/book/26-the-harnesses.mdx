You ask an AI to fix a bug. It reads the project, edits a file, runs a test, sees a failure, and tries again. The model is part of this process. But something also has to open the files, run the commands, and bring the results back.

That surrounding software is the **harness**. After learning about agents and skills, it helps to look at the system that makes them work together.

## What Is a Harness?

An **agent harness** is the software that runs an AI agent. It prepares the model's context, exposes tools, handles tool requests, and manages the steps of a task. Depending on the application, it can also manage permissions, saved progress, retries, and limits.

People sometimes use *agent*, *framework*, and *harness* loosely. In this chapter, we use these distinctions:

A harness can be a small loop in your own application or part of a larger coding assistant. It does not have to include multiple agents or a complicated framework. Anthropic describes this distinction between an agent and its harness in its [guide to evaluating agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents).

<Callout type="info" title="Two uses of the same word">
An agent harness runs the agent's work. An evaluation harness runs test tasks and measures how well that system performs. They can work together, but they have different jobs.
</Callout>

## How the Loop Works

Imagine the task is to improve an empty search results page. A typical loop looks like this:

1. **Prepare context.** Include the request, project instructions, relevant skill instructions, and available tool definitions.
2. **Call the model.** It might answer directly or request a tool, such as reading the search component.
3. **Check and execute.** The harness validates the request and checks permissions before the tool runs.
4. **Return the observation.** The file contents, command output, or error go back into the model's context.
5. **Continue or stop.** The model uses that evidence for its next step. The harness also enforces limits and can pause for user input.

Writing "run the tests" in a response does not run anything. A real tool has to execute the command, and its result has to come back. That feedback lets an agent react to what actually happened. See Anthropic's [explanation of agent workflows](https://www.anthropic.com/engineering/building-effective-agents).

## When the Model Writes the Loop

The loop above has a steady rhythm: the model asks for one tool, the harness runs it, and the result joins the model's context. For a few steps, that works well. For a task that touches hundreds of files, every step becomes another full model request, and the context fills with output the model needed only once.

Some harnesses offer another arrangement. The model writes a small program that calls the tools itself. The program runs in a sandbox, raw results such as files, logs, and search hits stay in its variables, and only what it prints returns to the model. This is called **programmatic tool calling**, an idea that grew out of research such as [CodeAct](https://arxiv.org/abs/2402.01030) (Wang et al., 2024).

<Compare
  before={{ label: "One tool call at a time", content: "Read file A. Here is A. Read file B. Here is B. After every result, the model is called again with its instructions, its history, and everything it has seen so far." }}
  after={{ label: "A program that calls the tools", content: "Search the project, read every match, keep the files that still use the old API, and print a short list. The harness runs the program and returns only the list." }}
/>

The context stays cleaner, because the model reasons over a summary. Model requests drop, because instructions and history are not re-sent every few calls. And loops and checks run in code, so a case the model meant to handle does not silently fall away.

Factory made this the default in [Droid 1.0](https://factory.com/news/frontier-harness), announced on October 29, 2026. Its Script tool runs JavaScript in a sandbox and can make hundreds of tool calls in one model request. Independent calls run at the same time, and a long script can run in the background and wake the model when it is done. Factory credits CodeAct, and notes that Cloudflare and Anthropic brought the idea to production in late 2025 and Codex brought it to coding agents. In Factory's own example of fixing a failing test, the same 15 tool calls took 5 model calls instead of 10; these are figures Factory reports for its own harness.

The trade-offs are real. The sandbox has no file, network, or system access of its own, only the tools the harness exposes. Permissions and approvals still have to apply to every tool the program calls. Printed output is capped. And a program is harder for a person to follow than a list of single steps.

### Workflows: The Same Idea One Level Up

The same move works with whole agents. In Anthropic's [Claude Managed Agents](https://platform.claude.com/docs/en/managed-agents/workflow-runs) (beta) and [Claude Code](https://code.claude.com/docs/en/workflows), an agent can write a **workflow**: a program that runs many agents in phases, fans work out, passes results from one agent to another, repeats a step until a review passes, and combines what comes back. It runs in the background while the main conversation stays free.

With subagents, the agent itself decides each next step. In a workflow, the program decides. The agent still chooses when to start one, so you guide that choice in its system prompt or instructions. Budgets matter too: every agent in a run spends tokens.

### Prompting for a Program

When the model plans a program, your prompt becomes its specification. Describe the whole job: which items to cover, the checks that must hold for every one, what to do when one fails, and what the final report should contain. For risky actions, ask to see a summary of the program first.

<TryIt compact prompt={`Handle this whole job with a program instead of one step at a time.

Job: \${job:check that every API route that changes data requires a signed-in user}
Items: \${items:all route files under src/app/api}
Check for every item: \${checks:the route verifies the session before it reads or writes anything}
If an item fails: \${failure:record the file path and the reason, then keep going}
Final report: \${report:the routes that failed, how many passed, and any file you could not read}

Before running anything that changes files, summarize the program for me and wait for my approval.`} />

Not every task needs a program. When each move depends on judging the last result, one call at a time is often clearer. A program shines when the job is large, repetitive, and easy to check.

## Why Prompts Matter Inside a Harness

A harness gives the model a way to act. Your prompts explain what useful action looks like. Without a clear goal, an agent can spend many steps doing work you did not need.

The current request is only one part of the instructions. An application may also supply a system prompt, project guidance, tool descriptions, and instructions from a loaded skill. The harness decides how these enter the context; the model follows the instruction hierarchy used by that system.

<Compare
  before={{ label: "Unclear task", content: "Fix search. Make it better." }}
  after={{ label: "A task the agent can check", content: "When search has no matches, show a helpful empty state. Keep matching behavior unchanged. />

You do not need to describe every click or command. Define the outcome, relevant constraints, and what counts as done. Let the agent choose routine steps when that flexibility helps.

Tool descriptions are also part of prompting. A tool with clear inputs, outputs, and limits is easier for the model to use correctly. Adding more tools without explaining them can create confusion.

## Where Skills Fit

A prompt usually describes the current task. A **skill** captures a method you want to reuse across tasks: how to review a change, investigate a bug, or prepare a report.

In the [Agent Skills format](https://agentskills.io/specification), a skill has a `SKILL.md` file and can include scripts, references, and assets. A compatible harness makes skills discoverable. It can provide their names and descriptions first, load the selected skill's instructions when relevant, and read supporting files only when needed. This is called **progressive disclosure**.

<Collapsible title="Open a small bug-fixing skill">

```markdown
---
name: verify-bug-fix
description: Use when fixing a reproducible bug in an existing project.
---

1. Read the project instructions and the relevant code.
2. Reproduce the reported behavior, or explain why you cannot.
3. Make the smallest change that addresses the cause.
4. Run relevant checks, including a nearby case that should still work.
5. Report the change, evidence, and remaining uncertainty.

If a required tool is unavailable, explain the limitation.
Do not describe an unrun check as passing.
```

</Collapsible>

The harness still needs the tools and environment that the skill expects. A skill describing a browser test does not install a browser. A script may need dependencies. Instructions may need changes when moved to another harness with different tools. Loading a skill also does not train the model or guarantee expertise.

Use the task prompt for what is specific today. Put a repeated procedure in a skill. Keep shared project rules in the instruction files your harness supports. This avoids copying a large, slightly different checklist into every request.

## Instructions and Permissions Have Different Jobs

"Do not edit files outside this project" is a useful instruction. A filesystem boundary that blocks those writes is an enforced control. Reliable setups use both.

Permissions, sandboxing, and approval checks must be implemented by the harness, its tools, or the underlying environment. A prompt cannot enforce them by itself. The [VS Code agent security documentation](https://code.visualstudio.com/docs/agents/run/security) shows concrete examples of these controls.

The same distinction matters for information coming back from tools. A web page or repository file can contain text that looks like an instruction. Treat that text as task data unless it comes from a trusted instruction source. Keep access limited to what the work needs.

## Where Does the Harness Live?

Every agent runs inside a harness, but someone has to build that harness, host it, and keep it working. Who does that decides how much you control and how much you have to maintain. Today a harness usually reaches you in one of four ways:

      <td>The agent as files in your project: prompts, tools, tests</td>
      <td>Changes go through ordinary code review; you still deploy and update it</td>
    </tr>
    <tr>
      <td>A managed service</td>
      <td>The provider</td>
      <td>Instructions, skills, tools, and a choice of model</td>
      <td>Little machinery to maintain; the provider's sandbox and limits set the edges</td>
    </tr>
    <tr>
      <td>Part of an automation system, such as CI</td>
      <td>The automation platform, when an event fires</td>
      <td>A task description and the outputs it is allowed to produce</td>
      <td>Fits pipelines you already have; nobody is watching a chat while it runs</td>
    </tr>
  </tbody>

Late October 2026 brought a clear example of each of the last three. Cursor's [Agent SDK](https://cursor.com/blog/agent-sdk), generally available since October 20, treats an agent as a small project: prompts in Markdown, tools as TypeScript functions, and evals beside them. You can run it locally, deploy it to Cursor's infrastructure, or run it on your own as a single Node process. On October 28, Microsoft released the [Copilot harness in Foundry Agent Service](https://devblogs.microsoft.com/foundry/microsoft-copilot-harness-in-foundry/) as a public preview. It is the [same harness](https://blogs.microsoft.com/blog/2026/10/28/introducing-the-microsoft-copilot-harness-unlocking-the-potential-of-truly-multi-model-agentic-work/) that powers GitHub Copilot in its app, CLI, and VS Code. Microsoft runs the agent loop and the sandbox; you bring skills, MCP tools, and agent definitions you can keep in source control. The same day, [GitHub Agentic Workflows](https://github.blog/changelog/2026-10-28-github-agentic-workflows-generally-available/) became generally available. You describe a job such as issue triage in a Markdown file, and it is compiled into an ordinary GitHub Actions workflow that runs Copilot or another coding agent.

Where the harness lives also decides where its boundaries are enforced. Instructions guide; permissions enforce. In your own loop, you build that enforcement yourself. On a managed service or an automation platform, the platform supplies it and you configure it. Agentic Workflows shows how many layers that can mean: agents get read-only permissions by default and run in a sandboxed container behind a firewall, and their proposed changes pass through validated "safe outputs" and a separate threat-detection scan before anything is applied. Your prompt still says what to do. The platform limits what a mistake can do.

The parts you write usually travel better than the loop. Skills and MCP are open standards, and Microsoft's announcement treats supporting them as the mark of a serious harness. A clear skill or tool description can often move to another harness with small adjustments; code written around one particular loop rarely can. Earlier we suggested keeping the model fixed while you compare harnesses. A multi-model harness offers the opposite experiment: Foundry lets you pick a supported model without rewriting the orchestration, and Agentic Workflows lets each workflow choose its model provider. You can change the model and hold everything else still.

Whichever path you choose, some things never move to the provider: the outcome you want, the instructions and skills that describe it, the tools and access you grant, and the checks that show the work is done. A harness can run the loop for you. It cannot decide what "done" means.

## What Makes a Harness Useful?

More autonomy is useful only when the system can check its work and recover from problems. For a long task, look at how the harness handles:

- **Context:** Keep relevant instructions and evidence available. Summarizing old steps can save space, but it can also lose details.
- **Progress:** Save decisions and unfinished work so the next session can continue. Saved state still needs to be loaded into context.
- **Failures:** Return errors clearly, use bounded retries, and avoid repeating actions with side effects blindly.
- **Limits:** Stop at a time, cost, or step budget, or when the work needs user input. Stopping is not proof of success.
- **Verification:** Inspect actual files, test results, or other outcomes. A confident final message is not enough.

When comparing setups, try the same real tasks and inspect both the outcomes and the execution traces. Keep the model fixed when you want to study a harness change. Change one prompt, skill, or tool setting at a time, and repeat tasks because individual runs vary.

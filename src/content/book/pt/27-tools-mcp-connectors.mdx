Você pede a um agente para encontrar os bugs abertos no seu projeto e preparar um rascunho de uma issue de acompanhamento. Para isso, ele precisa de mais do que boas instruções. Precisa de um jeito de acessar seu gerenciador de issues, ler os dados certos e talvez criar algo ali.

É aqui que entram **ferramentas**, **conectores** e **MCP**. Eles têm relação entre si, mas descrevem partes diferentes da configuração.

Uma ferramenta também pode funcionar localmente. Uma calculadora não precisa de conexão com uma conta. Uma ferramenta de leitura de arquivos pode funcionar inteiramente no seu computador. Um serviço externo é apenas uma possível fonte de ferramentas.

## O que uma ferramenta realmente contém

Uma ferramenta geralmente tem um **nome**, uma **descrição**, um **esquema de entrada** e uma implementação que faz o trabalho. A descrição ajuda o modelo a decidir quando usá-la. O esquema descreve os argumentos que ela aceita.

Aqui está uma pequena definição fictícia de ferramenta MCP:

<Collapsible title="Examine a definição de search_issues">

```json
{
  "name": "search_issues",
  "description": "Pesquise issues no projeto conectado. Esta ferramenta apenas lê dados.",
  "inputSchema": {
    "type": "object",
    "properties": {
      "query": { "type": "string" },
      "limit": { "type": "integer", "minimum": 1, "maximum": 20 }
    },
    "required": ["query"],
    "additionalProperties": false
  }
}
```

</Collapsible>

O modelo pode solicitar `search_issues` com `{"query": "bugs abertos", "limit": 3}`. A aplicação encaminha essa solicitação para a implementação. Ela consulta o gerenciador e devolve resultados ou um erro.

O nome e o esquema não executam nada sozinhos. A implementação precisa validar as entradas, verificar o acesso e realizar a operação. A resposta da ferramenta também é diferente da resposta final do modelo: ela pode conter IDs e títulos de issues, que o modelo resume depois. A [especificação de ferramentas MCP](https://modelcontextprotocol.io/specification/latest/server/tools) descreve como as ferramentas disponibilizam essas operações.

<Callout type="info" title="Uma solicitação não é um resultado">
“Vou criar uma issue” é uma afirmação. Uma chamada de ferramenta solicita a operação. Uma resposta bem-sucedida com o ID da nova issue é uma evidência de que ela aconteceu. Mantenha essas três coisas separadas.
</Callout>

## O que um conector acrescenta

Um conector reúne a integração com um sistema específico. Ele pode cuidar do login, da seleção de uma conta ou espaço de trabalho, da busca de dados e da disponibilização das ações suportadas como ferramentas. Alguns conectores apenas pesquisam ou leem. Outros também permitem gravar dados.

**Conector é um termo de produto, não um padrão técnico universal.** Um conector pode chamar diretamente a API de um serviço. Outro pode usar um servidor MCP. Um terceiro pode pesquisar em um índice criado a partir de documentos sincronizados. Confira o que a integração específica suporta. A [visão geral de conectores da Microsoft](https://learn.microsoft.com/en-us/azure/connectors/introduction) mostra um exemplo de integrações baseadas em APIs.

Conectar uma conta não significa que o agente vê todos os arquivos, carrega todos os seus dados no contexto ou tem permissão para realizar qualquer ação. O acesso depende da conta, dos escopos configurados, da aplicação e das permissões do próprio serviço. Os resultados de busca também podem refletir um índice mais antigo que os documentos originais.

Para o gerenciador de issues, separe estas perguntas: existe uma conexão configurada? A qual projeto ela pode acessar? Ela só pode ler ou também pode criar issues?

## O que o MCP padroniza

**MCP** significa **Model Context Protocol**. Ele define uma forma comum de comunicação entre aplicações de IA e provedores externos de capacidades. Não substitui a API de um serviço; um servidor MCP pode usar essa API internamente.

A [arquitetura do MCP](https://modelcontextprotocol.io/docs/learn/architecture) tem três papéis principais:

<InfoGrid columns={3} items={[
  { label: "Host", description: "A aplicação de IA em que o usuário trabalha. Ela coordena conexões, interações com o modelo e permissões.", color: "blue" },
  { label: "Cliente", description: "A parte dentro do host que mantém uma conexão com um servidor MCP.", color: "green" },
  { label: "Servidor", description: "Um programa que disponibiliza ferramentas, recursos ou prompts por MCP. Pode funcionar localmente ou de forma remota.", color: "amber" }
]} />

Para uma chamada de ferramenta, o cliente pode descobrir as ferramentas do servidor com `tools/list`. A aplicação disponibiliza ao modelo as definições das ferramentas relevantes. Se o modelo solicitar uma delas, a aplicação pode enviar uma solicitação `tools/call` pelo seu cliente MCP. O servidor executa ou delega a operação e devolve o resultado.

O modelo não precisa abrir uma conexão de rede sozinho. A aplicação e a implementação MCP cuidam da comunicação. A compatibilidade continua importante: o host e o servidor precisam suportar as capacidades que você quer usar. Descobrir uma ferramenta não garante permissão para executá-la; as verificações de acesso continuam valendo.

### O MCP oferece mais do que ferramentas

O MCP também define **recursos** e **prompts**. Essas palavras têm significados específicos no protocolo:

<InfoGrid columns={3} items={[
  { label: "Ferramentas", description: "Operações que o modelo pode solicitar, sujeitas aos controles da aplicação. Exemplo: pesquisar issues.", color: "blue" },
  { label: "Recursos", description: "Dados que a aplicação pode disponibilizar como contexto. Exemplo: um guia do projeto identificado por uma URI.", color: "green" },
  { label: "Prompts", description: "Modelos de mensagens reutilizáveis que os usuários podem selecionar, com argumentos opcionais. Exemplo: preparar um relatório de triagem de issues.", color: "amber" }
]} />

O [guia de conceitos do servidor MCP](https://modelcontextprotocol.io/docs/learn/server-concepts) descreve esses elementos como ferramentas controladas pelo modelo, recursos controlados pela aplicação e prompts controlados pelo usuário. Esses termos descrevem os padrões de interação previstos. Eles não removem as verificações de permissão da aplicação.

Um modelo de prompt MCP não é automaticamente uma skill. Uma skill pode reunir um procedimento mais longo, referências e scripts. Ela pode orientar o agente a usar ferramentas fornecidas por MCP, um conector direto ou funções locais.

### As skills também podem vir com o servidor

Até pouco tempo atrás, essas duas peças costumavam chegar separadas. Um servidor podia dar ao agente as suas ferramentas, mas o conhecimento para usá-las bem ficava em outro lugar: numa skill instalada à parte, num README ou no próprio prompt do usuário. Quando o serviço mudava, essas instruções podiam ficar para trás sem que ninguém percebesse.

A **extensão Skills** oficial do MCP, finalizada em setembro de 2026, fecha boa parte dessa lacuna. Agora um servidor pode oferecer não só as suas ferramentas, mas também as skills que explicam como usá-las, escritas no mesmo formato `SKILL.md` descrito em [Agentes e Habilidades](/book/25-agents-and-skills). As ferramentas dizem ao agente o que ele pode fazer. As skills dizem como fazer bem o trabalho. Agora as duas podem vir do mesmo servidor, de modo que as instruções ficam ao lado do serviço que descrevem e quem o mantém pode deixá-las sempre atualizadas.

O mecanismo se apoia em peças que você já conhece. Cada arquivo de uma skill é exposto como um recurso MCP, normalmente com uma URI `skill://`. Um cliente pode listar as skills de um servidor com `skills/list`, obter uma com `skills/get` e ler os arquivos de apoio com `resources/read`.

<Compare
  before={{ label: "Um servidor só com ferramentas", content: "O servidor do rastreador oferece search_issues e create_issue. O método de triagem (buscar duplicatas, seguir o modelo de issue) precisa vir de uma skill instalada à parte ou do seu prompt, e pode ficar desatualizado quando o serviço muda." }}
  after={{ label: "Um servidor que também traz uma skill", content: "O mesmo servidor também oferece uma skill de triagem de issues. No início, o host vê apenas o nome e a descrição dela e só carrega as instruções completas quando uma tarefa precisa delas. Quando os mantenedores mudam o serviço, podem atualizar a skill junto." }}
/>

O host continua decidindo como uma skill chega ao modelo. O modelo pode escolhê-la pelo nome e pela descrição, ou o usuário pode selecioná-la diretamente. Em qualquer caso, as instruções completas só entram no contexto quando são necessárias, e ler um arquivo `SKILL.md` não ativa a skill por si só.

<Callout type="warning" title="Uma skill vinda de um servidor continua sendo instrução">
Uma skill que vem de um servidor é texto que entra no contexto do agente e pode influenciar o que ele fará em seguida. Por isso, merece o mesmo escrutínio que o próprio servidor. Um host cuidadoso verifica o conteúdo e pede qualquer aprovação necessária antes de carregá-lo. Assim como outras extensões oficiais do MCP, como MCP Apps e MCP Tasks, Skills é opcional: só é usada quando o cliente e o servidor declaram suporte a ela. O suporte nos clientes ainda é inicial, então verifique se a sua aplicação realmente carrega skills de servidores antes de contar com isso.
</Callout>

## Dando instruções a um agente com ferramentas

Diga ao agente quais informações procurar, como usá-las e quais ações você espera. Evite presumir que existe uma conexão ou que uma ferramenta suporta todas as operações do serviço.

<Compare
  before={{ label: "Coisas demais para adivinhar", content: "Confira os bugs e resolva tudo." }}
  after={{ label: "Resultado e limites claros", content: "Pesquise no projeto conectado os bugs abertos sobre buscas sem resultados. Resuma as issues relevantes e inclua seus IDs. Prepare um rascunho de uma issue de acompanhamento se necessário, mas pergunte antes de criá-la. Se a conexão ou a ferramenta necessária estiver indisponível, explique o que falta. Não afirme que uma issue foi criada sem um resultado bem-sucedido da ferramenta." }}
/>

Uma skill reutilizável de triagem poderia acrescentar o método: buscar duplicatas, comparar os passos para reproduzir o problema, seguir o modelo de issue do projeto e relatar perguntas não resolvidas. A ferramenta fornece a operação. A skill explica como usá-la bem.

A saída da ferramenta ainda precisa ser avaliada. Um comentário de issue, um documento ou um resultado de busca pode conter erros ou texto que parece uma instrução. Trate o conteúdo recuperado como dados, sem permitir que ele altere a solicitação do usuário ou as regras da aplicação. O suporte a MCP, sozinho, não torna um servidor ou seu conteúdo confiável.

Se uma leitura falhar, o agente pode informar o erro ou tentar uma alternativa razoável. Se uma escrita exceder o tempo de espera, ele deve verificar se a alteração aconteceu antes de repeti-la. Caso contrário, uma nova tentativa pode criar uma issue duplicada. As credenciais devem ficar na configuração de conexão da integração, não no prompt da tarefa. Essas regras importam ainda mais quando um bot usa ferramentas em horários agendados enquanto você está fora, como descrito em [Bots sempre ativos](/book/28-persistent-bots).

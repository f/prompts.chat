## O Que São Agentes de IA?

Um **agente de IA** é um sistema de IA que pode autonomamente planejar, executar e iterar em tarefas. Diferente de interações simples de prompt-resposta, agentes podem:

- **Planejar** - Dividir objetivos complexos em passos acionáveis
- **Executar** - Usar ferramentas e tomar ações no mundo real
- **Observar** - Processar feedback de suas ações
- **Adaptar** - Ajustar sua abordagem baseado em resultados
- **Persistir** - Manter contexto e memória entre interações

Estes tipos de prompt se empilham juntos para formar comportamento completo de agente:

### Prompts de Sistema (A Identidade do Agente)

O prompt fundamental que estabelece quem o agente é e como se comporta:

```markdown
Você é um assistente de code review. Seu papel é:
- Analisar código para bugs, problemas de segurança e performance
- Sugerir melhorias seguindo melhores práticas
- Explicar seu raciocínio claramente
- Ser construtivo e educativo no feedback

Você tem acesso a ferramentas para ler arquivos, pesquisar código e rodar testes.
```

### Prompts de Planejamento (Como Pensar)

Instruções que guiam o processo de raciocínio e planejamento do agente:

```markdown
Antes de tomar ação, sempre:
1. Entenda a requisição completa
2. Divida em passos menores e verificáveis
3. Identifique quais ferramentas precisará
4. Considere casos limite e problemas potenciais
5. Execute passo a passo, validando conforme avança
```

### Prompts de Uso de Ferramentas (Como Agir)

Orientação sobre quando e como usar ferramentas disponíveis:

```markdown
Quando precisar entender um codebase:
- Use grep_search para encontrar padrões específicos
- Use read_file para examinar conteúdo de arquivos
- Use list_dir para explorar estrutura de diretórios
- Sempre verifique seu entendimento antes de fazer mudanças
```

### Prompts de Recuperação (Como Lidar com Falhas)

Instruções para quando as coisas dão errado:

```markdown
Se uma ação falhar:
1. Analise a mensagem de erro cuidadosamente
2. Considere abordagens alternativas
3. Peça esclarecimento se a tarefa for ambígua
4. Nunca repita a mesma ação falha sem mudanças
```

<Callout type="info" title="A Pilha de Prompts">
O comportamento de um agente emerge de camadas de prompts trabalhando juntas. O prompt de sistema define a fundação, prompts de planejamento guiam raciocínio, prompts de ferramentas habilitam ação, e prompts de recuperação lidam com falhas. Juntos, criam comportamento coerente e capaz.
</Callout>

## O Que São Skills?

Se prompts são os átomos, **skills são as moléculas**—blocos de construção reutilizáveis que dão aos agentes capacidades específicas.

Uma **skill** é um pacote abrangente e portátil de instruções que dá a um agente de IA expertise em um domínio ou tarefa específica. Skills são os blocos reutilizáveis de agentes: você os constrói uma vez, e qualquer agente pode usá-los.

<Callout type="tip" title="Skills = Blocos Reutilizáveis de Agentes">
Escreva uma skill para code review uma vez. Agora todo agente de código—seja para Python, JavaScript ou Rust—pode instantaneamente se tornar um expert code reviewer carregando essa skill. Skills permitem construir capacidades de agentes como blocos de LEGO.
</Callout>

O arquivo `SKILL.md` define a abordagem geral:

```markdown
---
name: code-review
description: Code review abrangente com análise de segurança, performance e estilo
---

# Skill de Code Review

Você é um expert code reviewer. Ao revisar código:

## Processo
1. **Entender Contexto** - O que este código faz? Que problema resolve?
2. **Verificar Correção** - Funciona? Há erros de lógica?
3. **Varredura de Segurança** - Reference security-checklist.md para vulnerabilidades comuns
4. **Review de Performance** - Verifique performance-tips.md para oportunidades de otimização
5. **Estilo & Manutenibilidade** - O código é legível e manutenível?

## Formato de Saída
Forneça feedback em categorias:
- 🔴 **Crítico** - Deve corrigir antes de merge
- 🟡 **Sugerido** - Melhorias recomendadas
- 🟢 **Bom ter** - Aprimoramentos opcionais

Sempre explique *por que* algo é um problema, não apenas *o que* está errado.
```

## Construindo Skills Eficazes

### 1. Defina a Expertise Claramente

Comece com uma descrição clara do que a skill permite:

```markdown
---
name: api-design
description: Projetar APIs RESTful seguindo melhores práticas da indústria, 
  incluindo versionamento, tratamento de erros e padrões de documentação
---
```

### 2. Estruture Conhecimento Hierarquicamente

Organize informação do geral para o específico:

```markdown
# Skill de Design de API

## Princípios Centrais
- Recursos devem ser substantivos, não verbos
- Use métodos HTTP semanticamente
- Versione suas APIs desde o primeiro dia

## Diretrizes Detalhadas
[Regras mais específicas...]

## Materiais de Referência
- Veja `rest-conventions.md` para convenções de nomenclatura
- Veja `error-codes.md` para respostas de erro padrão
```

### 3. Inclua Exemplos Concretos

Regras abstratas ficam claras com exemplos:

```markdown
## Nomenclatura de Endpoints

✅ Bom:
- GET /users/{id}
- POST /orders
- DELETE /products/{id}/reviews/{reviewId}

❌ Evite:
- GET /getUser
- POST /createNewOrder
- DELETE /removeProductReview
```

### 4. Forneça Frameworks de Decisão

Ajude o agente a fazer escolhas em situações ambíguas:

```markdown
## Quando Usar Paginação

Use paginação quando:
- Coleção pode exceder 100 itens
- Tamanho da resposta impacta performance
- Cliente pode não precisar de todos itens

Use resposta completa quando:
- Coleção é sempre pequena (<20 itens)
- Cliente tipicamente precisa de tudo
- Consistência em tempo real é crítica
```

### 5. Adicione Padrões de Recuperação

Antecipe o que pode dar errado:

```markdown
## Problemas Comuns

**Problema**: Cliente precisa de campos não na resposta padrão
**Solução**: Implemente seleção de campos: GET /users?fields=id,name,email

**Problema**: Mudanças breaking necessárias
**Solução**: Crie nova versão, deprecie antiga com cronograma
```

- **Modulares** - Cada skill lida bem com um domínio
- **Compatíveis** - Skills não devem dar instruções contraditórias
- **Priorizadas** - Quando skills se sobrepõem, defina qual tem precedência

## Quando as Skills Aprendem com a Experiência

Até aqui, todas as skills deste capítulo foram escritas por uma pessoa. Alguém percebe que uma tarefa volta sempre, senta e coloca em palavras como ela é feita. Mas um agente que trabalha com você dia após dia também vai guardando, em silêncio, um registro de como esse trabalho correu: quais instruções seguiu, onde você precisou intervir para corrigi-lo, quais passos ele teve que refazer. Um padrão mais recente aproveita esse registro. Em vez de esperar que alguém escreva a skill, o próprio sistema do agente olha para trás, para a sua experiência, e rascunha novas skills ou revisa as antigas por conta própria. Dá para imaginar isso como um ciclo, bem parecido com o ciclo do agente do início deste capítulo, só que mais lento e voltado para dentro:

A Perplexity descreve esse ciclo em detalhes para o **Brain**, o sistema de memória que se aprimora sozinho e que está por trás do seu agente Computer ([What is Brain?](https://www.perplexity.ai/help-center/en/articles/19700001-what-is-brain)). Em uma publicação de novembro de 2026 ([Self-improving skills](https://www.perplexity.ai/hub/blog/self-improving-skills)), a empresa explica como o Brain se apoia na memória e no histórico de sessões de um usuário para escrever e refinar skills *pessoais*. Na etapa de evidências, ele encontra sessões anteriores em que uma skill foi usada, principalmente aquelas em que ela deixou a desejar. Na reflexão, um agente de melhoria estuda essas sessões e propõe mudanças. A verificação confere se a proposta está bem formada e se tende a melhorar os resultados, e a ativação a aplica, de modo que as sessões seguintes viram evidências para a próxima rodada. O que torna o ciclo confiável é a cautela embutida nele. Uma skill nova exige duas ocorrências independentes do mesmo comportamento reutilizável, enquanto a atualização de uma skill existente pode se apoiar em uma única ocorrência bem fundamentada. O agente de melhoria nunca edita uma skill diretamente: ele escreve uma proposta com seu raciocínio e suas evidências, faz no máximo uma mudança por skill a cada execução e se abstém quando as evidências não justificam uma mudança. Além disso, as skills criadas automaticamente têm um limite de dez por usuário, então uma nova só entra se uma antiga for aposentada, com uma justificativa para a troca.

O **Hermes Agent**, da Nous Research, aborda a mesma ideia pelo lado de uma equipe. À medida que uma pessoa lhe delega trabalho recorrente, o Hermes transforma uma abordagem que deu certo em uma skill reutilizável: uma definição escrita acompanhada de código que executa os passos estáveis sempre da mesma forma ([Nous Research](https://nousresearch.com/press/hermes-enterprise-in-microsoft-teams)). O plugin Collective Wisdom cuida do momento em que uma skill sai do computador de uma pessoa. O Hermes pode sugerir que vale a pena compartilhar uma skill, mas a decisão continua com quem a escreveu, que revisa exatamente os arquivos que serão publicados na biblioteca da equipe. Os colegas então instalam uma versão específica, e não o que a skill por acaso pareça ser hoje ([Collective Wisdom](https://github.com/NousResearch/hermes-collective-wisdom)). O capítulo sobre [bots sempre ativos](/book/28-persistent-bots) mostra outro jeito de o Hermes aprender uma skill: quando alguém o conduz passo a passo por uma tarefa.

Lado a lado, os dois exemplos ensinam a mesma lição. Uma skill que se reescreve continua sendo um conjunto de instruções que um agente vai seguir, por isso merece o mesmo cuidado que uma escrita à mão. Peça evidências antes de uma mudança, de preferência de mais de uma sessão. Mantenha um ponto de revisão humana onde quer que uma skill passe de uma pessoa para outras. Guarde as versões, para que uma mudança ruim possa ser desfeita em vez de discutida. E fique de olho no desvio: uma skill revisada com frequência pode ir pendendo aos poucos para os hábitos de uma só pessoa ou para uma única sessão ruim, até descrever mais um humor passageiro do que o próprio trabalho.

O quanto subir a régua depende de quem a skill alcança. Uma skill pessoal, aprendida para um único usuário, pode se dar ao luxo de andar rápido, porque um erro só atinge esse usuário, que é justamente quem está em melhor posição para percebê-lo. Uma skill compartilhada ou nativa afeta todo mundo que a carrega. A Perplexity também traça essa linha: mudanças nas skills nativas que todos os usuários recebem precisam passar por testes de replay pareados e por revisão humana interna antes de chegar à versão oficial. Uma equipe pode adotar o mesmo instinto: deixar as skills pessoais aprenderem livremente e exigir que as compartilhadas mereçam cada mudança.

Você não precisa de um sistema que se aprimora sozinho para experimentar esse ciclo. Dá para percorrê-lo à mão, desde que você peça ao agente para propor em vez de aplicar:

## Compartilhando e Descobrindo Skills

Skills são mais valiosas quando compartilhadas. Plataformas como [prompts.chat](https://prompts.chat/skills) permitem você:

- **Descobrir** skills criadas pela comunidade para tarefas comuns
- **Baixar** skills diretamente para seus projetos
- **Compartilhar** sua própria expertise como skills reutilizáveis
- **Iterar** em skills baseado em uso real

Da mesma forma, dá para compartilhar unidades maiores do que uma única skill: bots inteiros, com suas instruções e rotinas, e equipes de bots que passam trabalho umas para as outras, como nos catálogos [Bots](https://prompts.chat/bots) e [Teams](https://prompts.chat/bots/teams). Exploramos as duas ideias no capítulo sobre [bots sempre ativos](/book/28-persistent-bots).

O agente fornece o framework de execução—planejamento, uso de ferramentas e memória—enquanto skills fornecem expertise de domínio. Esta separação significa:

- **Skills são portáteis** - A mesma skill funciona com diferentes agentes
- **Agentes são extensíveis** - Adicione novas capacidades adicionando skills
- **Expertise é compartilhável** - Especialistas de domínio podem contribuir skills sem construir agentes completos

## Melhores Práticas

### Para Construir Skills

1. **Comece específico, depois generalize** - Construa uma skill para seu caso de uso exato primeiro, depois abstraia
2. **Inclua casos de falha** - Documente o que a skill não pode fazer e como lidar
3. **Versione suas skills** - Rastreie mudanças para que agentes possam depender de versões estáveis
4. **Teste com tarefas reais** - Valide skills contra trabalho real, não apenas teoria

### Para Usar Skills com Agentes

1. **Leia a skill primeiro** - Entenda o que uma skill faz antes de implantá-la
2. **Customize com cuidado** - Sobrescreva defaults de skill apenas quando necessário
3. **Monitore performance** - Rastreie quão bem skills performam em seu contexto
4. **Contribua melhorias** - Quando melhorar uma skill, considere compartilhar de volta

エージェントに、プロジェクトの未解決のバグを探し、追加対応用の課題の下書きを作るよう頼みます。そのためには、良い指示だけでは足りません。課題管理ツールに接続し、必要なデータを読み、場合によっては新しい課題を作成する手段が必要です。

ここで登場するのが**ツール**、**コネクター**、**MCP**です。互いに関係していますが、それぞれ異なる部分を指しています。

## ツールには何が含まれる？

ツールには通常、**名前**、**説明**、**入力スキーマ**、そして実際に処理する実装があります。説明は、いつそのツールを使うかをモデルが判断する助けになります。スキーマは受け取れる引数を定義します。

架空のMCPツールの小さな定義を見てみましょう。

<Collapsible title="search_issuesの定義を見る">

```json
{
  "name": "search_issues",
  "description": "接続されたプロジェクトの課題を検索する。このツールはデータの読み取りのみを行う。",
  "inputSchema": {
    "type": "object",
    "properties": {
      "query": { "type": "string" },
      "limit": { "type": "integer", "minimum": 1, "maximum": 20 }
    },
    "required": ["query"],
    "additionalProperties": false
  }
}
```

</Collapsible>

モデルは`{"query": "未解決のバグ", "limit": 3}`を指定して`search_issues`を要求するかもしれません。周辺のアプリケーションがその要求を実装に送ります。実装は課題管理サービスに問い合わせ、結果またはエラーを返します。

名前とスキーマだけでは何も実行されません。実装が入力を検証し、アクセス権を確認し、実際の操作を行う必要があります。ツールの応答とモデルの最終回答も別です。たとえば応答に課題のIDやタイトルが含まれ、それをモデルが要約します。[MCPのツール仕様](https://modelcontextprotocol.io/specification/latest/server/tools)では、このような操作の公開方法を説明しています。

<Callout type="info" title="要求と結果は別のもの">
「課題を作成します」は発言です。ツール呼び出しは操作の要求です。新しい課題のIDを含む成功応答は、操作が行われた根拠です。この三つを区別しましょう。
</Callout>

### ツールはワークフロー全体を表すこともある

ここまで、ツールはどれも一つの操作でした。検索する、作成する、エクスポートする。けれども、ツール名の向こう側にあるものは、もっと大きくてもかまいません。あらかじめ書き定められ、ワークフローエンジンが実行するプロセス全体であってもよいのです。いつ**始めるか**、どんな**入力を渡すか**は、これまでどおりエージェントが決めます。そこから先は、プロセスが定めたとおりに、毎回同じ順序で進みます。

返金を例に考えてみましょう。サポート担当のエージェントは、不満を抱えた顧客の気持ちをくみ取るのは得意かもしれません。それでも、返金ポリシーを即興で運用されては困るはずです。返金ワークフローを一つのツールとしてまとめておけば、どの会話から始まったとしても、まず返金の対象かを確認し、次に責任者の承認を取り、最後に返金額を計上する、という順序が守られます。承認や本番環境へのデプロイなど、手順そのものがポリシー*である*プロセスも同じ形に収まります。また、ワークフローエンジンはたいてい実行ごとの記録を残すので、エージェントは過去の実行を調べ、夜のあいだにどの実行がどのステップで失敗したかを、推測ではなく事実として伝えられます。

最近の例として、AWSがあります。AWSは2026年10月29日、Step FunctionsのワークフローをAmazon Bedrock AgentCore Gateway経由でエージェントのツールとして使えるようになったと[発表しました](https://aws.amazon.com/about-aws/whats-new/2026/10/step-functions-workflows-ai-agent-tools/)。AgentCore Gatewayは、MCPを通じてエージェントとツールをつなぐサービスです。ただし、この考え方は特定のベンダーのものではありません。CIパイプライン、チケットシステムの承認フロー、チームがすでに信頼しているスクリプトなども、同じようにエージェントに渡せます。

ここで分け合っているのは、二つの強みです。モデルは柔軟で、いつもと違う状況を読み取り、妥当な次の一手を選べます。ワークフローは予測可能で、同じ入力なら同じ手順をたどります。始めるタイミングはエージェントに、手順はワークフローに任せれば、それぞれの強みが生きる場所に収まります。これはプロンプトの書き方も変えます。書くべきなのは目的と、ワークフローを呼び出すタイミングであって、その中の手順ではありません。手順をプロンプトで繰り返すと、ポリシーの二つ目の写しができてしまいます。その写しはいずれ本物とずれていくかもしれませんし、モデルが自分の手でなぞろうとするかもしれません。

<Compare
  before={{ label: "ワークフローを書き直す", content: "顧客に返金するときは、まず注文から30日以内かを確認し、次に責任者に確認して、それから返金額を計上し、最後に顧客へメールを送って。" }}
  after={{ label: "目的と呼び出すタイミングを書く", content: "顧客の請求に関する問題の解決を手伝って。顧客が返金を求めていて注文番号がわかっている場合は、その番号と理由を渡して返金ワークフローを呼び出して。返ってきた結果を報告して。ワークフローが確定する前に返金を約束しないこと。" }}
/>

## コネクターが追加するもの

コネクターは、特定のシステムとの連携をまとめたものです。サインイン、アカウントやワークスペースの選択、データの検索、対応する操作のツールとしての公開などを扱えます。検索や読み取りのみのコネクターもあれば、書き込みに対応するものもあります。

**コネクターは製品上の用語であり、一つの共通の技術標準ではありません。** サービスのAPIを直接呼ぶものも、MCPサーバーを使うものもあります。同期した文書から作ったインデックスを検索するものもあります。実際に使う連携機能が何に対応しているか確認しましょう。Microsoftの[コネクターの概要](https://learn.microsoft.com/en-us/azure/connectors/introduction)では、APIを利用する連携の例を紹介しています。

アカウントを接続しても、エージェントがすべてのファイルを見られる、すべてのデータをコンテキストに読み込む、すべての操作を実行できるという意味ではありません。アクセスは、アカウント、設定されたスコープ、アプリケーション、サービス側の権限に左右されます。検索結果が、元の文書より古いインデックスを反映していることもあります。

課題管理サービスでは、次の点を分けて考えましょう。接続は設定されているか。どのプロジェクトにアクセスできるか。読み取りだけか、それとも課題の作成もできるか。

## MCPが標準化すること

**MCP**は**Model Context Protocol**の略です。AIアプリケーションと、外部で機能を提供する側が通信するための共通の方法を定めています。サービスのAPIを置き換えるものではなく、MCPサーバーが内部でそのAPIを使うこともあります。

[MCPのアーキテクチャ](https://modelcontextprotocol.io/docs/learn/architecture)には、主に三つの役割があります。

<InfoGrid columns={3} items={[
  { label: "ホスト", description: "ユーザーが使うAIアプリケーション。接続、モデルとのやり取り、権限を調整する。", color: "blue" },
  { label: "クライアント", description: "ホストの内部でMCPサーバーとの接続を維持する部分。", color: "green" },
  { label: "サーバー", description: "MCPを通じてツール、リソース、プロンプトを提供するプログラム。ローカルでもリモートでも動かせる。", color: "amber" }
]} />

ツールを呼び出す際、クライアントは`tools/list`でサーバーのツールを見つけられます。アプリケーションは関連するツール定義をモデルに提供します。モデルがツールを要求すると、アプリケーションはMCPクライアントを通じて`tools/call`要求を送れます。サーバーは操作を実行するか別の処理に委ね、結果を返します。

モデル自身がネットワーク接続を開く必要はありません。通信はアプリケーションとMCPの実装が扱います。ただし互換性は必要です。ホストとサーバーの両方が、使いたい機能に対応していなければなりません。ツールを見つけても実行権限があるとは限らず、アクセスチェックは引き続き必要です。

### MCPはツール以外も提供する

MCPは**リソース**と**プロンプト**も定義しています。これらの言葉には、プロトコル内で特定の意味があります。

<InfoGrid columns={3} items={[
  { label: "ツール", description: "アプリケーションの制御のもとで、モデルが要求できる操作。例：課題の検索。", color: "blue" },
  { label: "リソース", description: "アプリケーションがコンテキストとして提供できるデータ。例：URIで識別されるプロジェクトガイド。", color: "green" },
  { label: "プロンプト", description: "ユーザーが選べる、再利用可能なメッセージのテンプレート。任意の引数を受け取ることもある。例：課題の分類・優先順位付けレポートを作る。", color: "amber" }
]} />

[MCPサーバーの概念ガイド](https://modelcontextprotocol.io/docs/learn/server-concepts)では、ツールはモデルが、リソースはアプリケーションが、プロンプトはユーザーが制御すると説明しています。これは想定する使い方の分類です。アプリケーションの権限チェックが不要になるわけではありません。

MCPのプロンプトテンプレートが、そのままスキルになるわけではありません。スキルには、長い手順、参考資料、スクリプトをまとめられます。MCP、直接接続のコネクター、ローカル関数から提供されるツールの使い方を、エージェントに説明することもあります。

### スキルもサーバーから届く

少し前まで、この二つは別々に届くのが普通でした。サーバーはエージェントにツールを渡せても、それを上手に使うためのノウハウは別の場所にありました。個別にインストールするスキル、READMEファイル、あるいはユーザー自身のプロンプトです。サービスが変わると、そうした手順はいつの間にか古くなってしまうことがありました。

2026年9月に正式版となったMCPの公式**Skills拡張**は、この隔たりを大きく埋めます。サーバーはツールだけでなく、その使い方を説明するスキルも提供できるようになりました。スキルは[エージェントとスキル](/book/25-agents-and-skills)で紹介したのと同じ`SKILL.md`形式で書かれます。ツールはエージェントに「何ができるか」を伝え、スキルは「どうすればうまくやれるか」を伝えます。その両方が同じサーバーから届くので、手順は説明対象のサービスのすぐそばに置かれ、サービスを保守する人たちが最新の状態に保てます。

仕組みは、すでに見てきた部品の上に成り立っています。スキル内の各ファイルはMCPのリソースとして公開され、慣例として`skill://`で始まるURIを持ちます。クライアントは`skills/list`でサーバーのスキルを一覧し、`skills/get`で1つを取得し、`resources/read`で補助ファイルを読み取れます。

<Compare
  before={{ label: "ツールだけを提供するサーバー", content: "課題管理サーバーはsearch_issuesとcreate_issueを公開しています。課題整理のやり方（重複の確認、課題テンプレートに従うこと）は、別途インストールしたスキルかあなたのプロンプトで補う必要があり、サービスが変わると古くなるおそれがあります。" }}
  after={{ label: "スキルも一緒に提供するサーバー", content: "同じサーバーが課題整理のスキルも提供します。ホストは最初にスキルの名前と説明だけを見て、タスクに必要になったときに初めて完全な手順を読み込みます。保守担当者はサービスを変更するとき、スキルも合わせて更新できます。" }}
/>

スキルをどうモデルに届けるかを決めるのは、引き続きホストです。モデルが名前と説明をもとに選ぶこともあれば、ユーザーが直接選ぶこともあります。どちらの場合も、完全な手順がコンテキストに入るのは必要になったときだけです。また、`SKILL.md`ファイルを読み取っただけでスキルが有効になるわけではありません。

<Callout type="warning" title="サーバーから届くスキルも指示である">
サーバーから届くスキルは、エージェントのコンテキストに入るテキストであり、その後の行動を左右することがあります。ですから、サーバーそのものと同じくらい慎重に扱う必要があります。注意深いホストは、読み込む前に内容を検証し、必要な承認を求めます。MCP Appsや、このあと紹介するTasks拡張など他の公式MCP拡張と同じく、Skillsは任意の拡張で、クライアントとサーバーの両方が対応を宣言したときにだけ使われます。クライアント側の対応はまだ始まったばかりです。頼りにする前に、使っているアプリケーションが実際にサーバーからスキルを読み込むかどうかを確認しましょう。
</Callout>

### ツールに時間や答えが必要なとき

ほとんどのツール呼び出しは短いやり取りです。エージェントが頼み、サーバーが答え、作業は先へ進みます。けれども、このリズムに収まらない仕事もあります。踏み込んだリサーチ、大きなレポートのエクスポート、ビルドなどは何分もかかることがありますし、この先どうするかをユーザーにしか決められない場面にたどり着く仕事もあります。MCPはこうした場面のために、二つの考え方を用意しています。時間のかかる仕事のための**Tasks**と、人の判断が必要な仕事のための**エリシテーション**（elicitation）です。

公式の[Tasks拡張](https://tasks.extensions.modelcontextprotocol.io/)（`io.modelcontextprotocol/tasks`）は、時間のかかる`tools/call`の終わり方を変えます。作業が終わるまでリクエストを開いたままにする代わりに、サーバーはすぐに永続的なタスクハンドルを返せます。クロークでコートを預けたときにもらう番号札のようなものです。クライアントは`tasks/get`でタスクの様子を確かめ、`tasks/update`で更新や回答を送り、`tasks/cancel`で止め、準備ができたら結果を受け取れます。その間、エージェントは別の作業を続け、あとで戻ってくることができます。これは、あなたが席を外している間も仕事をこなす[常時稼働ボット](/book/28-persistent-bots)にとって特に重要です。Tasksはどちらの側にとってもオプトインです。クライアントはリクエストごとに対応を宣言し、サーバーはリクエストごとにタスクを作るかどうかを判断します。既存のツールが自動的にこの能力を得るわけではなく、サーバーの作者が対応を加える必要があります。

<Compare
  before={{ label: "待たされるツール呼び出し", content: "エージェントがexport_reportを呼び出して待ちます。リクエストは何分も開いたままです。接続が切れると、エクスポートが終わったのか誰にもわからず、応答が返るまでエージェントはほかに何もできません。" }}
  after={{ label: "タスクハンドル", content: "エージェントがexport_reportを呼び出すと、すぐにタスクハンドルが返ってきます。エージェントは別の作業に移り、tasks/getでタスクを確認し、準備ができたら完成したレポートを受け取ります。予定が変われば、tasks/cancelで止められます。" }}
/>

[エリシテーション](https://modelcontextprotocol.io/specification/latest/client/elicitation)を使うと、サーバーは作業をいったん止め、ユーザーに構造化された入力を求められます。「ステージングにデプロイしますか？」「この返金を確定しますか？」といった確認や、それがないと作業を続けられない不足情報などです。ホストは小さなフォームを表示し、ユーザーは回答することも、断ることも、キャンセルすることもできます。断るのも正当な答えであり、その後どうするかはサーバーが決めます。二つの考え方は自然に結びつきます。実行中のタスクは`input_required`状態で一時停止し、作業の途中でユーザーに問いかけられるのです。書き込みの前に置かれたこうした問いは、判断が本当に必要なその場所で人が関わる、自然なチェックポイントになります。

<Callout type="warning" title="サーバーからのフォームも、サーバーからのリクエストです">
エリシテーションはアプリケーションではなくサーバーから届くものなので、ほかのツール出力と同じように慎重に扱う必要があります。答える前に何を求められているかを読み、信頼できるサーバーでない限り、パスワードやAPIキーなどの秘密情報をそうしたフォームに入力してはいけません。対応状況もアプリケーションによって異なります。VS Codeは[エリシテーションへの対応をドキュメントで説明しており](https://code.visualstudio.com/api/extension-guides/ai/mcp)、Cursorもエリシテーションに対応しています。Claude Codeはターミナルアプリに[MCP Tasksとエリシテーション](https://code.claude.com/docs/en/mcp)をパブリックベータとして追加しましたが、動作するすべての環境でまだ使えるわけではありません。公式の[クライアント対応表](https://modelcontextprotocol.io/extensions/client-matrix)で、どのアプリケーションがどの拡張に対応しているかを確認できます。どちらの機能も、頼りにする前に自分のアプリケーションが対応しているかを確かめましょう。
</Callout>

### サーバーを見つけ、接続は一度だけ

エージェントがリモートのサーバーを使うには、まず誰かがそのサーバーを見つけ、接続方法を調べ、サインインしなければなりません。長いあいだ、それはREADMEからURLをコピーし、どのトランスポートを使えばよいかを推測し、同じ設定をアプリケーションごとに繰り返すことを意味していました。いま、二種類の助けが届き始めています。クライアントが接続する**前に**読める情報と、**一度**設定すれば使い回せる接続です。

見つける側では、MCPの**Server Cards**拡張（[SEP-2127](https://modelcontextprotocol.io/seps/2127-mcp-server-cards)）が2026年10月6日に正式版となりました。この拡張が定めるのは、リモートサーバーについての小さな静的ドキュメントです。サーバーの名前、エンドポイントとトランスポート、対応するプロトコルのバージョンが書かれています。Webサイトは、`/.well-known/ai-catalog.json` に置いたAIカタログにカードを並べられます。そのため、ドメインを指定されたクライアントは、手作業の設定なしに、どこへどう接続すればよいかを知ることができます。カードにはツールの一覧があえて含まれていません。サーバーが提供するツールは、サインインしているユーザーによって変わりうるからです。ツールはこれまでどおり、接続後に `tools/list` で取得します。

つなぐ側では、GitHubが2026年10月28日、[GitHubが検証したMCPサーバー](https://github.blog/changelog/2026-10-28-connect-your-tools-to-copilot-without-all-the-setup/)のパブリックプレビューでの提供を始めました。GitHubはこれをコネクターとも呼んでいます。SlackやSentryのようなサービスに一度サインインすれば、その接続がCopilotアプリ、Copilot CLI、VS Code、クラウド上のCopilot、GitHub Mobileで使えます。

さらに、ツールはWebサービスだけではありません。同じ日、GoogleはAndroid Dev Summitで、Androidの統一的なツール呼び出しレイヤーと位置づける**AppFunctions**がベータになったと[発表しました](https://developer.android.com/blog/posts/build-it-your-way-a-next-era-of-android-development)。Android MCPを通じて、スマートフォン上のアプリは、メモの作成やメッセージの送信といった機能を、アプリ自身のオンデバイスエージェントやシステムレベルのエージェントに提供できます。しかも、誰かがそのアプリを開く必要はありません。

ここで、前に触れた点に戻ります。**コネクター**は製品上の用語です。サーバーカード、検証済みのバッジ、一度きりのサインインは、設定を楽にし、*誰に*接続しているのかを信頼する助けになります。けれども、*何を*許可するかまでは決めてくれません。どのアカウントをつなぐか、どの権限を認めるか、どの操作を承認待ちにするかを選ぶのは、やはりあなたです。見つけるためのメタデータも検証も、一覧に並んだツールが実際に何をできるのかを確かめる作業の代わりにはなりません。

## ツールを持つエージェントへの指示

探してほしい情報、その使い方、期待する操作をエージェントに伝えましょう。接続があることや、サービスのすべての操作にツールが対応していることを前提にしないでください。

<Compare
  before={{ label: "推測に任せすぎている", content: "バグを確認して、全部片づけて。" }}
  after={{ label: "明確な結果と境界", content: "接続されたプロジェクトで、検索結果が空になることに関する未解決のバグを探して。関連する課題を要約し、IDも含めて。必要なら追加対応用の課題を下書きして。ただし作成する前に確認して。接続や必要なツールが使えなければ、何が足りないか説明して。ツールの成功結果がないのに、課題を作成したと報告しないで。" }}
/>

再利用可能な課題整理スキルには、重複の確認、再現手順の比較、プロジェクトの課題テンプレートの使用、未解決の疑問の報告といった方法を追加できます。ツールが操作を提供し、スキルがその上手な使い方を説明します。

ツールの出力にも判断が必要です。課題のコメント、文書、検索結果には、間違いや指示のように見える文章が含まれることがあります。取得した内容はデータとして扱い、ユーザーの依頼やアプリケーションの規則を変更させないでください。MCPに対応しているだけで、サーバーや内容を信頼できるわけではありません。

読み取りに失敗した場合、エージェントはエラーを報告するか、妥当な代替手段を試せます。書き込みがタイムアウトした場合は、繰り返す前に変更が行われたか確認するべきです。そうしないと、再試行で課題が重複するかもしれません。認証情報はタスクのプロンプトではなく、連携の接続設定に置きます。[常時稼働ボット](/book/28-persistent-bots)で説明するように、あなたがいない間にボットがスケジュールに沿ってツールを使う場合、これらのルールはさらに重要になります。

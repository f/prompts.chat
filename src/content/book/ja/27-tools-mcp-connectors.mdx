エージェントに、プロジェクトの未解決のバグを探し、追加対応用の課題の下書きを作るよう頼みます。そのためには、良い指示だけでは足りません。課題管理ツールに接続し、必要なデータを読み、場合によっては新しい課題を作成する手段が必要です。

ここで登場するのが**ツール**、**コネクター**、**MCP**です。互いに関係していますが、それぞれ異なる部分を指しています。

## ツールには何が含まれる？

ツールには通常、**名前**、**説明**、**入力スキーマ**、そして実際に処理する実装があります。説明は、いつそのツールを使うかをモデルが判断する助けになります。スキーマは受け取れる引数を定義します。

架空のMCPツールの小さな定義を見てみましょう。

<Collapsible title="search_issuesの定義を見る">

```json
{
  "name": "search_issues",
  "description": "接続されたプロジェクトの課題を検索する。このツールはデータの読み取りのみを行う。",
  "inputSchema": {
    "type": "object",
    "properties": {
      "query": { "type": "string" },
      "limit": { "type": "integer", "minimum": 1, "maximum": 20 }
    },
    "required": ["query"],
    "additionalProperties": false
  }
}
```

</Collapsible>

モデルは`{"query": "未解決のバグ", "limit": 3}`を指定して`search_issues`を要求するかもしれません。周辺のアプリケーションがその要求を実装に送ります。実装は課題管理サービスに問い合わせ、結果またはエラーを返します。

名前とスキーマだけでは何も実行されません。実装が入力を検証し、アクセス権を確認し、実際の操作を行う必要があります。ツールの応答とモデルの最終回答も別です。たとえば応答に課題のIDやタイトルが含まれ、それをモデルが要約します。[MCPのツール仕様](https://modelcontextprotocol.io/specification/latest/server/tools)では、このような操作の公開方法を説明しています。

<Callout type="info" title="要求と結果は別のもの">
「課題を作成します」は発言です。ツール呼び出しは操作の要求です。新しい課題のIDを含む成功応答は、操作が行われた根拠です。この三つを区別しましょう。
</Callout>

## コネクターが追加するもの

コネクターは、特定のシステムとの連携をまとめたものです。サインイン、アカウントやワークスペースの選択、データの検索、対応する操作のツールとしての公開などを扱えます。検索や読み取りのみのコネクターもあれば、書き込みに対応するものもあります。

**コネクターは製品上の用語であり、一つの共通の技術標準ではありません。** サービスのAPIを直接呼ぶものも、MCPサーバーを使うものもあります。同期した文書から作ったインデックスを検索するものもあります。実際に使う連携機能が何に対応しているか確認しましょう。Microsoftの[コネクターの概要](https://learn.microsoft.com/en-us/azure/connectors/introduction)では、APIを利用する連携の例を紹介しています。

アカウントを接続しても、エージェントがすべてのファイルを見られる、すべてのデータをコンテキストに読み込む、すべての操作を実行できるという意味ではありません。アクセスは、アカウント、設定されたスコープ、アプリケーション、サービス側の権限に左右されます。検索結果が、元の文書より古いインデックスを反映していることもあります。

課題管理サービスでは、次の点を分けて考えましょう。接続は設定されているか。どのプロジェクトにアクセスできるか。読み取りだけか、それとも課題の作成もできるか。

## MCPが標準化すること

**MCP**は**Model Context Protocol**の略です。AIアプリケーションと、外部で機能を提供する側が通信するための共通の方法を定めています。サービスのAPIを置き換えるものではなく、MCPサーバーが内部でそのAPIを使うこともあります。

[MCPのアーキテクチャ](https://modelcontextprotocol.io/docs/learn/architecture)には、主に三つの役割があります。

<InfoGrid columns={3} items={[
  { label: "ホスト", description: "ユーザーが使うAIアプリケーション。接続、モデルとのやり取り、権限を調整する。", color: "blue" },
  { label: "クライアント", description: "ホストの内部でMCPサーバーとの接続を維持する部分。", color: "green" },
  { label: "サーバー", description: "MCPを通じてツール、リソース、プロンプトを提供するプログラム。ローカルでもリモートでも動かせる。", color: "amber" }
]} />

ツールを呼び出す際、クライアントは`tools/list`でサーバーのツールを見つけられます。アプリケーションは関連するツール定義をモデルに提供します。モデルがツールを要求すると、アプリケーションはMCPクライアントを通じて`tools/call`要求を送れます。サーバーは操作を実行するか別の処理に委ね、結果を返します。

モデル自身がネットワーク接続を開く必要はありません。通信はアプリケーションとMCPの実装が扱います。ただし互換性は必要です。ホストとサーバーの両方が、使いたい機能に対応していなければなりません。ツールを見つけても実行権限があるとは限らず、アクセスチェックは引き続き必要です。

### MCPはツール以外も提供する

MCPは**リソース**と**プロンプト**も定義しています。これらの言葉には、プロトコル内で特定の意味があります。

<InfoGrid columns={3} items={[
  { label: "ツール", description: "アプリケーションの制御のもとで、モデルが要求できる操作。例：課題の検索。", color: "blue" },
  { label: "リソース", description: "アプリケーションがコンテキストとして提供できるデータ。例：URIで識別されるプロジェクトガイド。", color: "green" },
  { label: "プロンプト", description: "ユーザーが選べる、再利用可能なメッセージのテンプレート。任意の引数を受け取ることもある。例：課題の分類・優先順位付けレポートを作る。", color: "amber" }
]} />

[MCPサーバーの概念ガイド](https://modelcontextprotocol.io/docs/learn/server-concepts)では、ツールはモデルが、リソースはアプリケーションが、プロンプトはユーザーが制御すると説明しています。これは想定する使い方の分類です。アプリケーションの権限チェックが不要になるわけではありません。

MCPのプロンプトテンプレートが、そのままスキルになるわけではありません。スキルには、長い手順、参考資料、スクリプトをまとめられます。MCP、直接接続のコネクター、ローカル関数から提供されるツールの使い方を、エージェントに説明することもあります。

### スキルもサーバーから届く

少し前まで、この二つは別々に届くのが普通でした。サーバーはエージェントにツールを渡せても、それを上手に使うためのノウハウは別の場所にありました。個別にインストールするスキル、READMEファイル、あるいはユーザー自身のプロンプトです。サービスが変わると、そうした手順はいつの間にか古くなってしまうことがありました。

2026年9月に正式版となったMCPの公式**Skills拡張**は、この隔たりを大きく埋めます。サーバーはツールだけでなく、その使い方を説明するスキルも提供できるようになりました。スキルは[エージェントとスキル](/book/25-agents-and-skills)で紹介したのと同じ`SKILL.md`形式で書かれます。ツールはエージェントに「何ができるか」を伝え、スキルは「どうすればうまくやれるか」を伝えます。その両方が同じサーバーから届くので、手順は説明対象のサービスのすぐそばに置かれ、サービスを保守する人たちが最新の状態に保てます。

仕組みは、すでに見てきた部品の上に成り立っています。スキル内の各ファイルはMCPのリソースとして公開され、慣例として`skill://`で始まるURIを持ちます。クライアントは`skills/list`でサーバーのスキルを一覧し、`skills/get`で1つを取得し、`resources/read`で補助ファイルを読み取れます。

<Compare
  before={{ label: "ツールだけを提供するサーバー", content: "課題管理サーバーはsearch_issuesとcreate_issueを公開しています。課題整理のやり方（重複の確認、課題テンプレートに従うこと）は、別途インストールしたスキルかあなたのプロンプトで補う必要があり、サービスが変わると古くなるおそれがあります。" }}
  after={{ label: "スキルも一緒に提供するサーバー", content: "同じサーバーが課題整理のスキルも提供します。ホストは最初にスキルの名前と説明だけを見て、タスクに必要になったときに初めて完全な手順を読み込みます。保守担当者はサービスを変更するとき、スキルも合わせて更新できます。" }}
/>

スキルをどうモデルに届けるかを決めるのは、引き続きホストです。モデルが名前と説明をもとに選ぶこともあれば、ユーザーが直接選ぶこともあります。どちらの場合も、完全な手順がコンテキストに入るのは必要になったときだけです。また、`SKILL.md`ファイルを読み取っただけでスキルが有効になるわけではありません。

<Callout type="warning" title="サーバーから届くスキルも指示である">
サーバーから届くスキルは、エージェントのコンテキストに入るテキストであり、その後の行動を左右することがあります。ですから、サーバーそのものと同じくらい慎重に扱う必要があります。注意深いホストは、読み込む前に内容を検証し、必要な承認を求めます。MCP AppsやMCP Tasksなど他の公式MCP拡張と同じく、Skillsは任意の拡張で、クライアントとサーバーの両方が対応を宣言したときにだけ使われます。クライアント側の対応はまだ始まったばかりです。頼りにする前に、使っているアプリケーションが実際にサーバーからスキルを読み込むかどうかを確認しましょう。
</Callout>

## ツールを持つエージェントへの指示

探してほしい情報、その使い方、期待する操作をエージェントに伝えましょう。接続があることや、サービスのすべての操作にツールが対応していることを前提にしないでください。

<Compare
  before={{ label: "推測に任せすぎている", content: "バグを確認して、全部片づけて。" }}
  after={{ label: "明確な結果と境界", content: "接続されたプロジェクトで、検索結果が空になることに関する未解決のバグを探して。関連する課題を要約し、IDも含めて。必要なら追加対応用の課題を下書きして。ただし作成する前に確認して。接続や必要なツールが使えなければ、何が足りないか説明して。ツールの成功結果がないのに、課題を作成したと報告しないで。" }}
/>

再利用可能な課題整理スキルには、重複の確認、再現手順の比較、プロジェクトの課題テンプレートの使用、未解決の疑問の報告といった方法を追加できます。ツールが操作を提供し、スキルがその上手な使い方を説明します。

ツールの出力にも判断が必要です。課題のコメント、文書、検索結果には、間違いや指示のように見える文章が含まれることがあります。取得した内容はデータとして扱い、ユーザーの依頼やアプリケーションの規則を変更させないでください。MCPに対応しているだけで、サーバーや内容を信頼できるわけではありません。

読み取りに失敗した場合、エージェントはエラーを報告するか、妥当な代替手段を試せます。書き込みがタイムアウトした場合は、繰り返す前に変更が行われたか確認するべきです。そうしないと、再試行で課題が重複するかもしれません。認証情報はタスクのプロンプトではなく、連携の接続設定に置きます。[常時稼働ボット](/book/28-persistent-bots)で説明するように、あなたがいない間にボットがスケジュールに沿ってツールを使う場合、これらのルールはさらに重要になります。

L'ingénierie des prompts est rarement un processus en une seule étape. Les meilleurs prompts émergent à travers l'itération—tester, observer et affiner jusqu'à atteindre les résultats souhaités.

<Callout type="info" title="Premier jet, pas version finale">
Considérez votre premier prompt comme un brouillon. Même les ingénieurs de prompts expérimentés réussissent rarement du premier coup.
</Callout>

## Le cycle d'itération

L'affinement efficace des prompts suit un cycle prévisible : écrire, tester, analyser et améliorer. Chaque itération vous rapproche d'un prompt qui produit de manière fiable les résultats dont vous avez besoin.

## Schémas d'affinement courants

La plupart des échecs de prompts relèvent d'une poignée de catégories. Apprendre à reconnaître ces schémas vous permet de diagnostiquer et de corriger rapidement les problèmes sans repartir de zéro.

### Problème : sortie trop longue

C'est l'un des problèmes les plus courants. Sans contraintes explicites, les modèles ont tendance à être exhaustifs plutôt que concis.

<DiffView 
  before="Explique comment fonctionne la photosynthèse."
  after={`Explique comment fonctionne la photosynthèse en 3-4 phrases adaptées à un enfant de 10 ans.`}
  beforeLabel="Original"
  afterLabel="Affiné"
/>

### Problème : sortie trop vague

Les prompts vagues produisent des sorties vagues. Le modèle ne peut pas deviner ce que « meilleur » signifie pour vous, ni quels aspects comptent le plus à vos yeux.

<DiffView 
  before="Donne-moi des conseils pour de meilleures présentations."
  after={`Donne-moi 5 conseils précis et directement applicables pour améliorer des présentations techniques destinées à un public non technique. Pour chaque conseil, donne un exemple concret.`}
  beforeLabel="Original"
  afterLabel="Affiné"
/>

### Problème : mauvais ton

Le ton est subjectif et varie selon le contexte. Ce qui semble « professionnel » au modèle ne correspond pas forcément à la voix de votre organisation ni à la relation que vous entretenez avec votre destinataire.

<DiffView 
  before="Écris un email d'excuses pour avoir manqué une échéance."
  after={`Écris un email d'excuses professionnel mais chaleureux pour avoir manqué l'échéance d'un projet. Le ton doit montrer que j'assume la responsabilité sans m'excuser à l'excès. Inclus un plan concret pour éviter de nouveaux retards.`}
  beforeLabel="Original"
  afterLabel="Affiné"
/>

### Problème : informations clés manquantes

Une demande ouverte appelle une réponse ouverte. Si vous avez besoin de retours d'un type précis, vous devez les demander explicitement.

<DiffView 
  before="Relis ce code."
  after={`Relis ce code Python en cherchant :
1. Les bugs et erreurs logiques
2. Les problèmes de performance
3. Les failles de sécurité
4. Le style de code (PEP 8)

Pour chaque problème trouvé, explique-le et propose une correction.

[code]`}
  beforeLabel="Original"
  afterLabel="Affiné"
/>

### Problème : format incohérent

Sans modèle de réponse, le modèle structurera chaque réponse différemment, ce qui rend la comparaison difficile et l'automatisation impossible.

  before="Analyse ces trois produits."

### Étape 2 : faire des changements ciblés

Résistez à l'envie de tout réécrire. Changer plusieurs variables à la fois empêche de savoir ce qui a aidé et ce qui a nui. Faites un changement, testez-le, puis continuez :

```
Itération 1 : Ajouter une contrainte de longueur
Itération 2 : Préciser le format
Itération 3 : Ajouter un exemple
Itération 4 : Affiner les consignes de ton
```

### Étape 3 : documenter ce qui fonctionne

Le savoir-faire en ingénierie des prompts se perd facilement. Tenez un journal de ce que vous avez essayé et pourquoi. Vous gagnerez du temps quand vous reviendrez sur le prompt ou que vous affronterez des problèmes similaires :

```markdown
## Prompt : réponse à un email client

### Version 1 (trop formelle)
"Écris une réponse à cette réclamation client."

### Version 2 (meilleur ton, structure encore absente)
"Écris une réponse amicale mais professionnelle à cette réclamation. 
Commence par faire preuve d'empathie."

### Version 3 (finale, bons résultats)
"Écris une réponse à cette réclamation client. Structure :
1. Reconnaître sa frustration (1 phrase)
2. S'excuser de façon précise (1 phrase)  
3. Expliquer la solution (2-3 phrases)
4. Proposer une aide supplémentaire (1 phrase)

Ton : amical, professionnel, empathique mais pas obséquieux."
```

## Stratégies d'affinement par type de tâche

Chaque type de tâche échoue de façon prévisible. Connaître les modes d'échec courants vous aide à diagnostiquer et à corriger les problèmes plus vite.

### Pour la génération de contenu

La génération de contenu produit souvent des textes génériques, à côté du sujet ou mal formatés. La solution consiste généralement à préciser davantage les contraintes, à fournir des exemples concrets ou à définir explicitement la voix de votre marque.

<InfoGrid items={[
  { icon: "target", title: "Trop générique", description: "Ajouter des contraintes et un contexte précis", example: "« Écris sur les chiens » → « Écris sur les golden retrievers pour des propriétaires débutants, en te concentrant sur le dressage et les besoins d'exercice »" },
  { icon: "scissors", title: "Trop long", description: "Fixer une limite de mots ou de paragraphes", example: "Ajouter : « Réponds en moins de 150 mots » ou « 3 paragraphes maximum »" },
  { icon: "palette", title: "Mauvais style", description: "Fournir des exemples de style", example: "« Écris dans le style de cet exemple : [coller un extrait] »" },
  { icon: "megaphone", title: "Hors de l'image de marque", description: "Inclure les règles de voix de la marque", example: "« Adopte un ton amical et décontracté. Évite le jargon. Tutoie le lecteur. »" }
]} />

### Pour la génération de code

Le code produit peut échouer sur le plan technique (erreurs de syntaxe, fonctionnalités du langage inadaptées) ou sur le plan architectural (mauvais schémas de conception, cas oubliés). Les problèmes techniques demandent de préciser la version et l'environnement ; les problèmes d'architecture demandent des consignes de conception.

  { icon: "git-branch", title: "Mauvaise approche", description: "Décrire les schémas de conception préférés", example: "« Adopte une approche fonctionnelle, évite les classes » ou « Suis le pattern repository »" },
  { icon: "shield", title: "Cas limites oubliés", description: "Lister les scénarios à gérer", example: "« Gère : entrée vide, valeurs null, délais réseau dépassés, formats invalides »" },
  { icon: "tag", title: "Nommage médiocre", description: "Inclure les conventions de nommage", example: "« Utilise le camelCase pour les variables, le PascalCase pour les classes, UPPER_SNAKE pour les constantes »" }

### Pour l'analyse

Les tâches d'analyse produisent souvent des résultats superficiels ou peu structurés. Guidez le modèle avec des cadres précis (SWOT, cinq forces de Porter), demandez plusieurs points de vue ou fournissez un modèle pour la structure de la réponse.

### Pour les questions-réponses

Les réponses aux questions peuvent être trop laconiques ou trop bavardes, et manquer d'indications de fiabilité ou de sources. Précisez le niveau de détail attendu et si vous voulez des citations ou une expression de l'incertitude.

  { icon: "help-circle", title: "Incertain", description: "Demander un niveau de confiance", example: "« Évalue ta confiance de 1 à 10 » ou « Signale les hypothèses que tu fais »" },

## La technique de la boucle de rétroaction

Voici une méta-technique : utilisez le modèle lui-même pour améliorer vos prompts. Montrez-lui ce que vous avez essayé, ce que vous avez obtenu et ce que vous vouliez. Il peut souvent suggérer des améliorations auxquelles vous n'aviez pas pensé.

```
J'ai utilisé ce prompt :
"[votre prompt]"

Et j'ai obtenu cette sortie :
"[sortie du modèle]"

Je voulais quelque chose de plus [décrire l'écart]. Comment devrais-je 
modifier mon prompt pour obtenir de meilleurs résultats ?
```

## Tests A/B de prompts

Pour les prompts destinés à être utilisés de façon répétée ou à grande échelle, ne vous contentez pas du premier qui fonctionne. Testez des variantes pour trouver l'approche la plus fiable et de la meilleure qualité.

```
Prompt A : "Résume cet article en 3 points."
Prompt B : "Extrais les 3 idées les plus importantes de cet article."
Prompt C : "Quels sont les principaux enseignements de cet article ? Cites-en 3."
```

Exécutez chacun plusieurs fois et comparez :
- La cohérence des sorties
- La qualité des informations
- La pertinence par rapport à vos besoins

## Quand arrêter d'itérer

Le mieux est l'ennemi du bien. Sachez reconnaître quand votre prompt est prêt à servir et quand vous ne faites plus que le peaufiner pour des gains de plus en plus faibles.

## Gestion de versions pour les prompts

Les prompts sont du code. Tout prompt utilisé en production mérite la même rigueur : gestion de versions, journal des modifications et possibilité de revenir en arrière si quelque chose casse.

<Callout type="tip" title="Versionnage intégré">
De nombreux outils de prompts conservent un historique des versions à votre place. Sur prompts.chat, par exemple, chaque modification du texte d'un prompt est enregistrée comme une nouvelle version, et vous pouvez comparer deux versions côte à côte.
</Callout>

Pour les prompts que vous gérez vous-même, utilisez une arborescence de dossiers :

```
prompts/
├── reponse-client/
│   ├── v1.0.txt    # Version initiale
│   ├── v1.1.txt    # Correction du ton
│   ├── v2.0.txt    # Restructuration majeure
│   └── current.txt # Lien symbolique vers la version active
└── changelog.md    # Historique des modifications
```

## Résumé

<Callout type="tip" title="Points clés à retenir">
Commencez simple, observez attentivement, changez une chose à la fois, documentez ce qui fonctionne, et sachez quand arrêter. Les meilleurs prompts ne sont pas écrits—ils sont découverts par l'itération systématique.
</Callout>

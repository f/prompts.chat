Vous demandez à un agent de trouver les bugs ouverts dans votre projet et de rédiger un ticket de suivi. Pour cela, de bonnes instructions ne suffisent pas. Il lui faut un moyen d'accéder à votre outil de suivi, de lire les bonnes données et, éventuellement, d'y créer quelque chose.

C'est là qu'interviennent les **outils**, les **connecteurs** et **MCP**. Ils sont liés, mais décrivent des parties différentes de la configuration.

Un outil peut aussi fonctionner localement. Une calculatrice n'a pas besoin d'une connexion à un compte. Un outil de lecture de fichiers peut fonctionner entièrement sur votre ordinateur. Un service externe n'est qu'une source possible d'outils.

## Ce que contient réellement un outil

Un outil possède généralement un **nom**, une **description**, un **schéma d'entrée** et une implémentation qui effectue le travail. La description aide le modèle à décider quand l'utiliser. Le schéma décrit les arguments qu'il accepte.

Voici une petite définition fictive d'outil MCP :

<Collapsible title="Examiner la définition de search_issues">

```json
{
  "name": "search_issues",
  "description": "Rechercher des tickets dans le projet connecté. Cet outil lit uniquement des données.",
  "inputSchema": {
    "type": "object",
    "properties": {
      "query": { "type": "string" },
      "limit": { "type": "integer", "minimum": 1, "maximum": 20 }
    },
    "required": ["query"],
    "additionalProperties": false
  }
}
```

</Collapsible>

Le modèle pourrait demander `search_issues` avec `{"query": "bugs ouverts", "limit": 3}`. L'application transmet cette demande à l'implémentation. Celle-ci interroge le système de suivi et renvoie des résultats ou une erreur.

Le nom et le schéma n'exécutent rien par eux-mêmes. L'implémentation doit valider les entrées, vérifier l'accès et effectuer l'opération. La réponse d'un outil est aussi distincte de la réponse finale du modèle : elle peut contenir des identifiants et des titres de tickets que le modèle résume ensuite. La [spécification des outils MCP](https://modelcontextprotocol.io/specification/latest/server/tools) décrit comment les outils rendent ces opérations accessibles.

<Callout type="info" title="Une demande n'est pas un résultat">
« Je vais créer un ticket » est une déclaration. Un appel d'outil demande l'opération. Une réponse réussie avec l'identifiant du nouveau ticket prouve qu'elle a eu lieu. Gardez ces trois choses distinctes.
</Callout>

### Un outil peut représenter tout un workflow

Jusqu'ici, chaque outil était une seule opération : chercher, créer, exporter. Mais ce qui se cache derrière le nom d'un outil peut être bien plus vaste. Ce peut être un processus entier, écrit à l'avance et exécuté par un moteur de workflows. L'agent décide toujours **quand** le lancer et **quelles données** lui transmettre. Tout le reste se déroule exactement comme le processus le prévoit, dans le même ordre, à chaque fois.

Prenez un remboursement. Un agent de support peut très bien comprendre un client mécontent, mais vous ne voulez sans doute pas qu'il improvise votre politique de remboursement. Emballé dans un seul outil, le workflow de remboursement vérifie d'abord l'éligibilité, demande ensuite l'accord d'un responsable, puis crédite le montant, quelle que soit la conversation qui l'a déclenché. Les validations, les déploiements et les autres processus dont les étapes *sont* la politique entrent dans le même moule. Les moteurs de workflows gardent en général une trace de chaque exécution : l'agent peut donc aussi consulter les exécutions passées et vous dire lesquelles ont échoué pendant la nuit, et à quelle étape, au lieu de deviner.

AWS en donne un exemple récent. Le 29 octobre 2026, AWS a [annoncé](https://aws.amazon.com/about-aws/whats-new/2026/10/step-functions-workflows-ai-agent-tools/) que les workflows Step Functions peuvent servir d'outils aux agents via Amazon Bedrock AgentCore Gateway, qui relie les agents à des outils grâce à MCP. L'idée n'appartient à aucun fournisseur en particulier : un pipeline de CI, un circuit de validation dans un outil de tickets ou un script auquel votre équipe fait déjà confiance peuvent être proposés à un agent de la même façon.

Il s'agit de répartir deux qualités. Le modèle est souple : il sait lire une situation inhabituelle et choisir une suite raisonnable. Le workflow est prévisible : la même entrée passe par les mêmes étapes. Laisser le moment à l'agent et les étapes au workflow place chaque qualité là où elle sert le mieux. Cela change aussi le prompt. Décrivez l'objectif et le moment d'appeler le workflow, pas les étapes qu'il contient. Répéter les étapes crée une seconde copie de la politique, qui peut s'écarter de l'originale et que le modèle risque de vouloir suivre lui-même, à la main.

  before={{ label: "Redécrire le workflow", content: "Pour rembourser un client, vérifie d'abord que la commande date de moins de 30 jours, puis demande à un responsable, crédite ensuite le montant et envoie enfin un e-mail au client." }}
  after={{ label: "Décrire l'objectif et le déclencheur", content: "Aide les clients à résoudre leurs problèmes de facturation. Quand un client demande un remboursement et que tu as le numéro de commande, appelle le workflow de remboursement avec ce numéro et le motif. Rends compte du résultat qu'il renvoie. Ne promets aucun remboursement avant que le workflow l'ait confirmé." }}
/>

## Ce qu'ajoute un connecteur

Un connecteur regroupe l'intégration avec un système particulier. Il peut gérer la connexion, le choix d'un compte ou d'un espace de travail, la recherche de données et la présentation des actions disponibles sous forme d'outils. Certains connecteurs permettent seulement de chercher ou de lire. D'autres permettent aussi d'écrire.

**Connecteur est un terme de produit, pas une norme technique universelle.** Un connecteur peut appeler directement l'API d'un service. Un autre peut utiliser un serveur MCP. Un troisième peut interroger un index construit à partir de documents synchronisés. Vérifiez ce que l'intégration concernée prend en charge. La [présentation des connecteurs de Microsoft](https://learn.microsoft.com/en-us/azure/connectors/introduction) donne un exemple d'intégrations basées sur des API.

Connecter un compte ne signifie pas que l'agent voit tous les fichiers, charge toutes vos données dans son contexte ou peut effectuer n'importe quelle action. L'accès dépend du compte, des portées d'autorisation configurées, de l'application et des permissions du service. Les résultats de recherche peuvent aussi provenir d'un index plus ancien que les documents d'origine.

Pour le système de suivi, séparez ces questions : une connexion est-elle configurée ? À quel projet donne-t-elle accès ? Permet-elle seulement de lire, ou aussi de créer des tickets ?

## Ce que MCP standardise

**MCP** signifie **Model Context Protocol**. Il définit une méthode commune de communication entre les applications IA et les fournisseurs de capacités externes. Il ne remplace pas l'API d'un service ; un serveur MCP peut utiliser cette API en arrière-plan.

L'[architecture MCP](https://modelcontextprotocol.io/docs/learn/architecture) comporte trois rôles principaux :

<InfoGrid columns={3} items={[
  { label: "Hôte", description: "L'application IA dans laquelle l'utilisateur travaille. Elle coordonne les connexions, les interactions avec le modèle et les permissions.", color: "blue" },
  { label: "Client", description: "La partie de l'hôte qui maintient une connexion avec un serveur MCP.", color: "green" },
  { label: "Serveur", description: "Un programme qui rend des outils, des ressources ou des prompts accessibles via MCP. Il peut fonctionner localement ou à distance.", color: "amber" }
]} />

Pour un appel d'outil, le client peut découvrir les outils du serveur avec `tools/list`. L'application fournit au modèle les définitions des outils pertinents. Si le modèle en demande un, l'application peut envoyer une requête `tools/call` via son client MCP. Le serveur exécute ou délègue l'opération, puis renvoie le résultat.

Le modèle n'a pas besoin d'ouvrir lui-même une connexion réseau. L'application et l'implémentation MCP gèrent la communication. La compatibilité reste importante : l'hôte et le serveur doivent prendre en charge les capacités que vous voulez utiliser. Découvrir un outil ne garantit pas le droit de l'exécuter ; les contrôles d'accès s'appliquent toujours.

### MCP propose plus que des outils

MCP définit aussi des **ressources** et des **prompts**. Ces mots ont un sens précis dans le protocole :

<InfoGrid columns={3} items={[
  { label: "Outils", description: "Des opérations que le modèle peut demander, sous réserve des contrôles de l'application. Exemple : rechercher des tickets.", color: "blue" },
  { label: "Ressources", description: "Des données que l'application peut fournir comme contexte. Exemple : un guide de projet identifié par une URI.", color: "green" },
  { label: "Prompts", description: "Des modèles de messages réutilisables que les utilisateurs peuvent sélectionner, avec des arguments facultatifs. Exemple : préparer un rapport de tri des tickets.", color: "amber" }
]} />

Le [guide des concepts de serveur MCP](https://modelcontextprotocol.io/docs/learn/server-concepts) les décrit comme des outils contrôlés par le modèle, des ressources contrôlées par l'application et des prompts contrôlés par l'utilisateur. Ces termes décrivent les modes d'interaction prévus. Ils ne suppriment pas les contrôles de permissions de l'application.

Un modèle de prompt MCP n'est pas automatiquement un skill. Un skill peut regrouper une procédure plus longue, des références et des scripts. Il peut expliquer à l'agent comment utiliser des outils fournis via MCP, un connecteur direct ou des fonctions locales.

### Les skills peuvent aussi venir avec le serveur

Jusqu'à récemment, ces deux pièces arrivaient le plus souvent séparément. Un serveur pouvait donner ses outils à un agent, mais le savoir-faire pour bien s'en servir se trouvait ailleurs : dans un skill installé à part, dans un README ou dans le prompt de l'utilisateur. Quand le service changeait, ces instructions pouvaient prendre du retard sans que personne ne s'en aperçoive.

L'**extension Skills** officielle de MCP, finalisée en septembre 2026, comble une bonne partie de cet écart. Un serveur peut désormais proposer non seulement ses outils, mais aussi les skills qui expliquent comment les utiliser, rédigés dans le même format `SKILL.md` que celui décrit dans [Agents et Compétences](/book/25-agents-and-skills). Les outils disent à l'agent ce qu'il peut faire. Les skills lui disent comment bien faire le travail. Désormais, les deux peuvent venir du même serveur : les instructions vivent à côté du service qu'elles décrivent, et ceux qui le maintiennent peuvent les tenir à jour.

Le mécanisme repose sur des éléments que vous connaissez déjà. Chaque fichier d'un skill est exposé comme une ressource MCP, généralement avec une URI `skill://`. Un client peut lister les skills d'un serveur avec `skills/list`, en récupérer un avec `skills/get` et lire ses fichiers annexes avec `resources/read`.

<Compare
  before={{ label: "Un serveur qui n'offre que des outils", content: "Le serveur du gestionnaire de tickets expose search_issues et create_issue. La méthode de tri (chercher les doublons, suivre le modèle de ticket) doit venir d'un skill installé à part ou de votre prompt, et elle peut se périmer quand le service évolue." }}
  after={{ label: "Un serveur qui fournit aussi un skill", content: "Le même serveur propose aussi un skill de tri des tickets. L'hôte ne voit d'abord que son nom et sa description, et ne charge les instructions complètes que lorsqu'une tâche en a besoin. Quand les mainteneurs font évoluer le service, ils peuvent mettre le skill à jour en même temps." }}
/>

C'est toujours l'hôte qui décide comment un skill parvient au modèle. Le modèle peut le choisir d'après son nom et sa description, ou l'utilisateur peut le sélectionner directement. Dans les deux cas, les instructions complètes n'entrent dans le contexte qu'au moment où elles sont utiles, et la simple lecture d'un fichier `SKILL.md` n'active pas le skill.

<Callout type="warning" title="Un skill fourni par un serveur reste une instruction">
Un skill venu d'un serveur est du texte qui entre dans le contexte de l'agent et peut orienter ce qu'il fera ensuite. Il mérite donc le même examen que le serveur lui-même. Un hôte prudent vérifie le contenu et demande toute approbation nécessaire avant de le charger. Comme d'autres extensions officielles de MCP, par exemple MCP Apps et l'extension Tasks présentée juste après, Skills est facultative : elle n'est utilisée que si le client et le serveur déclarent tous deux la prendre en charge. La prise en charge côté client n'en est qu'à ses débuts ; vérifiez donc que votre application charge réellement des skills depuis les serveurs avant de compter dessus.
</Callout>

### Quand un outil a besoin de temps ou d'une réponse

La plupart des appels d'outils sont de brefs échanges : l'agent demande, le serveur répond, et le travail continue. Certaines tâches ne suivent pas ce rythme. Une recherche approfondie, l'export d'un gros rapport ou une compilation peuvent prendre de longues minutes, et certains travaux arrivent à un point où seul l'utilisateur peut décider de la suite. MCP propose deux idées pour ces moments-là : **Tasks**, pour le travail qui demande du temps, et l'**élicitation** (*elicitation*), pour le travail qui demande une personne.

L'[extension officielle Tasks](https://tasks.extensions.modelcontextprotocol.io/) (`io.modelcontextprotocol/tasks`) change la façon dont se termine un `tools/call` lent. Au lieu de garder la requête ouverte jusqu'à la fin du travail, le serveur peut répondre aussitôt avec un identifiant de tâche durable, un peu comme le ticket qu'on vous remet au vestiaire. Le client peut consulter la tâche avec `tasks/get`, envoyer des mises à jour ou des réponses avec `tasks/update`, l'arrêter avec `tasks/cancel`, et récupérer le résultat quand il est prêt. Entre-temps, l'agent reste libre de poursuivre son travail et de revenir plus tard, ce qui compte surtout pour les [bots toujours actifs](/book/28-persistent-bots) qui travaillent pendant votre absence. Tasks est facultatif des deux côtés : le client déclare sa prise en charge à chaque requête, et le serveur décide, requête par requête, s'il crée une tâche. Les outils existants n'acquièrent pas cette capacité d'eux-mêmes ; c'est à l'auteur du serveur de l'ajouter.

<Compare
  before={{ label: "Un appel d'outil bloquant", content: "L'agent appelle export_report et attend. La requête reste ouverte pendant des minutes. Si la connexion tombe, personne ne sait si l'export est terminé, et l'agent ne peut rien faire d'autre avant la réponse." }}
  after={{ label: "Un identifiant de tâche", content: "L'agent appelle export_report et reçoit aussitôt un identifiant de tâche. Il passe à autre chose, consulte la tâche avec tasks/get et récupère le rapport une fois prêt. Si les plans changent, tasks/cancel l'arrête." }}
/>

L'[élicitation](https://modelcontextprotocol.io/specification/latest/client/elicitation) permet à un serveur de marquer une pause pour demander à l'utilisateur des informations structurées : « Déployer en staging ? », « Confirmer ce remboursement ? », ou un détail manquant sans lequel le travail ne peut pas continuer. L'hôte affiche un petit formulaire, et l'utilisateur peut répondre, refuser ou annuler. Refuser est aussi une réponse valable, et c'est le serveur qui décide de la suite. Les deux idées se rejoignent naturellement : une tâche en cours peut se mettre en pause dans l'état `input_required` et poser une question à l'utilisateur en plein travail. Avant une écriture, une telle question est un point de contrôle naturel où l'humain garde la main, placé exactement là où la décision compte.

<Callout type="warning" title="Un formulaire venu d'un serveur reste une demande du serveur">
Une élicitation vient du serveur, pas de votre application ; elle mérite donc le même examen que n'importe quelle sortie d'outil. Lisez ce qui vous est demandé avant de répondre, et ne saisissez jamais un mot de passe, une clé d'API ou tout autre secret dans un tel formulaire si vous ne faites pas confiance au serveur. La prise en charge varie aussi d'une application à l'autre : VS Code [documente sa prise en charge de l'élicitation](https://code.visualstudio.com/api/extension-guides/ai/mcp), Cursor prend en charge l'élicitation, et Claude Code a ajouté [MCP Tasks et les élicitations](https://code.claude.com/docs/en/mcp) en bêta publique dans son application de terminal, mais pas encore partout où il fonctionne. La [matrice officielle de prise en charge des clients](https://modelcontextprotocol.io/extensions/client-matrix) indique quelles applications prennent en charge quelles extensions ; vérifiez donc la vôtre avant de compter sur l'une ou l'autre de ces fonctionnalités.
</Callout>

### Trouver un serveur et ne se connecter qu'une fois

Avant qu'un agent puisse utiliser un serveur distant, quelqu'un doit le trouver, comprendre comment s'y connecter et s'identifier. Longtemps, cela voulait dire copier une URL depuis un README, deviner quel transport utiliser et refaire la configuration dans chaque application. Deux sortes d'aide arrivent désormais : des informations qu'un client peut lire **avant** de se connecter, et des connexions que l'on configure **une fois** pour les réutiliser.

Côté découverte, l'extension **Server Cards** de MCP ([SEP-2127](https://modelcontextprotocol.io/seps/2127-mcp-server-cards)) a été finalisée le 6 octobre 2026. Elle décrit un petit document statique consacré à un serveur distant : son nom, ses points de terminaison et ses transports, ainsi que les versions du protocole qu'il prend en charge. Un site peut répertorier ses cartes dans un catalogue d'IA à l'adresse `/.well-known/ai-catalog.json`, si bien qu'un client à qui l'on indique un domaine peut apprendre où et comment se connecter sans configuration manuelle. La carte laisse volontairement de côté la liste des outils, car les outils d'un serveur peuvent varier selon l'utilisateur connecté. Ceux-ci s'obtiennent toujours avec `tools/list` une fois la connexion établie.

Côté connexion, GitHub a commencé le 28 octobre 2026 à déployer en préversion publique les [serveurs MCP vérifiés par GitHub](https://github.blog/changelog/2026-10-28-connect-your-tools-to-copilot-without-all-the-setup/), qu'il appelle aussi connecteurs. Vous vous connectez une seule fois à un service comme Slack ou Sentry, et la connexion fonctionne dans l'application Copilot, dans Copilot CLI, dans VS Code, dans Copilot dans le cloud et dans GitHub Mobile.

Les outils ne sont d'ailleurs pas seulement des services web. Le même jour, lors de l'Android Dev Summit, Google a [annoncé](https://developer.android.com/blog/posts/build-it-your-way-a-next-era-of-android-development) qu'**AppFunctions**, qu'il présente comme la couche unifiée d'appel d'outils d'Android, est désormais en bêta. Grâce à Android MCP, une application de votre téléphone peut proposer des fonctions, comme créer une note ou envoyer un message, à son propre agent sur l'appareil ou à des agents du système, sans que personne ait besoin d'ouvrir l'application.

Cela nous ramène à une idée vue plus haut : **connecteur** est un terme de produit. Une carte de serveur, un badge de vérification et une connexion unique simplifient la mise en place et vous aident à savoir *à qui* vous vous connectez. Ils ne décident pas de *ce que* vous accordez. C'est toujours vous qui choisissez quel compte connecter, quelles permissions autoriser et quelles actions doivent attendre votre accord. Ni les métadonnées de découverte ni la vérification ne remplacent l'examen de ce que les outils peuvent réellement faire une fois qu'ils sont listés.

## Donner des instructions à un agent doté d'outils

Indiquez à l'agent quelles informations chercher, comment les utiliser et quelles actions vous attendez. Ne supposez pas qu'une connexion existe ni qu'un outil prend en charge toutes les opérations du service.

Un skill de tri réutilisable pourrait ajouter la méthode : chercher les doublons, comparer les étapes de reproduction, suivre le modèle de ticket du projet et signaler les questions non résolues. L'outil fournit l'opération. Le skill explique comment bien l'utiliser.

Les résultats d'outils demandent toujours du jugement. Un commentaire de ticket, un document ou un résultat de recherche peut contenir des erreurs ou du texte qui ressemble à une instruction. Traitez le contenu récupéré comme des données, sans le laisser changer la demande de l'utilisateur ou les règles de l'application. Le support de MCP ne suffit pas à rendre un serveur ou son contenu digne de confiance.

Si une lecture échoue, l'agent peut signaler l'erreur ou essayer une alternative raisonnable. Si une écriture dépasse le délai prévu, il devrait vérifier si la modification a eu lieu avant de réessayer. Sinon, une nouvelle tentative pourrait créer un doublon. Les identifiants de connexion doivent rester dans la configuration de l'intégration, pas dans le prompt de la tâche. Ces règles comptent encore plus quand un bot utilise des outils selon un planning pendant votre absence, comme le décrit [Bots toujours actifs](/book/28-persistent-bots).

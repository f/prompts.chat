Vous demandez à une IA de corriger un bug. Elle lit le projet, modifie un fichier, lance un test, constate un échec et réessaie. Le modèle fait partie de ce processus. Mais il faut aussi un système pour ouvrir les fichiers, exécuter les commandes et renvoyer les résultats.

Ce logiciel qui entoure le modèle est le **harness**. Après avoir découvert les agents et les skills, il est utile de regarder le système qui les fait fonctionner ensemble.

## Qu'est-ce qu'un harness ?

Un **harness d'agent** est le logiciel qui fait fonctionner un agent IA. Il prépare le contexte du modèle, met des outils à disposition, traite les demandes d'utilisation des outils et gère les étapes d'une tâche. Selon l'application, il peut aussi gérer les permissions, la progression enregistrée, les nouvelles tentatives et les limites.

Les termes *agent*, *framework* et *harness* sont parfois utilisés de manière assez vague. Dans ce chapitre, nous faisons les distinctions suivantes :

Un harness peut être une petite boucle dans votre application ou une partie d'un assistant de programmation plus complet. Il n'a pas besoin de plusieurs agents ni d'un framework compliqué. Anthropic explique cette distinction entre un agent et son harness dans son [guide d'évaluation des agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents).

<Callout type="info" title="Deux usages du même mot">
Un harness d'agent exécute le travail de l'agent. Un harness d'évaluation lance des tâches de test et mesure les performances de ce système. Ils peuvent fonctionner ensemble, mais leurs rôles sont différents.
</Callout>

## Comment fonctionne la boucle

Imaginez que la tâche consiste à améliorer une page de recherche sans résultats. Une boucle typique ressemble à ceci :

1. **Préparer le contexte.** Inclure la demande, les instructions du projet, celles des skills pertinents et les définitions des outils disponibles.
2. **Appeler le modèle.** Il peut répondre directement ou demander un outil, par exemple pour lire le composant de recherche.
3. **Vérifier et exécuter.** Le harness valide la demande et vérifie les permissions avant l'exécution de l'outil.
4. **Renvoyer l'observation.** Le contenu du fichier, la sortie de la commande ou l'erreur rejoint le contexte du modèle.
5. **Continuer ou s'arrêter.** Le modèle utilise ces éléments pour l'étape suivante. Le harness applique aussi des limites et peut attendre une réponse de l'utilisateur.

Écrire « lance les tests » dans une réponse n'exécute rien. Un vrai outil doit lancer la commande et renvoyer son résultat. Ce retour permet à l'agent de réagir à ce qui s'est réellement passé. Consultez l'[explication des workflows d'agents d'Anthropic](https://www.anthropic.com/engineering/building-effective-agents).

## Pourquoi les prompts comptent dans un harness

Un harness donne au modèle un moyen d'agir. Vos prompts expliquent quelles actions sont utiles. Sans objectif clair, un agent peut passer de nombreuses étapes à faire un travail dont vous n'avez pas besoin.

La demande actuelle n'est qu'une partie des instructions. Une application peut aussi fournir un prompt système, des consignes de projet, des descriptions d'outils et les instructions d'un skill chargé. Le harness décide comment ces éléments entrent dans le contexte ; le modèle suit la hiérarchie des instructions utilisée par ce système.

Vous n'avez pas besoin de décrire chaque clic ou chaque commande. Définissez le résultat, les contraintes pertinentes et les critères de fin. Laissez l'agent choisir les étapes courantes quand cette souplesse est utile.

Les descriptions d'outils font aussi partie du prompting. Un outil dont les entrées, les sorties et les limites sont claires est plus facile à utiliser correctement pour le modèle. Ajouter des outils sans les expliquer peut créer de la confusion.

## La place des skills

Un prompt décrit généralement la tâche actuelle. Un **skill** conserve une méthode que vous souhaitez réutiliser pour différentes tâches : relire une modification, analyser un bug ou préparer un rapport.

Dans le [format Agent Skills](https://agentskills.io/specification), un skill possède un fichier `SKILL.md` et peut inclure des scripts, des références et des ressources. Un harness compatible permet de découvrir les skills. Il peut d'abord fournir leurs noms et descriptions, charger les instructions du skill sélectionné quand elles sont pertinentes et ne lire les fichiers complémentaires qu'en cas de besoin. C'est ce qu'on appelle la **divulgation progressive**.

<Collapsible title="Ouvrir un petit skill de correction de bugs">

```markdown
---
name: verify-bug-fix
description: À utiliser pour corriger un bug reproductible dans un projet existant.
---

1. Lire les instructions du projet et le code concerné.
2. Reproduire le comportement signalé ou expliquer pourquoi ce n'est pas possible.
3. Faire la plus petite modification qui corrige la cause.
4. Exécuter les vérifications pertinentes, y compris un cas proche qui doit toujours fonctionner.
5. Présenter la modification, les preuves et les incertitudes restantes.

Si un outil nécessaire est indisponible, expliquer la limite.
Ne pas présenter une vérification non exécutée comme réussie.
```

</Collapsible>

Le harness a toujours besoin des outils et de l'environnement attendus par le skill. Un skill qui décrit un test dans un navigateur n'installe pas de navigateur. Un script peut avoir besoin de dépendances. Les instructions peuvent nécessiter des adaptations lorsqu'elles passent à un autre harness avec des outils différents. Charger un skill n'entraîne pas non plus le modèle et ne garantit pas une expertise.

Utilisez le prompt de la tâche pour ce qui est spécifique aujourd'hui. Placez une procédure répétée dans un skill. Gardez les règles communes du projet dans les fichiers d'instructions pris en charge par votre harness. Cela évite de copier une longue liste légèrement différente dans chaque demande.

## Les instructions et les permissions ont des rôles différents

« Ne modifie pas de fichiers en dehors de ce projet » est une instruction utile. Une limite du système de fichiers qui bloque ces écritures est un contrôle appliqué par le système. Une configuration fiable utilise les deux.

Les permissions, le sandboxing et les contrôles d'approbation doivent être mis en œuvre par le harness, ses outils ou l'environnement sous-jacent. Un prompt ne peut pas les imposer à lui seul. La [documentation de VS Code sur la sécurité des agents](https://code.visualstudio.com/docs/agents/run/security) donne des exemples concrets de ces contrôles.

Cette distinction compte aussi pour les informations renvoyées par les outils. Une page web ou un fichier de dépôt peut contenir du texte qui ressemble à une instruction. Traitez ce texte comme des données de la tâche, sauf s'il provient d'une source d'instructions fiable. Limitez l'accès à ce dont le travail a besoin.

## Où vit le harness ?

Tout agent fonctionne dans un harness, mais il faut bien que quelqu'un le construise, l'héberge et le maintienne en état de marche. Qui s'en charge détermine ce que vous contrôlez et ce que vous devez entretenir. Aujourd'hui, un harness vous arrive généralement par l'une de ces quatre voies :

      <td>S'intègre aux pipelines existants ; personne ne regarde une conversation pendant qu'il tourne</td>
    </tr>
  </tbody>
</table>

La fin d'octobre 2026 a fourni un exemple parlant pour chacune des trois dernières. L'[Agent SDK](https://cursor.com/blog/agent-sdk) de Cursor, disponible pour tous depuis le 20 octobre, traite un agent comme un petit projet : des prompts en Markdown, des outils écrits comme des fonctions TypeScript, et des évaluations (evals) juste à côté. Vous pouvez exécuter l'agent en local, le déployer sur l'infrastructure de Cursor ou le faire tourner sur vos propres serveurs comme un simple processus Node. Le 28 octobre, Microsoft a lancé en préversion publique le [Copilot harness dans Foundry Agent Service](https://devblogs.microsoft.com/foundry/microsoft-copilot-harness-in-foundry/). C'est le [même harness](https://blogs.microsoft.com/blog/2026/10/28/introducing-the-microsoft-copilot-harness-unlocking-the-potential-of-truly-multi-model-agentic-work/) que celui qui fait fonctionner GitHub Copilot dans son application, sa CLI et VS Code. Microsoft fait tourner la boucle de l'agent et la sandbox ; vous apportez les skills, les outils MCP et des définitions d'agent que vous pouvez garder sous contrôle de version. Le même jour, [GitHub Agentic Workflows](https://github.blog/changelog/2026-10-28-github-agentic-workflows-generally-available/) est devenu disponible pour tous. On y décrit une tâche, comme le tri des nouvelles issues, dans un fichier Markdown, qui est ensuite compilé en un workflow GitHub Actions tout à fait ordinaire, exécutant Copilot ou un autre agent de code.

L'endroit où vit le harness décide aussi de l'endroit où ses limites sont appliquées. Les instructions orientent ; les permissions s'imposent. Dans votre propre boucle, c'est à vous de construire ces garde-fous. Avec un service géré ou une plateforme d'automatisation, c'est la plateforme qui les fournit, et vous qui les configurez. Agentic Workflows montre combien de couches cela peut représenter : par défaut, les agents n'ont que des droits de lecture et s'exécutent dans un conteneur isolé derrière un pare-feu, et les modifications qu'ils proposent passent par des « safe outputs » validées puis par une analyse des menaces distincte avant que quoi que ce soit ne soit appliqué. Votre prompt dit toujours quoi faire. La plateforme limite les dégâts qu'une erreur peut causer.

Ce que vous écrivez voyage généralement mieux que la boucle elle-même. Les skills et MCP sont des standards ouverts, et l'annonce de Microsoft fait de leur prise en charge la marque d'un harness sérieux. Un skill clair ou une bonne description d'outil passe souvent d'un harness à l'autre moyennant quelques ajustements ; du code écrit autour d'une boucle particulière, rarement. Plus haut, nous conseillions de garder le même modèle pour comparer des harnesses. Un harness multimodèle permet l'expérience inverse : Foundry vous laisse choisir un modèle pris en charge sans réécrire l'orchestration, et Agentic Workflows laisse chaque workflow choisir son fournisseur de modèles. Vous pouvez changer de modèle en gardant tout le reste en place.

Quelle que soit la voie choisie, certaines choses ne passent jamais au fournisseur : le résultat que vous visez, les instructions et les skills qui le décrivent, les outils et les accès que vous accordez, et les vérifications qui montrent que le travail est fait. Un harness peut faire tourner la boucle à votre place. Il ne peut pas décider de ce que « terminé » veut dire.

## Qu'est-ce qui rend un harness utile ?

Plus d'autonomie n'est utile que si le système peut vérifier son travail et se remettre des problèmes. Pour une tâche longue, regardez comment le harness gère ces points :

- **Contexte :** Garder les instructions et les preuves pertinentes disponibles. Résumer les anciennes étapes peut économiser de la place, mais aussi faire perdre des détails.
- **Progression :** Enregistrer les décisions et le travail inachevé pour que la prochaine session puisse continuer. L'état enregistré doit tout de même être chargé dans le contexte.
- **Échecs :** Renvoyer clairement les erreurs, limiter les nouvelles tentatives et éviter de répéter aveuglément des actions ayant des effets de bord.
- **Limites :** S'arrêter à une limite de temps, de coût ou d'étapes, ou quand le travail nécessite une réponse de l'utilisateur. S'arrêter ne prouve pas la réussite.
- **Vérification :** Examiner les fichiers réels, les résultats de tests ou d'autres résultats. Un message final assuré ne suffit pas.

Pour comparer des configurations, essayez les mêmes tâches réelles et examinez les résultats ainsi que les traces d'exécution. Gardez le même modèle quand vous voulez étudier un changement de harness. Changez un seul prompt, skill ou réglage d'outil à la fois, et répétez les tâches car les exécutions varient.

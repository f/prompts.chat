אתם מבקשים מסוכן למצוא את הבאגים הפתוחים בפרויקט ולהכין טיוטה של משימת המשך. כדי לעשות את זה, הוא צריך יותר מהוראות טובות. הוא צריך דרך להגיע למערכת מעקב הבעיות שלכם, לקרוא את הנתונים הנכונים ואולי גם ליצור שם משהו.

## מה כלי באמת מכיל

לכלי יש בדרך כלל **שם**, **תיאור**, **סכמת קלט** ומימוש שמבצע את העבודה. התיאור עוזר למודל להחליט מתי להשתמש בו. הסכמה מתארת את הארגומנטים שהוא מקבל.

הנה הגדרה קטנה של כלי MCP דמיוני:

<Collapsible title="בדקו את ההגדרה של search_issues">

```json
{
  "name": "search_issues",
  "description": "חפש דיווחים בפרויקט המחובר. הכלי הזה רק קורא נתונים.",
  "inputSchema": {
    "type": "object",
    "properties": {
      "query": { "type": "string" },
      "limit": { "type": "integer", "minimum": 1, "maximum": 20 }
    },
    "required": ["query"],
    "additionalProperties": false
  }
}
```

</Collapsible>

המודל עשוי לבקש את `search_issues` עם `{"query": "באגים פתוחים", "limit": 3}`. היישום שסביבו מנתב את הבקשה למימוש. המימוש פונה למערכת המעקב ומחזיר תוצאות או שגיאה.

השם והסכמה לא מבצעים דבר בעצמם. המימוש צריך לבדוק את הקלט, לבדוק גישה ולבצע את הפעולה עצמה. גם תגובת הכלי נפרדת מהתשובה הסופית של המודל: התגובה עשויה לכלול מזהים וכותרות של דיווחים, שהמודל מסכם אחר כך. [מפרט הכלים של MCP](https://modelcontextprotocol.io/specification/latest/server/tools) מתאר איך כלים חושפים את הפעולות האלה.

<Callout type="info" title="בקשה אינה תוצאה">
"אצור דיווח" היא אמירה. קריאה לכלי מבקשת את הפעולה. תגובה מוצלחת עם המזהה של הדיווח החדש היא ראיה לכך שהפעולה התבצעה. הפרידו בין שלושת הדברים האלה.
</Callout>

## מה המחבר מוסיף

מחבר אורז את האינטגרציה עם מערכת מסוימת. הוא יכול לטפל בכניסה לחשבון, בבחירת חשבון או סביבת עבודה, במציאת נתונים ובחשיפת פעולות נתמכות ככלים. חלק מהמחברים רק מחפשים או קוראים. אחרים תומכים גם בכתיבה.

**מחבר הוא מונח של מוצר, ולא תקן טכני אוניברסלי אחד.** מחבר אחד עשוי לקרוא ישירות ל־API של השירות. אחר עשוי להשתמש בשרת MCP. שלישי עשוי לחפש באינדקס שנבנה ממסמכים שסונכרנו. בדקו במה האינטגרציה המסוימת תומכת. [הסקירה של Microsoft על מחברים](https://learn.microsoft.com/en-us/azure/connectors/introduction) נותנת דוגמה לאינטגרציות שנבנו סביב API.

חיבור חשבון לא אומר שהסוכן רואה כל קובץ, טוען את כל הנתונים שלכם להקשר שלו או מורשה לבצע כל פעולה. הגישה תלויה בחשבון, בהיקפי ההרשאה שהוגדרו, ביישום ובהרשאות של השירות עצמו. גם תוצאות החיפוש עשויות להגיע מאינדקס שפחות מעודכן מהמסמכים המקוריים.

במערכת מעקב הבעיות, הפרידו בין השאלות האלה: האם הוגדר חיבור? לאיזה פרויקט הוא יכול לגשת? האם הוא יכול רק לקרוא, או גם ליצור דיווחים?

## מה MCP מתקנן

**MCP** הוא קיצור של **Model Context Protocol**, פרוטוקול ההקשר של המודל. הוא מגדיר דרך משותפת לתקשורת בין יישומי AI לספקים של יכולות חיצוניות. הוא לא מחליף את ה־API של השירות; שרת MCP יכול להשתמש באותו API מאחורי הקלעים.

המודל לא צריך לפתוח חיבור רשת בעצמו. היישום ומימוש ה־MCP מטפלים בתקשורת. התאימות עדיין חשובה: המארח והשרת צריכים לתמוך ביכולות שתרצו להשתמש בהן. גילוי כלי לא מבטיח הרשאה להפעיל אותו; בדיקות הגישה עדיין חלות.

תבנית פרומפט של MCP אינה אוטומטית מיומנות. מיומנות יכולה לארוז נוהל ארוך יותר, חומרי עזר וסקריפטים. היא יכולה להסביר לסוכן איך להשתמש בכלים שמגיעים דרך MCP, מחבר ישיר או פונקציות מקומיות.

### מיומנויות יכולות להגיע גם עם השרת

עד לא מזמן, שני החלקים האלה הגיעו בדרך כלל בנפרד. שרת יכול היה לתת לסוכן את הכלים שלו, אבל הידע איך להשתמש בהם היטב ישב במקום אחר: במיומנות שהותקנה בנפרד, בקובץ README או בפרומפט של המשתמש עצמו. כשהשירות השתנה, ההוראות האלה יכלו להתיישן בלי שאיש ישים לב.

**הרחבת Skills** הרשמית של MCP, שהגיעה לגרסה סופית בספטמבר 2026, סוגרת חלק גדול מהפער הזה. שרת יכול עכשיו להציע לא רק את הכלים שלו אלא גם את המיומנויות שמסבירות איך להשתמש בהם, כתובות באותו פורמט `SKILL.md` שמתואר בפרק [סוכנים ומיומנויות](/book/25-agents-and-skills). הכלים אומרים לסוכן מה הוא יכול לעשות. המיומנויות אומרות לו איך לעשות את העבודה היטב. עכשיו שניהם יכולים להגיע מאותו שרת, כך שההוראות נמצאות לצד השירות שהן מתארות, ומי שמתחזקים אותו יכולים לשמור אותן מעודכנות.

המנגנון נשען על רכיבים שכבר הכרתם. כל קובץ במיומנות נחשף כמשאב MCP, בדרך כלל עם URI מסוג `skill://`. לקוח יכול להציג את רשימת המיומנויות של שרת באמצעות `skills/list`, לקבל אחת מהן באמצעות `skills/get` ולקרוא את קובצי העזר שלה באמצעות `resources/read`.

המארח עדיין מחליט איך מיומנות מגיעה למודל. המודל יכול לבחור בה לפי השם והתיאור שלה, או שהמשתמש יכול לבחור בה ישירות. בכל מקרה, ההוראות המלאות נכנסות להקשר רק כשיש בהן צורך, וקריאה של קובץ `SKILL.md` לא מפעילה את המיומנות כשלעצמה.

<Callout type="warning" title="מיומנות שמגיעה משרת היא עדיין הוראות">
מיומנות שמגיעה משרת היא טקסט שנכנס להקשר של הסוכן, והיא יכולה להשפיע על מה שיעשה בהמשך. לכן היא ראויה לאותה בדיקה כמו השרת עצמו. מארח זהיר מאמת את התוכן ומבקש כל אישור נדרש לפני שהוא טוען אותו. כמו הרחבות רשמיות אחרות של MCP, למשל MCP Apps ו־MCP Tasks, גם Skills היא אופציונלית: משתמשים בה רק כשגם הלקוח וגם השרת מצהירים שהם תומכים בה. התמיכה בצד הלקוחות עדיין בראשיתה, אז בדקו אם היישום שלכם באמת טוען מיומנויות משרתים לפני שאתם סומכים עליהן.
</Callout>

## כתיבת פרומפט לסוכן שיש לו כלים

אמרו לסוכן איזה מידע לחפש, איך להשתמש בו ואילו פעולות אתם מצפים שיבצע. אל תניחו שחיבור קיים או שכלי תומך בכל פעולה שהשירות מציע.

מיומנות למיון ראשוני שאפשר להשתמש בה שוב יכולה להוסיף את השיטה: לבדוק כפילויות, להשוות שלבי שחזור, לפעול לפי תבנית הדיווח של הפרויקט ולדווח על שאלות שלא נפתרו. הכלי מספק את הפעולה. המיומנות מסבירה איך להשתמש בו היטב.

גם פלט של כלי דורש שיקול דעת. תגובה בדיווח, מסמך או תוצאת חיפוש יכולים להכיל טעויות או טקסט שנראה כמו הוראה. התייחסו לתוכן שאוחזר כנתונים, ואל תתנו לו לשנות את בקשת המשתמש או את כללי היישום. תמיכה ב־MCP לבדה לא הופכת שרת או את תוכנו למהימנים.

אם קריאה נכשלת, הסוכן יכול לדווח על השגיאה או לנסות חלופה סבירה. אם כתיבה מגיעה לזמן הקצוב, עליו לבדוק אם השינוי התרחש לפני שהוא חוזר עליה. אחרת, ניסיון חוזר עלול ליצור דיווח כפול. פרטי ההתחברות שייכים להגדרות החיבור של האינטגרציה, ולא לפרומפט המשימה. הכללים האלה חשובים עוד יותר כשבוט משתמש בכלים לפי לוח זמנים בזמן שאתם לא שם, כפי שמתואר ב[בוטים שתמיד פועלים](/book/28-persistent-bots).

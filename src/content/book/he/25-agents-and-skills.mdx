## מהם סוכני AI?

- **להתמיד** - לשמור על הקשר וזיכרון לאורך אינטראקציות

הפרומפט היסודי שמגדיר מי הסוכן וכיצד הוא מתנהג:

```markdown
You are a code review assistant. Your role is to:
- Analyze code for bugs, security issues, and performance problems
- Suggest improvements following best practices
- Explain your reasoning clearly
- Be constructive and educational in feedback

You have access to tools for reading files, searching code, and running tests.
```

### פרומפטים לתכנון (איך לחשוב)

הוראות שמנחות את תהליך החשיבה והתכנון של הסוכן:

```markdown
Before taking action, always:
1. Understand the complete request
2. Break it into smaller, verifiable steps
3. Identify which tools you'll need
4. Consider edge cases and potential issues
5. Execute step by step, validating as you go
```

### פרומפטים לשימוש בכלים (איך לפעול)

הנחיה מתי ואיך להשתמש בכלים הזמינים:

```markdown
When you need to understand a codebase:
- Use grep_search for finding specific patterns
- Use read_file to examine file contents
- Use list_dir to explore directory structure
- Always verify your understanding before making changes
```

### פרומפטים להתאוששות (איך להתמודד עם כישלון)

הוראות למקרים שבהם דברים משתבשים:

```markdown
If an action fails:
1. Analyze the error message carefully
2. Consider alternative approaches
3. Ask for clarification if the task is ambiguous
4. Never repeat the same failed action without changes
```

## מהן מיומנויות?

אם פרומפטים הם האטומים, **מיומנויות הן המולקולות**—אבני בניין לשימוש חוזר שנותנות לסוכנים יכולות ספציפיות.

**מיומנות** היא חבילה מקיפה וניידת של הוראות שנותנת לסוכן AI מומחיות בתחום או משימה מסוימים. מיומנויות הן הבלוקים הניתנים לשימוש חוזר של סוכנים: בונים אותן פעם אחת, וכל סוכן יכול להשתמש בהן.

You are an expert code reviewer. When reviewing code:

## Process

2. **Check Correctness** - Does it work? Are there logic errors?
3. **Security Scan** - Reference security-checklist.md for common vulnerabilities

- 🟡 **Suggested** - Recommended improvements
- 🟢 **Nice to have** - Optional enhancements

Always explain *why* something is an issue, not just *what* is wrong.
```

## בניית מיומנויות יעילות

### 1. הגדר את המומחיות בבירור

name: api-design

  including versioning, error handling, and documentation standards
---
```

### 2. מבנה ידע בצורה היררכית

ארגן מידע מהכללי לספציפי:

```markdown
# API Design Skill

## Core Principles
- Resources should be nouns, not verbs
- Use HTTP methods semantically
- Version your APIs from day one

## Detailed Guidelines
[More specific rules...]

## Reference Materials
- See `rest-conventions.md` for naming conventions
- See `error-codes.md` for standard error responses
```

### 3. כלול דוגמאות קונקרטיות

כללים מופשטים הופכים ברורים עם דוגמאות:

```markdown
## Endpoint Naming

✅ Good:
- GET /users/{id}
- POST /orders
- DELETE /products/{id}/reviews/{reviewId}

❌ Avoid:
- GET /getUser
- POST /createNewOrder
- DELETE /removeProductReview
```

### 4. ספק מסגרות לקבלת החלטות

עזור לסוכן לבצע בחירות במצבים עמומים:

```markdown
## When to Use Pagination

Use pagination when:
- Collection could exceed 100 items
- Response size impacts performance
- Client may not need all items

Use full response when:
- Collection is always small (<20 items)
- Client typically needs everything
- Real-time consistency is critical
```

Perplexity מתארת את הלולאה הזו בפירוט עבור **Brain**, מערכת הזיכרון המשפרת את עצמה שעומדת מאחורי הסוכן שלה, Computer ([What is Brain?](https://www.perplexity.ai/help-center/en/articles/19700001-what-is-brain)). ברשומה מנובמבר 2026 ([Self-improving skills](https://www.perplexity.ai/hub/blog/self-improving-skills)) החברה מסבירה כיצד Brain נשען על הזיכרון ועל היסטוריית הסשנים של המשתמש כדי לכתוב ולחדד מיומנויות *אישיות*. בשלב הראיות הוא מאתר סשנים קודמים שבהם נעשה שימוש במיומנות, ובמיוחד כאלה שבהם היא לא עמדה במשימה. ברפלקציה, סוכן שיפור בוחן את הסשנים האלה ומציע שינויים. האימות בודק שההצעה בנויה כראוי ושסביר שתשפר את התוצאות, וההפעלה מיישמת אותה, כך שהסשנים הבאים הופכים לראיות לסבב שאחריו. מה שהופך את הלולאה לאמינה הוא האיפוק שמובנה בה. מיומנות חדשה דורשת שתי הופעות בלתי תלויות של אותה התנהגות שניתן לחזור עליה, ואילו עדכון למיומנות קיימת יכול להישען על מקרה מבוסס אחד. סוכן השיפור אף פעם לא עורך מיומנות ישירות: הוא כותב הצעה עם הנימוקים והראיות שלו, מבצע לכל היותר שינוי אחד לכל מיומנות בכל הרצה, ונמנע מהצעה כשהראיות אינן מצדיקות שינוי. בנוסף, מספר המיומנויות שנוצרות אוטומטית מוגבל לעשר לכל משתמש, כך שמיומנות חדשה נכנסת רק אם ישנה יוצאת, ועם נימוק להחלפה.

**Hermes Agent** של Nous Research ניגש לאותו רעיון מצד הצוות. ככל שאדם מעביר אליו עבודה חוזרת, Hermes הופך גישה שהצליחה למיומנות לשימוש חוזר: הגדרה כתובה, יחד עם קוד שמריץ את הצעדים היציבים באותה דרך בכל פעם ([Nous Research](https://nousresearch.com/press/hermes-enterprise-in-microsoft-teams)). התוסף Collective Wisdom מטפל ברגע שבו מיומנות יוצאת מהמחשב של אדם אחד. Hermes עשוי להציע שמיומנות מסוימת שווה שיתוף, אבל ההחלטה נשארת בידי מי שכתב אותה, והוא בודק בדיוק את הקבצים שיפורסמו בספרייה של הצוות. חברי הצוות מתקינים אחר כך גרסה מסוימת אחת, ולא את מה שהמיומנות במקרה נראית כמו היום ([Collective Wisdom](https://github.com/NousResearch/hermes-collective-wisdom)). הפרק על [בוטים שפועלים תמיד](/book/28-persistent-bots) מראה דרך נוספת שבה Hermes רוכש מיומנות: כשמובילים אותו צעד אחר צעד דרך משימה.

כשמניחים את שתי הדוגמאות זו לצד זו, עולה מהן אותו לקח. מיומנות שכותבת את עצמה מחדש היא עדיין אוסף של הוראות שסוכן ימלא, ולכן היא ראויה לאותה הקפדה כמו מיומנות שנכתבה ביד. דרשו ראיות לפני שינוי, רצוי מיותר מסשן אחד. השאירו נקודת בדיקה אנושית בכל מקום שבו מיומנות עוברת מאדם אחד לאחרים. שמרו גרסאות, כדי שאפשר יהיה לבטל שינוי גרוע במקום להתווכח עליו. ושימו לב לסחיפה: מיומנות שמתעדכנת מספיק פעמים עלולה לנטות לאט לאט אל ההרגלים של אדם אחד או אל סשן גרוע אחד, עד שהיא מתארת מצב רוח חולף יותר מאשר את העבודה עצמה.

גובה הרף תלוי במי שהמיומנות מגיעה אליו. מיומנות אישית, שנלמדה עבור משתמש אחד, יכולה להרשות לעצמה לנוע מהר, כי טעות פוגעת רק באותו משתמש, והוא גם זה שבעמדה הטובה ביותר להבחין בה. מיומנות משותפת או מובנית משפיעה על כל מי שטוען אותה. גם Perplexity מותחת את הקו הזה: שינויים במיומנויות המובנות שכל משתמש מקבל חייבים לעבור מבחני הרצה חוזרת מזווגים (paired replay) וסקירה אנושית פנימית לפני שהם מגיעים לגרסה הרשמית. צוות יכול לאמץ את אותו אינסטינקט: לתת למיומנויות אישיות ללמוד בחופשיות, ולדרוש ממיומנויות משותפות להצדיק כל שינוי.

לא צריך מערכת שמשפרת את עצמה כדי לנסות את הלולאה הזו. אפשר להריץ אותה ידנית, כל עוד מבקשים מהסוכן להציע ולא ליישם:

<TryIt compact prompt={`חזור לסשן שלנו מ\${session:אתמול, כשהכנו את דוח המכירות השבועי}. אני רוצה לשפר את המיומנות \${skill:weekly-report}, אבל אל תשנה אותה עדיין.

1. צטט מילה במילה את הרגעים באותו סשן שבהם המיומנות לא עמדה במשימה או שנאלצתי לתקן אותך.

## שיטות עבודה מומלצות

### לבניית מיומנויות

1. **התחל ספציפי, ואז הכלל** - בנה מיומנות למקרה השימוש המדויק שלך תחילה, ואז הפשט
2. **כלול מקרי כישלון** - תעד מה המיומנות לא יכולה לעשות ואיך להתמודד עם זה
3. **נהל גרסאות של המיומנויות שלך** - עקוב אחר שינויים כדי שסוכנים יוכלו להסתמך על גרסאות יציבות
4. **בדוק עם משימות אמיתיות** - אמת מיומנויות מול עבודה בפועל, לא רק תיאוריה

### לשימוש במיומנויות עם סוכנים

1. **קרא את המיומנות תחילה** - הבן מה מיומנות עושה לפני שפורסים אותה
2. **התאם אישית בתבונה** - דרוס ברירות מחדל של מיומנות רק כאשר הכרחי
3. **עקוב אחר ביצועים** - עקוב אחר כמה טוב מיומנויות מתפקדות בהקשר שלך
4. **תרום שיפורים** - כאשר אתה משפר מיומנות, שקול לשתף בחזרה

از یک عامل می‌خواهید باگ‌های باز پروژه‌تان را پیدا کند و پیش‌نویس یک مورد پیگیری آماده کند. برای این کار، دستورالعمل خوب به‌تنهایی کافی نیست. عامل به راهی نیاز دارد تا به سیستم پیگیری مشکلات شما برسد، دادهٔ درست را بخواند و شاید چیزی هم آنجا ایجاد کند.

اینجاست که **ابزارها**، **اتصال‌دهنده‌ها** و **MCP** وارد می‌شوند. این‌ها به هم مربوط‌اند، اما بخش‌های متفاوتی از تنظیمات را توصیف می‌کنند.

ابزار می‌تواند محلی هم کار کند. ماشین‌حساب به اتصال حساب نیاز ندارد. ابزار خواندن فایل ممکن است کاملاً روی رایانهٔ شما کار کند. سرویس خارجی فقط یکی از منابع ممکن برای ابزارهاست.

## یک ابزار واقعاً چه چیزهایی دارد؟

ابزار معمولاً **نام**، **توضیح**، **طرح‌وارهٔ ورودی** و کدی دارد که کار را انجام می‌دهد. توضیح به مدل کمک می‌کند تصمیم بگیرد چه زمانی از آن استفاده کند. طرح‌واره آرگومان‌های قابل قبول را مشخص می‌کند.

این یک تعریف کوچک برای ابزار فرضی MCP است:

<Collapsible title="تعریف search_issues را بررسی کنید">

```json
{
  "name": "search_issues",
  "description": "موارد پروژهٔ متصل را جست‌وجو کن. این ابزار فقط داده می‌خواند.",
  "inputSchema": {
    "type": "object",
    "properties": {
      "query": { "type": "string" },
      "limit": { "type": "integer", "minimum": 1, "maximum": 20 }
    },
    "required": ["query"],
    "additionalProperties": false
  }
}
```

</Collapsible>

مدل ممکن است `search_issues` را با `{"query": "باگ‌های باز", "limit": 3}` درخواست کند. برنامهٔ پیرامون مدل این درخواست را به کد اجرایی می‌فرستد. کد از سیستم پیگیری پرس‌وجو می‌کند و نتیجه‌ها یا خطا را برمی‌گرداند.

نام و طرح‌واره به‌تنهایی چیزی اجرا نمی‌کنند. کد اجرایی باید ورودی‌ها را اعتبارسنجی کند، دسترسی را بررسی کند و عملیات واقعی را انجام دهد. پاسخ ابزار هم از پاسخ نهایی مدل جداست: پاسخ ممکن است شناسه و عنوان موارد را داشته باشد و مدل آن‌ها را خلاصه کند. [مشخصات ابزارهای MCP](https://modelcontextprotocol.io/specification/latest/server/tools) توضیح می‌دهد ابزارها چگونه این عملیات را ارائه می‌کنند.

<Callout type="info" title="درخواست، نتیجه نیست">
«یک مورد ایجاد می‌کنم» یک جمله است. فراخوانی ابزار، عملیات را درخواست می‌کند. پاسخ موفق همراه شناسهٔ مورد جدید، مدرکی است که نشان می‌دهد این اتفاق افتاده است. این سه را از هم جدا نگه دارید.
</Callout>

## اتصال‌دهنده چه چیزی اضافه می‌کند؟

اتصال‌دهنده یکپارچه‌سازی با سیستمی مشخص را بسته‌بندی می‌کند. ممکن است ورود، انتخاب حساب یا فضای کاری، پیدا کردن داده و ارائهٔ عملیات پشتیبانی‌شده به‌صورت ابزار را مدیریت کند. بعضی اتصال‌دهنده‌ها فقط جست‌وجو یا خواندن انجام می‌دهند. بعضی دیگر نوشتن را هم پشتیبانی می‌کنند.

**اتصال‌دهنده یک اصطلاح محصولی است، نه یک استاندارد فنی جهانی واحد.** یک اتصال‌دهنده ممکن است API سرویس را مستقیم فراخوانی کند. دیگری ممکن است از سرور MCP استفاده کند. سومی ممکن است نمایه‌ای از اسناد همگام‌شده را جست‌وجو کند. بررسی کنید یکپارچه‌سازی مورد نظر دقیقاً چه چیزهایی را پشتیبانی می‌کند. [مرور اتصال‌دهنده‌ها در مستندات Microsoft](https://learn.microsoft.com/en-us/azure/connectors/introduction) نمونه‌ای از یکپارچه‌سازی‌های مبتنی بر API را نشان می‌دهد.

وصل کردن حساب به این معنا نیست که عامل همهٔ فایل‌ها را می‌بیند، تمام داده‌هایتان را وارد زمینه‌اش می‌کند یا اجازهٔ هر عملیاتی دارد. دسترسی به حساب، محدوده‌های مجوز تنظیم‌شده، برنامه و مجوزهای خود سرویس بستگی دارد. نتیجه‌های جست‌وجو هم ممکن است از نمایه‌ای بیایند که از اسناد اصلی قدیمی‌تر است.

برای سیستم پیگیری، این سؤال‌ها را جدا نگه دارید: آیا اتصال تنظیم شده است؟ به کدام پروژه دسترسی دارد؟ فقط می‌تواند بخواند یا می‌تواند مورد جدید هم ایجاد کند؟

## MCP چه چیزی را استاندارد می‌کند؟

**MCP** مخفف **Model Context Protocol**، یعنی پروتکل زمینهٔ مدل است. راهی مشترک برای ارتباط برنامه‌های هوش مصنوعی با ارائه‌دهندگان قابلیت‌های خارجی تعریف می‌کند. جای API سرویس را نمی‌گیرد؛ سرور MCP می‌تواند در پشت صحنه از همان API استفاده کند.

[معماری MCP](https://modelcontextprotocol.io/docs/learn/architecture) سه نقش اصلی دارد:

  { label: "کلاینت", description: "بخشی درون میزبان که اتصال به سرور MCP را نگه می‌دارد.", color: "green" },
  { label: "سرور", description: "برنامه‌ای که ابزارها، منابع یا پرامپت‌ها را از طریق MCP ارائه می‌کند. می‌تواند محلی یا راه‌دور اجرا شود.", color: "amber" }

برای فراخوانی ابزار، کلاینت می‌تواند با `tools/list` ابزارهای سرور را پیدا کند. برنامه تعریف ابزارهای مرتبط را در دسترس مدل می‌گذارد. اگر مدل یکی را درخواست کند، برنامه می‌تواند از طریق کلاینت MCP خود درخواست `tools/call` بفرستد. سرور عملیات را اجرا می‌کند یا به بخش دیگری می‌سپارد و نتیجه را برمی‌گرداند.

مدل لازم نیست خودش اتصال شبکه باز کند. برنامه و پیاده‌سازی MCP ارتباط را مدیریت می‌کنند. سازگاری همچنان مهم است: میزبان و سرور باید قابلیت‌هایی را که می‌خواهید استفاده کنید پشتیبانی کنند. پیدا کردن ابزار تضمین نمی‌کند اجازهٔ اجرای آن را دارید؛ بررسی دسترسی همچنان انجام می‌شود.

### MCP فراتر از ابزارهاست

MCP **منابع** و **پرامپت‌ها** را هم تعریف می‌کند. این واژه‌ها در پروتکل معنی مشخصی دارند:

  { label: "منابع", description: "داده‌هایی که برنامه می‌تواند به‌عنوان زمینه در دسترس بگذارد. مثال: راهنمای پروژه با یک شناسهٔ URI.", color: "green" },

[راهنمای مفاهیم سرور MCP](https://modelcontextprotocol.io/docs/learn/server-concepts) این‌ها را ابزارهای تحت کنترل مدل، منابع تحت کنترل برنامه و پرامپت‌های تحت کنترل کاربر توصیف می‌کند. این‌ها الگوهای تعامل مورد نظر را نشان می‌دهند. بررسی مجوزهای برنامه را حذف نمی‌کنند.

الگوی پرامپت MCP خودبه‌خود مهارت نیست. مهارت می‌تواند روالی طولانی‌تر، منابع مرجع و اسکریپت‌ها را بسته‌بندی کند. ممکن است به عامل بگوید چگونه از ابزارهای ارائه‌شده از طریق MCP، اتصال‌دهندهٔ مستقیم یا توابع محلی استفاده کند.

### مهارت‌ها هم می‌توانند همراه سرور بیایند

تا همین اواخر، این دو بخش معمولاً جدا از هم می‌رسیدند. سرور می‌توانست ابزارهایش را در اختیار عامل بگذارد، اما دانشِ خوب به کار بردن آن‌ها جای دیگری بود: در مهارتی که جداگانه نصب می‌شد، در یک فایل README یا در پرامپت خود کاربر. وقتی سرویس تغییر می‌کرد، این دستورالعمل‌ها ممکن بود بی‌سروصدا عقب بمانند.

**افزونهٔ Skills**، افزونهٔ رسمی MCP که در سپتامبر ۲۰۲۶ به نسخهٔ نهایی رسید، بخش بزرگی از این فاصله را پر می‌کند. اکنون سرور می‌تواند نه فقط ابزارهایش، بلکه مهارت‌هایی را هم ارائه کند که شیوهٔ استفاده از آن‌ها را توضیح می‌دهند؛ مهارت‌هایی که با همان قالب `SKILL.md` نوشته می‌شوند که در فصل [عامل‌ها و مهارت‌ها](/book/25-agents-and-skills) شرح داده شد. ابزارها به عامل می‌گویند چه کاری از دستش برمی‌آید. مهارت‌ها به او می‌گویند چطور کار را خوب انجام دهد. حالا هر دو می‌توانند از یک سرور بیایند؛ بنابراین دستورالعمل‌ها کنار همان سرویسی قرار می‌گیرند که توصیفش می‌کنند و نگه‌دارندگان سرویس می‌توانند آن‌ها را به‌روز نگه دارند.

این سازوکار بر قطعه‌هایی بنا شده که پیش‌تر با آن‌ها آشنا شده‌اید. هر فایلِ یک مهارت به‌صورت یک منبع MCP ارائه می‌شود و معمولاً نشانی URI آن با `skill://` شروع می‌شود. کلاینت می‌تواند مهارت‌های یک سرور را با `skills/list` فهرست کند، یکی را با `skills/get` دریافت کند و فایل‌های پشتیبانش را با `resources/read` بخواند.

همچنان میزبان است که تصمیم می‌گیرد مهارت چگونه به مدل برسد. ممکن است مدل آن را بر اساس نام و توضیحش انتخاب کند، یا کاربر مستقیماً آن را برگزیند. در هر دو حالت، دستورالعمل‌های کامل فقط هنگام نیاز وارد زمینه می‌شوند و خواندن یک فایل `SKILL.md` به‌تنهایی مهارت را فعال نمی‌کند.

<Callout type="warning" title="مهارتی که از سرور می‌آید هم دستورالعمل است">
مهارتی که سرور ارائه می‌کند متنی است که وارد زمینهٔ عامل می‌شود و می‌تواند قدم بعدی او را شکل دهد. پس همان‌قدر دقت می‌طلبد که خود سرور. میزبانِ محتاط پیش از بارگذاری، محتوا را راستی‌آزمایی می‌کند و هر تأییدی را که لازم باشد می‌گیرد. مانند دیگر افزونه‌های رسمی MCP، از جمله MCP Apps و افزونهٔ Tasks که در ادامه می‌آید، افزونهٔ Skills اختیاری است: فقط وقتی به کار می‌رود که هم کلاینت و هم سرور پشتیبانی از آن را اعلام کنند. پشتیبانی کلاینت‌ها هنوز در آغاز راه است؛ پس پیش از تکیه بر آن، بررسی کنید که آیا برنامهٔ شما واقعاً مهارت‌ها را از سرورها بارگذاری می‌کند.
</Callout>

### وقتی ابزار به زمان یا پاسخ نیاز دارد

بیشتر فراخوانی‌های ابزار داد و ستدی کوتاه‌اند: عامل درخواست می‌کند، سرور پاسخ می‌دهد و کار پیش می‌رود. اما برخی کارها با این ریتم جور نیستند. یک پژوهش عمیق، خروجی گرفتن از گزارشی بزرگ یا ساختن (build) یک پروژه ممکن است دقیقه‌ها طول بکشد، و برخی کارها به جایی می‌رسند که فقط کاربر می‌تواند تصمیم بگیرد بعد چه شود. MCP برای این لحظه‌ها دو ایده دارد: **Tasks** برای کاری که زمان می‌خواهد، و **elicitation** (درخواست اطلاعات از کاربر) برای کاری که به یک انسان نیاز دارد.

[افزونهٔ رسمی Tasks](https://tasks.extensions.modelcontextprotocol.io/) (`io.modelcontextprotocol/tasks`) شیوهٔ پایان یافتن یک `tools/call` کُند را تغییر می‌دهد. سرور به‌جای آنکه درخواست را تا پایان کار باز نگه دارد، می‌تواند بی‌درنگ با یک شناسهٔ ماندگار برای کار (task handle) پاسخ دهد؛ چیزی شبیه ژتونی که وقتی پالتویتان را به رخت‌کن می‌سپارید به شما می‌دهند. کلاینت می‌تواند با `tasks/get` وضعیت کار را ببیند، با `tasks/update` به‌روزرسانی یا پاسخ بفرستد، با `tasks/cancel` آن را متوقف کند و وقتی نتیجه آماده شد آن را بگیرد. در این فاصله، عامل آزاد است به کارهای دیگر برسد و بعد برگردد؛ این موضوع به‌ویژه برای [بات‌های همیشه‌فعال](/book/28-persistent-bots) که در نبود شما کار انجام می‌دهند اهمیت دارد. Tasks برای هر دو طرف اختیاری است: کلاینت در هر درخواست پشتیبانی‌اش را اعلام می‌کند و سرور برای هر درخواست جداگانه تصمیم می‌گیرد که کاری بسازد یا نه. ابزارهای موجود این توانایی را خودبه‌خود به دست نمی‌آورند؛ سازندهٔ سرور باید آن را اضافه کند.

[Elicitation](https://modelcontextprotocol.io/specification/latest/client/elicitation) به سرور امکان می‌دهد مکث کند و از کاربر ورودی ساختاریافته بخواهد: «روی staging منتشر شود؟»، «این بازپرداخت تأیید شود؟» یا جزئیاتی جاافتاده که کار بدون آن نمی‌تواند ادامه یابد. میزبان فرمی کوچک نشان می‌دهد و کاربر می‌تواند پاسخ دهد، رد کند یا انصراف دهد. رد کردن هم پاسخی معتبر است و سرور تصمیم می‌گیرد پس از آن چه کند. این دو ایده به‌طور طبیعی به هم می‌رسند: کاری که در جریان است می‌تواند در وضعیت `input_required` متوقف شود و وسط کار از کاربر چیزی بپرسد. پیش از یک عمل نوشتن، چنین پرسشی نقطهٔ بازبینی طبیعی‌ای است که تصمیم را به انسان می‌سپارد، درست همان‌جا که تصمیم اهمیت دارد.

<Callout type="warning" title="فرمی که از سرور می‌آید همچنان درخواستی از سرور است">
درخواست elicitation از سرور می‌آید، نه از برنامهٔ شما؛ پس همان‌قدر دقت می‌طلبد که هر خروجی ابزار. پیش از پاسخ دادن بخوانید چه چیزی از شما خواسته شده، و اگر به سرور اعتماد ندارید هرگز رمز عبور، کلید API یا هر راز دیگری را در چنین فرمی وارد نکنید. پشتیبانی هم از برنامه‌ای به برنامهٔ دیگر فرق می‌کند: VS Code [پشتیبانی از elicitation را مستند کرده است](https://code.visualstudio.com/api/extension-guides/ai/mcp)، Cursor از elicitation پشتیبانی می‌کند، و Claude Code [MCP Tasks و elicitation](https://code.claude.com/docs/en/mcp) را به‌صورت بتای عمومی به برنامهٔ ترمینال خود افزوده است، اما هنوز نه در همهٔ محیط‌هایی که در آن‌ها اجرا می‌شود. [جدول رسمی پشتیبانی کلاینت‌ها](https://modelcontextprotocol.io/extensions/client-matrix) نشان می‌دهد کدام برنامه از کدام افزونه‌ها پشتیبانی می‌کند؛ پس پیش از تکیه بر هر یک از این دو قابلیت، برنامهٔ خودتان را بررسی کنید.
</Callout>

## پرامپت‌نویسی برای عاملی که ابزار دارد

به عامل بگویید دنبال چه اطلاعاتی بگردد، چگونه از آن استفاده کند و چه عملیاتی انتظار دارید. فرض نکنید اتصال وجود دارد یا ابزار تمام عملیات سرویس را پشتیبانی می‌کند.

مهارت قابل استفادهٔ مجدد برای بررسی اولیه می‌تواند روش را اضافه کند: موارد تکراری را بررسی کن، مراحل بازتولید را مقایسه کن، از الگوی ثبت موارد پروژه پیروی کن و سؤال‌های حل‌نشده را گزارش بده. ابزار عملیات را فراهم می‌کند. مهارت توضیح می‌دهد چگونه از آن خوب استفاده شود.

خروجی ابزار همچنان به قضاوت نیاز دارد. نظر یک مورد، سند یا نتیجهٔ جست‌وجو ممکن است اشتباه یا متنی شبیه دستورالعمل داشته باشد. محتوای بازیابی‌شده را داده در نظر بگیرید و اجازه ندهید درخواست کاربر یا قواعد برنامه را تغییر دهد. پشتیبانی MCP به‌تنهایی سرور یا محتوایش را قابل اعتماد نمی‌کند.

اگر خواندن شکست خورد، عامل می‌تواند خطا را گزارش کند یا جایگزین معقولی امتحان کند. اگر نوشتن به پایان مهلت رسید، پیش از تکرار باید بررسی کند آیا تغییر انجام شده است. وگرنه تلاش مجدد ممکن است مورد تکراری ایجاد کند. اطلاعات ورود به تنظیم اتصال یکپارچه‌سازی تعلق دارد، نه پرامپت کار. این قواعد وقتی باتی در نبود شما و طبق زمان‌بندی از ابزارها استفاده می‌کند، اهمیت بیشتری پیدا می‌کنند؛ این موضوع در [بات‌های همیشه‌فعال](/book/28-persistent-bots) توضیح داده شده است.

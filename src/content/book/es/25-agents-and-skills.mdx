## ¿Qué Son los Agentes de IA?

Un **agente de IA** es un sistema de IA que puede planificar, ejecutar e iterar autónomamente sobre tareas. A diferencia de las interacciones simples de prompt-respuesta, los agentes pueden:

- **Planificar** - Descomponer objetivos complejos en pasos accionables
- **Ejecutar** - Usar herramientas y tomar acciones en el mundo real
- **Observar** - Procesar retroalimentación de sus acciones
- **Adaptar** - Ajustar su enfoque basándose en resultados
- **Persistir** - Mantener contexto y memoria entre interacciones

Estos tipos de prompts se apilan juntos para formar el comportamiento completo del agente:

### Prompts de Sistema (La Identidad del Agente)

El prompt fundamental que establece quién es el agente y cómo se comporta:

```markdown
Eres un asistente de revisión de código. Tu rol es:
- Analizar código buscando bugs, problemas de seguridad y de rendimiento
- Sugerir mejoras siguiendo mejores prácticas
- Explicar tu razonamiento claramente
- Ser constructivo y educativo en la retroalimentación

Tienes acceso a herramientas para leer archivos, buscar código y ejecutar pruebas.
```

### Prompts de Planificación (Cómo Pensar)

Instrucciones que guían el proceso de razonamiento y planificación del agente:

```markdown
Antes de tomar acción, siempre:
1. Entiende la solicitud completa
2. Divídela en pasos más pequeños y verificables
3. Identifica qué herramientas necesitarás
4. Considera casos límite y problemas potenciales
5. Ejecuta paso a paso, validando mientras avanzas
```

### Prompts de Uso de Herramientas (Cómo Actuar)

Orientación sobre cuándo y cómo usar las herramientas disponibles:

```markdown
Cuando necesites entender un código base:
- Usa grep_search para encontrar patrones específicos
- Usa read_file para examinar contenidos de archivos
- Usa list_dir para explorar estructura de directorios
- Siempre verifica tu comprensión antes de hacer cambios
```

### Prompts de Recuperación (Cómo Manejar Fallos)

Instrucciones para cuando las cosas salen mal:

```markdown
Si una acción falla:
1. Analiza el mensaje de error cuidadosamente
2. Considera enfoques alternativos
3. Pide clarificación si la tarea es ambigua
4. Nunca repitas la misma acción fallida sin cambios
```

<Callout type="info" title="La Pila de Prompts">
El comportamiento de un agente emerge de capas de prompts trabajando juntos. El prompt de sistema establece la base, los prompts de planificación guían el razonamiento, los prompts de herramientas habilitan la acción, y los prompts de recuperación manejan los fallos. Juntos, crean comportamiento coherente y capaz.
</Callout>

## ¿Qué Son los Skills?

Si los prompts son los átomos, **los skills son las moléculas**—bloques de construcción reutilizables que dan a los agentes capacidades específicas.

Un **skill** es un paquete completo y portátil de instrucciones que da a un agente de IA experiencia en un dominio o tarea específica. Los skills son los bloques reutilizables de los agentes: los construyes una vez, y cualquier agente puede usarlos.

<Callout type="tip" title="Skills = Bloques de Agentes Reutilizables">
Escribe un skill para revisión de código una vez. Ahora cada agente de programación—ya sea para Python, JavaScript o Rust—puede convertirse instantáneamente en un revisor de código experto cargando ese skill. Los skills te permiten construir capacidades de agentes como bloques LEGO.
</Callout>

El archivo `SKILL.md` define el enfoque general:

```markdown
---
name: code-review
description: Revisión de código completa con análisis de seguridad, rendimiento y estilo
---

# Skill de Revisión de Código

Eres un revisor de código experto. Al revisar código:

## Proceso
1. **Entender Contexto** - ¿Qué hace este código? ¿Qué problema resuelve?
2. **Verificar Corrección** - ¿Funciona? ¿Hay errores lógicos?
3. **Escaneo de Seguridad** - Referencia security-checklist.md para vulnerabilidades comunes
4. **Revisión de Rendimiento** - Revisa performance-tips.md para oportunidades de optimización
5. **Estilo y Mantenibilidad** - ¿Es el código legible y mantenible?

## Formato de Salida
Proporciona retroalimentación en categorías:
- 🔴 **Crítico** - Debe corregirse antes de merge
- 🟡 **Sugerido** - Mejoras recomendadas
- 🟢 **Opcional** - Mejoras opcionales

Siempre explica *por qué* algo es un problema, no solo *qué* está mal.
```

## Construyendo Skills Efectivos

### 1. Define la Experiencia Claramente

Comienza con una descripción clara de lo que habilita el skill:

```markdown
---
name: api-design
description: Diseña APIs RESTful siguiendo mejores prácticas de la industria, 
  incluyendo versionado, manejo de errores, y estándares de documentación
---
```

### 2. Estructura el Conocimiento Jerárquicamente

Organiza la información de lo general a lo específico:

```markdown
# Skill de Diseño de API

## Principios Centrales
- Los recursos deben ser sustantivos, no verbos
- Usa métodos HTTP semánticamente
- Versiona tus APIs desde el día uno

## Directrices Detalladas
[Reglas más específicas...]

## Materiales de Referencia
- Ver `rest-conventions.md` para convenciones de nombres
- Ver `error-codes.md` para respuestas de error estándar
```

### 3. Incluye Ejemplos Concretos

Las reglas abstractas se aclaran con ejemplos:

```markdown
## Nombres de Endpoints

✅ Bueno:
- GET /users/{id}
- POST /orders
- DELETE /products/{id}/reviews/{reviewId}

❌ Evitar:
- GET /getUser
- POST /createNewOrder
- DELETE /removeProductReview
```

### 4. Proporciona Marcos de Decisión

Ayuda al agente a tomar decisiones en situaciones ambiguas:

```markdown
## Cuándo Usar Paginación

Usa paginación cuando:
- La colección podría exceder 100 elementos
- El tamaño de respuesta impacta el rendimiento
- El cliente puede no necesitar todos los elementos

Usa respuesta completa cuando:
- La colección siempre es pequeña (<20 elementos)
- El cliente típicamente necesita todo
- La consistencia en tiempo real es crítica
```

### 5. Añade Patrones de Recuperación

Anticipa qué puede salir mal:

```markdown
## Problemas Comunes

**Problema**: El cliente necesita campos que no están en la respuesta estándar
**Solución**: Implementa selección de campos: GET /users?fields=id,name,email

**Problema**: Se necesitan cambios incompatibles
**Solución**: Crea nueva versión, depreca la anterior con línea de tiempo
```

- **Modulares** - Cada skill maneja bien un dominio
- **Compatibles** - Los skills no deben dar instrucciones contradictorias
- **Priorizados** - Cuando los skills se superponen, define cuál tiene precedencia

## Cuando los Skills Aprenden de la Experiencia

Hasta ahora, todos los skills de este capítulo los ha escrito una persona. Alguien nota que una tarea vuelve una y otra vez, se sienta y pone por escrito cómo se hace. Pero un agente que trabaja contigo día tras día también va guardando, en silencio, un registro de cómo fue ese trabajo: qué instrucciones siguió, dónde tuviste que intervenir para corregirlo, qué pasos tuvo que repetir. Un patrón más reciente aprovecha ese registro. En lugar de esperar a que alguien escriba el skill, el propio sistema del agente repasa su experiencia y redacta skills nuevos, o revisa los que ya existen, por su cuenta. Puedes imaginarlo como un ciclo, muy parecido al ciclo del agente del inicio de este capítulo, solo que más lento y vuelto hacia dentro:

Perplexity describe este ciclo en detalle para **Brain**, el sistema de memoria que se mejora a sí mismo y que está detrás de su agente Computer ([What is Brain?](https://www.perplexity.ai/help-center/en/articles/19700001-what-is-brain)). En una publicación de noviembre de 2026 ([Self-improving skills](https://www.perplexity.ai/hub/blog/self-improving-skills)), la empresa explica cómo Brain se apoya en la memoria y el historial de sesiones de un usuario para escribir y pulir skills *personales*. En la etapa de evidencia, busca sesiones pasadas en las que se usó un skill, sobre todo aquellas en las que se quedó corto. En la reflexión, un agente de mejora estudia esas sesiones y propone cambios. La verificación comprueba que la propuesta está bien formada y que probablemente mejorará los resultados, y la activación la aplica, de modo que las sesiones siguientes se convierten en evidencia para la próxima ronda. Lo que hace fiable el ciclo es la prudencia que lleva incorporada. Un skill nuevo exige dos apariciones independientes del mismo comportamiento reutilizable, mientras que para actualizar uno existente puede bastar un único caso bien fundamentado. El agente de mejora nunca edita un skill directamente: redacta una propuesta con su razonamiento y su evidencia, hace como máximo un cambio por skill en cada ejecución y se abstiene cuando la evidencia no justifica un cambio. Además, los skills creados automáticamente tienen un límite de diez por usuario, así que uno nuevo solo entra si se retira uno antiguo, justificando el reemplazo.

**Hermes Agent**, de Nous Research, aborda la misma idea desde el lado de un equipo. A medida que una persona le delega trabajo recurrente, Hermes convierte un enfoque que funcionó en un skill reutilizable: una definición escrita acompañada de código que ejecuta los pasos estables siempre de la misma manera ([Nous Research](https://nousresearch.com/press/hermes-enterprise-in-microsoft-teams)). Su plugin Collective Wisdom se ocupa del momento en que un skill sale del ordenador de una persona. Hermes puede sugerir que vale la pena compartir un skill, pero la decisión sigue siendo de quien lo escribió, que revisa exactamente los archivos que se publicarán en la biblioteca del equipo. Después, los compañeros instalan una versión concreta, no lo que el skill parezca ser ese día ([Collective Wisdom](https://github.com/NousResearch/hermes-collective-wisdom)). El capítulo sobre [bots siempre activos](/book/28-persistent-bots) muestra otra forma en que Hermes adquiere un skill: cuando alguien lo guía paso a paso por una tarea.

Puestos uno junto al otro, los dos ejemplos dejan la misma lección. Un skill que se reescribe a sí mismo sigue siendo un conjunto de instrucciones que un agente va a seguir, así que merece el mismo cuidado que uno escrito a mano. Pide evidencia antes de un cambio, idealmente de más de una sesión. Mantén un punto de revisión humana allí donde un skill pasa de una persona a otras. Conserva las versiones, para que un mal cambio pueda revertirse en lugar de discutirse sin fin. Y vigila la deriva: un skill que se revisa con suficiente frecuencia puede inclinarse poco a poco hacia los hábitos de una sola persona o hacia una sola mala sesión, hasta describir más un estado de ánimo pasajero que el trabajo en sí.

Lo alto que pongas el listón depende de a quién llegue el skill. Un skill personal, aprendido para un solo usuario, puede permitirse avanzar rápido, porque un error solo afecta a ese usuario, que además es quien mejor puede notarlo. Un skill compartido o integrado afecta a todos los que lo cargan. Perplexity también traza esa línea: los cambios en los skills integrados que recibe cada usuario deben superar pruebas de reproducción emparejadas y una revisión humana interna antes de llegar a la versión oficial. Un equipo puede adoptar el mismo instinto: dejar que los skills personales aprendan con libertad y exigir a los compartidos que se ganen cada cambio.

No necesitas un sistema que se mejore a sí mismo para probar este ciclo. Puedes recorrerlo a mano, siempre que le pidas al agente que proponga en lugar de aplicar:

<TryIt compact prompt={`Repasa nuestra sesión de \${session:ayer, cuando preparamos el informe semanal de ventas}. Quiero mejorar el skill \${skill:informe-semanal}, pero no lo cambies todavía.

## Compartiendo y Descubriendo Skills

Los skills son más valiosos cuando se comparten. Plataformas como [prompts.chat](https://prompts.chat/skills) te permiten:

- **Descubrir** skills creados por la comunidad para tareas comunes
- **Descargar** skills directamente a tus proyectos
- **Compartir** tu propia experiencia como skills reutilizables
- **Iterar** en skills basándote en uso del mundo real

Del mismo modo se pueden compartir unidades más grandes que una sola skill: bots completos con sus instrucciones y rutinas, y equipos de bots que se pasan el trabajo entre sí, como en los catálogos [Bots](https://prompts.chat/bots) y [Teams](https://prompts.chat/bots/teams). Veremos ambas ideas en el capítulo sobre [bots siempre activos](/book/28-persistent-bots).

El agente proporciona el marco de ejecución—planificación, uso de herramientas y memoria—mientras los skills proporcionan experiencia de dominio. Esta separación significa:

- **Los skills son portátiles** - El mismo skill funciona con diferentes agentes
- **Los agentes son extensibles** - Añade nuevas capacidades agregando skills
- **La experiencia es compartible** - Expertos de dominio pueden contribuir skills sin construir agentes completos

## Mejores Prácticas

### Para Construir Skills

1. **Empieza específico, luego generaliza** - Construye un skill para tu caso de uso exacto primero, luego abstrae
2. **Incluye casos de fallo** - Documenta lo que el skill no puede hacer y cómo manejarlo
3. **Versiona tus skills** - Rastrea cambios para que los agentes puedan depender de versiones estables
4. **Prueba con tareas reales** - Valida skills contra trabajo real, no solo teoría

### Para Usar Skills con Agentes

1. **Lee el skill primero** - Entiende lo que hace un skill antes de desplegarlo
2. **Personaliza con cuidado** - Sobrescribe valores predeterminados del skill solo cuando sea necesario
3. **Monitorea el rendimiento** - Rastrea qué tan bien funcionan los skills en tu contexto
4. **Contribuye mejoras** - Cuando mejores un skill, considera compartirlo

## Was sind KI-Agents?

Ein **KI-Agent** ist ein KI-System, das autonom Aufgaben planen, ausführen und iterieren kann. Im Gegensatz zu einfachen Prompt-Antwort-Interaktionen können Agents:

- **Planen** - Komplexe Ziele in umsetzbare Schritte aufbrechen
- **Ausführen** - Tools nutzen und Aktionen in der realen Welt durchführen
- **Beobachten** - Feedback von ihren Aktionen verarbeiten
- **Anpassen** - Ihren Ansatz basierend auf Ergebnissen justieren
- **Persistieren** - Kontext und Gedächtnis über Interaktionen hinweg bewahren

Jeder Agent, egal wie anspruchsvoll, ist aus Prompts gebaut. So wie Atome sich zu Molekülen verbinden und Moleküle sich zu komplexen Strukturen verbinden, kombinieren sich Prompts, um intelligentes Agent-Verhalten zu erzeugen.

Diese Prompt-Typen stapeln sich zusammen, um vollständiges Agent-Verhalten zu bilden:

### System Prompts (Die Identität des Agents)

Der grundlegende Prompt, der festlegt, wer der Agent ist und wie er sich verhält:

```markdown
Du bist ein Code-Review-Assistent. Deine Rolle ist es:
- Code auf Bugs, Sicherheitsprobleme und Performance-Probleme zu analysieren
- Verbesserungen nach Best Practices vorzuschlagen
- Deine Begründung klar zu erklären
- Konstruktiv und lehrreich in Feedback zu sein

Du hast Zugriff auf Tools zum Lesen von Dateien, Durchsuchen von Code und Ausführen von Tests.
```

### Planungs-Prompts (Wie denken)

Anweisungen, die den Reasoning- und Planungsprozess des Agents leiten:

```markdown
Bevor du handelst, immer:
1. Verstehe die vollständige Anfrage
2. Zerlege sie in kleinere, verifizierbare Schritte
3. Identifiziere welche Tools du benötigst
4. Berücksichtige Edge Cases und potenzielle Probleme
5. Führe Schritt für Schritt aus und validiere dabei
```

### Tool-Nutzungs-Prompts (Wie handeln)

Anleitung, wann und wie verfügbare Tools zu nutzen sind:

```markdown
Wenn du eine Codebase verstehen musst:
- Nutze grep_search zum Finden spezifischer Muster
- Nutze read_file zum Untersuchen von Dateiinhalten
- Nutze list_dir zum Erkunden der Verzeichnisstruktur
- Verifiziere immer dein Verständnis bevor du Änderungen machst
```

### Recovery-Prompts (Wie mit Fehlern umgehen)

Anweisungen für wenn etwas schiefgeht:

```markdown
Wenn eine Aktion fehlschlägt:
1. Analysiere die Fehlermeldung sorgfältig
2. Erwäge alternative Ansätze
3. Frage nach Klärung wenn die Aufgabe mehrdeutig ist
4. Wiederhole niemals die gleiche fehlgeschlagene Aktion ohne Änderungen
```

<Callout type="info" title="Der Prompt-Stack">
Das Verhalten eines Agents entsteht aus Schichten von Prompts, die zusammenarbeiten. Der System-Prompt legt das Fundament, Planungs-Prompts leiten das Reasoning, Tool-Prompts ermöglichen Aktion und Recovery-Prompts behandeln Fehler. Zusammen erzeugen sie kohärentes, fähiges Verhalten.
</Callout>

## Was sind Skills?

Wenn Prompts die Atome sind, sind **Skills die Moleküle** – wiederverwendbare Bausteine, die Agents spezifische Fähigkeiten verleihen.

Ein **Skill** ist ein umfassendes, portables Paket von Anweisungen, das einem KI-Agent Expertise in einer spezifischen Domäne oder Aufgabe verleiht. Skills sind die wiederverwendbaren Blöcke von Agents: du baust sie einmal, und jeder Agent kann sie nutzen.

<Callout type="tip" title="Skills = Wiederverwendbare Agent-Blöcke">
Schreibe einmal einen Skill für Code-Review. Jetzt kann jeder Coding-Agent – ob für Python, JavaScript oder Rust – sofort ein Experten-Code-Reviewer werden, indem er diesen Skill lädt. Skills lassen dich Agent-Fähigkeiten wie LEGO-Blöcke bauen.
</Callout>

```markdown
name: code-review

# Code-Review-Skill

Du bist ein Experten-Code-Reviewer. Beim Review von Code:

## Prozess
1. **Kontext verstehen** - Was macht dieser Code? Welches Problem löst er?
2. **Korrektheit prüfen** - Funktioniert es? Gibt es Logikfehler?

- 🟢 **Nice to have** - Optionale Verbesserungen

```

## Effektive Skills bauen

### 1. Die Expertise klar definieren

Beginne mit einer klaren Beschreibung, was der Skill ermöglicht:

```markdown
---
name: api-design
description: RESTful APIs nach Branchen-Best-Practices designen, 
  einschließlich Versionierung, Fehlerbehandlung und Dokumentationsstandards
---
```

### 2. Wissen hierarchisch strukturieren

Organisiere Informationen von allgemein zu spezifisch:

```markdown
# API-Design-Skill

## Kernprinzipien
- Ressourcen sollten Nomen sein, nicht Verben
- HTTP-Methoden semantisch nutzen
- APIs von Tag eins an versionieren

## Detaillierte Richtlinien
[Spezifischere Regeln...]

## Referenzmaterialien
- Siehe `rest-conventions.md` für Namenskonventionen
- Siehe `error-codes.md` für Standard-Fehlerantworten
```

### 3. Konkrete Beispiele einschließen

Abstrakte Regeln werden mit Beispielen klar:

```markdown
## Endpoint-Benennung

✅ Gut:
- GET /users/{id}
- POST /orders
- DELETE /products/{id}/reviews/{reviewId}

❌ Vermeiden:
- GET /getUser
- POST /createNewOrder
- DELETE /removeProductReview
```

### 4. Entscheidungs-Frameworks liefern

Hilf dem Agent, in mehrdeutigen Situationen Entscheidungen zu treffen:

```markdown
## Wann Paginierung nutzen

Paginierung nutzen wenn:
- Sammlung könnte 100 Items überschreiten
- Antwortgröße Performance beeinflusst
- Client braucht vielleicht nicht alle Items

Volle Antwort nutzen wenn:
- Sammlung ist immer klein (<20 Items)
- Client braucht typischerweise alles
- Echtzeit-Konsistenz ist kritisch
```

### 5. Recovery-Muster hinzufügen

Antizipiere was schiefgehen kann:

```markdown
## Häufige Probleme

**Problem**: Client braucht Felder, die nicht in Standard-Antwort sind
**Lösung**: Feld-Auswahl implementieren: GET /users?fields=id,name,email

**Problem**: Breaking Changes nötig
**Lösung**: Neue Version erstellen, alte mit Zeitplan deprecaten
```

- **Modular** - Jeder Skill behandelt eine Domäne gut
- **Kompatibel** - Skills sollten keine widersprüchlichen Anweisungen geben
- **Priorisiert** - Wenn Skills sich überlappen, definiere welcher Vorrang hat

## Wenn Skills aus Erfahrung lernen

Bisher wurde jeder Skill in diesem Kapitel von einem Menschen geschrieben. Jemand merkt, dass eine Aufgabe immer wiederkehrt, setzt sich hin und fasst das nötige Wissen in Worte. Ein Agent, der Tag für Tag mit dir arbeitet, führt aber nebenbei auch Buch darüber, wie diese Arbeit gelaufen ist: welchen Anweisungen er gefolgt ist, wo du eingreifen und ihn korrigieren musstest, welche Schritte er doppelt machen musste. Ein neueres Muster macht sich diese Aufzeichnungen zunutze. Statt darauf zu warten, dass jemand den Skill schreibt, blickt das System des Agents selbst auf seine Erfahrung zurück und entwirft eigenständig neue Skills oder überarbeitet bestehende. Man kann sich das als Schleife vorstellen, ganz ähnlich der Agent-Schleife vom Anfang dieses Kapitels, nur langsamer und nach innen gewandt:

Perplexity beschreibt diese Schleife ausführlich für **Brain**, das sich selbst verbessernde Gedächtnissystem hinter seinem Agenten Computer ([What is Brain?](https://www.perplexity.ai/help-center/en/articles/19700001-what-is-brain)). In einem Beitrag vom November 2026 ([Self-improving skills](https://www.perplexity.ai/hub/blog/self-improving-skills)) erklärt das Unternehmen, wie Brain auf das Gedächtnis und den Sitzungsverlauf eines Nutzers zurückgreift, um *persönliche* Skills zu schreiben und zu verfeinern. In der Belegphase sucht es frühere Sitzungen, in denen ein Skill verwendet wurde, vor allem solche, in denen er nicht ausreichte. In der Reflexion untersucht ein Verbesserungs-Agent diese Sitzungen und schlägt Änderungen vor. Die Prüfung stellt sicher, dass der Vorschlag formal korrekt ist und die Ergebnisse voraussichtlich verbessert, und die Aktivierung übernimmt ihn, sodass die folgenden Sitzungen zu Belegen für die nächste Runde werden. Vertrauenswürdig wird die Schleife durch die Zurückhaltung, die in ihr steckt. Ein neuer Skill erfordert zwei voneinander unabhängige Vorkommen desselben wiederverwendbaren Verhaltens, während für die Aktualisierung eines bestehenden Skills ein einziges, gut belegtes Vorkommen genügen kann. Der Verbesserungs-Agent ändert einen Skill nie direkt: Er schreibt einen Vorschlag mit Begründung und Belegen, nimmt pro Lauf höchstens eine Änderung je Skill vor und verzichtet ganz darauf, wenn die Belege keine Änderung tragen. Außerdem sind automatisch erstellte Skills auf zehn pro Nutzer begrenzt. Ein neuer kommt also nur hinzu, wenn ein alter ausscheidet, und dieser Tausch muss begründet werden.

**Hermes Agent** von Nous Research nähert sich derselben Idee aus der Sicht eines Teams. Wenn ein Mensch ihm wiederkehrende Arbeit überträgt, macht Hermes aus einem erfolgreichen Vorgehen einen wiederverwendbaren Skill: eine schriftliche Beschreibung, kombiniert mit Code, der die stabilen Schritte jedes Mal gleich ausführt ([Nous Research](https://nousresearch.com/press/hermes-enterprise-in-microsoft-teams)). Das Plugin Collective Wisdom kümmert sich um den Moment, in dem ein Skill den Rechner einer einzelnen Person verlässt. Hermes kann vorschlagen, dass sich das Teilen eines Skills lohnt, doch die Entscheidung bleibt bei der Person, die ihn verfasst hat. Sie prüft genau die Dateien, die in der Bibliothek des Teams veröffentlicht werden. Teammitglieder installieren anschließend eine bestimmte Version und nicht das, wonach der Skill heute zufällig aussieht ([Collective Wisdom](https://github.com/NousResearch/hermes-collective-wisdom)). Das Kapitel über [Always-On Bots](/book/28-persistent-bots) zeigt einen weiteren Weg, wie Hermes einen Skill lernt: indem man ihn Schritt für Schritt durch eine Aufgabe führt.

Nebeneinander gestellt, lehren beide Beispiele dasselbe. Ein Skill, der sich selbst umschreibt, besteht immer noch aus Anweisungen, denen ein Agent folgen wird, und verdient daher dieselbe Sorgfalt wie ein von Hand geschriebener. Verlange Belege, bevor sich etwas ändert, am besten aus mehr als einer Sitzung. Sieh überall dort eine menschliche Prüfung vor, wo ein Skill von einer Person an andere weitergegeben wird. Bewahre Versionen auf, damit sich eine schlechte Änderung zurücknehmen lässt, statt über sie streiten zu müssen. Und achte auf schleichende Verschiebungen: Ein Skill, der oft genug überarbeitet wird, kann sich langsam an die Gewohnheiten einer einzelnen Person oder an eine einzige missglückte Sitzung anpassen, bis er eher eine vorübergehende Laune beschreibt als die Arbeit selbst.

Wie hoch die Messlatte liegen sollte, hängt davon ab, wen der Skill erreicht. Ein persönlicher Skill, für einen einzigen Nutzer gelernt, darf sich schnell bewegen, denn ein Fehler trifft nur diesen Nutzer, und der ist am besten in der Lage, ihn zu bemerken. Ein geteilter oder eingebauter Skill betrifft dagegen alle, die ihn laden. Auch Perplexity zieht diese Linie: Änderungen an den eingebauten Skills, die jeder Nutzer erhält, müssen gepaarte Replay-Tests und eine interne menschliche Prüfung bestehen, bevor sie in die maßgebliche Version gelangen. Ein Team kann denselben Instinkt übernehmen: persönliche Skills frei lernen lassen und von geteilten verlangen, sich jede Änderung zu verdienen.

Um diese Schleife auszuprobieren, brauchst du kein sich selbst verbesserndes System. Du kannst sie auch von Hand durchlaufen, solange du den Agenten bittest, Änderungen vorzuschlagen statt sie umzusetzen:

1. Zitiere genau die Stellen in dieser Sitzung, an denen der Skill nicht ausreichte oder ich dich korrigieren musste.

## Skills teilen und entdecken

Skills sind am wertvollsten, wenn sie geteilt werden. Plattformen wie [prompts.chat](https://prompts.chat/skills) erlauben dir:

- **Entdecken** - Community-erstellte Skills für häufige Aufgaben
- **Herunterladen** - Skills direkt in deine Projekte
- **Teilen** - Deine eigene Expertise als wiederverwendbare Skills
- **Iterieren** - Skills basierend auf realem Einsatz

Auf dieselbe Weise lassen sich auch größere Einheiten als ein einzelner Skill teilen: ganze Bots mit ihren Anweisungen und Routinen und Teams von Bots, die sich gegenseitig Arbeit übergeben, wie in den Katalogen [Bots](https://prompts.chat/bots) und [Teams](https://prompts.chat/bots/teams). Beide Ideen betrachten wir im Kapitel über [ständig aktive Bots](/book/28-persistent-bots).

<Callout type="tip" title="Mit Community-Skills beginnen">
Bevor du einen Skill von Grund auf baust, prüfe ob jemand dein Problem bereits gelöst hat. Community-Skills sind kampferprobt und oft besser als bei Null zu starten.
</Callout>

Der Agent liefert das Ausführungs-Framework – Planung, Tool-Nutzung und Gedächtnis – während Skills Domänen-Expertise liefern. Diese Trennung bedeutet:

- **Skills sind portabel** - Der gleiche Skill funktioniert mit verschiedenen Agents
- **Agents sind erweiterbar** - Füge neue Fähigkeiten hinzu, indem du Skills hinzufügst
- **Expertise ist teilbar** - Domänen-Experten können Skills beitragen ohne volle Agents zu bauen

## Best Practices

### Für das Bauen von Skills

1. **Spezifisch beginnen, dann generalisieren** - Baue zuerst einen Skill für deinen exakten Anwendungsfall, dann abstrahiere
2. **Fehlerfälle einschließen** - Dokumentiere was der Skill nicht kann und wie damit umzugehen ist
3. **Skills versionieren** - Verfolge Änderungen, damit Agents auf stabile Versionen vertrauen können
4. **Mit echten Aufgaben testen** - Validiere Skills gegen tatsächliche Arbeit, nicht nur Theorie

### Für die Nutzung von Skills mit Agents

1. **Den Skill zuerst lesen** - Verstehe was ein Skill macht bevor du ihn einsetzt
2. **Durchdacht anpassen** - Überschreibe Skill-Defaults nur wenn nötig
3. **Performance überwachen** - Verfolge wie gut Skills in deinem Kontext performen
4. **Verbesserungen beitragen** - Wenn du einen Skill verbesserst, erwäge zurückzuteilen

Die Prompt Engineers von morgen werden nicht nur Prompts schreiben – sie werden Skill-Ökosysteme architektieren, die KI-Agents wirklich zu Experten in spezifischen Domänen machen.

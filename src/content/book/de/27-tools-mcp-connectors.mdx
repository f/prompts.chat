Du bittest einen Agent, die offenen Bugs in deinem Projekt zu finden und ein Folge-Issue zu entwerfen. Dafür braucht er mehr als gute Anweisungen. Er muss dein Ticketsystem erreichen, die richtigen Daten lesen und dort vielleicht etwas erstellen können.

Hier kommen **Werkzeuge**, **Konnektoren** und **MCP** ins Spiel. Sie hängen zusammen, beschreiben aber verschiedene Teile des Systems.

Ein Werkzeug kann auch lokal arbeiten. Ein Taschenrechner braucht keine Kontoverbindung. Ein Werkzeug zum Lesen von Dateien kann vollständig auf deinem Computer laufen. Ein externer Dienst ist nur eine mögliche Quelle für Werkzeuge.

## Was ein Werkzeug tatsächlich enthält

Ein Werkzeug hat meistens einen **Namen**, eine **Beschreibung**, ein **Eingabeschema** und eine Implementierung, die die Arbeit ausführt. Die Beschreibung hilft dem Modell zu entscheiden, wann es das Werkzeug nutzen soll. Das Schema beschreibt die erlaubten Argumente.

Hier ist eine kleine, erfundene MCP-Werkzeugdefinition:

<Collapsible title="Die Definition von search_issues ansehen">

```json
{
  "name": "search_issues",
  "description": "Suche Issues im verbundenen Projekt. Dieses Werkzeug liest nur Daten.",
  "inputSchema": {
    "type": "object",
    "properties": {
      "query": { "type": "string" },
      "limit": { "type": "integer", "minimum": 1, "maximum": 20 }
    },
    "required": ["query"],
    "additionalProperties": false
  }
}
```

</Collapsible>

Das Modell könnte `search_issues` mit `{"query": "offene Bugs", "limit": 3}` anfordern. Die umgebende Anwendung leitet diese Anfrage an die Implementierung weiter. Diese fragt das Ticketsystem ab und gibt Ergebnisse oder einen Fehler zurück.

Name und Schema führen selbst nichts aus. Die Implementierung muss Eingaben validieren, den Zugriff prüfen und den tatsächlichen Vorgang ausführen. Die Werkzeugantwort ist außerdem von der abschließenden Antwort des Modells getrennt: Sie kann Issue-IDs und Titel enthalten, die das Modell anschließend zusammenfasst. Die [MCP-Werkzeugspezifikation](https://modelcontextprotocol.io/specification/latest/server/tools) beschreibt, wie Werkzeuge diese Vorgänge bereitstellen.

<Callout type="info" title="Eine Anfrage ist kein Ergebnis">
„Ich werde ein Issue erstellen“ ist eine Aussage. Ein Werkzeugaufruf fordert den Vorgang an. Eine erfolgreiche Antwort mit der ID des neuen Issues belegt, dass er stattgefunden hat. Halte diese drei Dinge auseinander.
</Callout>

## Was ein Konnektor ergänzt

Ein Konnektor bündelt die Integration mit einem bestimmten System. Er kann Anmeldung, Konto- oder Arbeitsbereichsauswahl, Datensuche und die Bereitstellung unterstützter Aktionen als Werkzeuge übernehmen. Einige Konnektoren können nur suchen oder lesen. Andere unterstützen auch Schreibzugriffe.

**Konnektor ist ein Produktbegriff, kein einheitlicher technischer Standard.** Ein Konnektor ruft vielleicht direkt die API eines Dienstes auf. Ein anderer nutzt einen MCP-Server. Ein dritter durchsucht einen Index aus synchronisierten Dokumenten. Prüfe, was die jeweilige Integration unterstützt. Microsofts [Übersicht zu Konnektoren](https://learn.microsoft.com/en-us/azure/connectors/introduction) zeigt ein Beispiel für Integrationen auf Basis von APIs.

Ein verbundenes Konto bedeutet nicht, dass der Agent jede Datei sieht, alle deine Daten in seinen Kontext lädt oder jede Aktion ausführen darf. Der Zugriff hängt vom Konto, den konfigurierten Berechtigungsbereichen, der Anwendung und den Berechtigungen des Dienstes ab. Suchergebnisse können außerdem aus einem Index stammen, der älter als die Originaldokumente ist.

Halte beim Ticketsystem diese Fragen auseinander: Ist eine Verbindung eingerichtet? Auf welches Projekt kann sie zugreifen? Kann sie nur lesen oder auch Issues erstellen?

## Was MCP standardisiert

**MCP** steht für **Model Context Protocol**. Es definiert einen gemeinsamen Kommunikationsweg für KI-Anwendungen und externe Funktionsanbieter. Es ersetzt nicht die API eines Dienstes; ein MCP-Server kann diese API im Hintergrund nutzen.

Die [MCP-Architektur](https://modelcontextprotocol.io/docs/learn/architecture) hat drei zentrale Rollen:

<InfoGrid columns={3} items={[
  { label: "Host", description: "Die KI-Anwendung, in der der Nutzer arbeitet. Sie koordiniert Verbindungen, Modellinteraktionen und Berechtigungen.", color: "blue" },
  { label: "Client", description: "Der Teil im Host, der eine Verbindung zu einem MCP-Server aufrechterhält.", color: "green" },
  { label: "Server", description: "Ein Programm, das Werkzeuge, Ressourcen oder Prompts über MCP bereitstellt. Es kann lokal oder entfernt laufen.", color: "amber" }
]} />

Für einen Werkzeugaufruf kann der Client die Werkzeuge des Servers mit `tools/list` abfragen. Die Anwendung stellt dem Modell relevante Werkzeugdefinitionen bereit. Wenn das Modell eines davon anfordert, kann die Anwendung über ihren MCP-Client eine `tools/call`-Anfrage senden. Der Server führt den Vorgang aus oder delegiert ihn und gibt das Ergebnis zurück.

Das Modell muss nicht selbst eine Netzwerkverbindung öffnen. Die Anwendung und die MCP-Implementierung übernehmen die Kommunikation. Kompatibilität bleibt wichtig: Host und Server müssen die Funktionen unterstützen, die du nutzen möchtest. Ein gefundenes Werkzeug bedeutet nicht automatisch, dass du es ausführen darfst; Zugriffsprüfungen gelten weiterhin.

### MCP bietet mehr als Werkzeuge

MCP definiert auch **Ressourcen** und **Prompts**. Diese Wörter haben im Protokoll bestimmte Bedeutungen:

<InfoGrid columns={3} items={[
  { label: "Werkzeuge", description: "Vorgänge, die das Modell unter den Kontrollen der Anwendung anfordern kann. Beispiel: Issues suchen.", color: "blue" },
  { label: "Ressourcen", description: "Daten, die die Anwendung als Kontext bereitstellen kann. Beispiel: ein Projektleitfaden mit einer URI.", color: "green" },
  { label: "Prompts", description: "Wiederverwendbare Nachrichtenvorlagen, die Nutzer auswählen können, mit optionalen Argumenten. Beispiel: einen Bericht zur Issue-Sichtung vorbereiten.", color: "amber" }
]} />

Der [Leitfaden zu MCP-Serverkonzepten](https://modelcontextprotocol.io/docs/learn/server-concepts) beschreibt sie als modellgesteuerte Werkzeuge, anwendungsgesteuerte Ressourcen und nutzergesteuerte Prompts. Diese Begriffe beschreiben die vorgesehenen Interaktionsmuster. Sie heben die Berechtigungsprüfungen der Anwendung nicht auf.

Eine MCP-Promptvorlage ist nicht automatisch ein Skill. Ein Skill kann einen längeren Ablauf, Referenzen und Skripte bündeln. Er kann dem Agent erklären, wie er Werkzeuge über MCP, einen direkten Konnektor oder lokale Funktionen nutzt.

### Skills können mit dem Server mitkommen

Bis vor Kurzem kamen diese beiden Teile meist getrennt an. Ein Server konnte einem Agent seine Werkzeuge geben, doch das Wissen, wie man sie gut einsetzt, lag woanders: in einem separat installierten Skill, in einer README oder im Prompt des Nutzers. Änderte sich der Dienst, konnten diese Anweisungen unbemerkt veralten.

Die offizielle **Skills-Erweiterung** von MCP, seit September 2026 final, schließt einen großen Teil dieser Lücke. Ein Server kann jetzt nicht nur seine Werkzeuge anbieten, sondern auch die Skills, die erklären, wie man sie nutzt. Sie sind im selben `SKILL.md`-Format geschrieben, das in [Agenten & Skills](/book/25-agents-and-skills) beschrieben wird. Werkzeuge sagen einem Agent, was er tun kann. Skills sagen ihm, wie er die Aufgabe gut erledigt. Nun können beide vom selben Server kommen. So stehen die Anweisungen direkt neben dem Dienst, den sie beschreiben, und die Menschen, die ihn pflegen, können sie aktuell halten.

Der Mechanismus baut auf Bausteinen auf, die du schon kennst. Jede Datei eines Skills wird als MCP-Ressource bereitgestellt, üblicherweise mit einer `skill://`-URI. Ein Client kann die Skills eines Servers mit `skills/list` auflisten, einen davon mit `skills/get` abrufen und die zugehörigen Dateien mit `resources/read` lesen.

<Compare
  before={{ label: "Ein Server nur mit Werkzeugen", content: "Der Tracker-Server stellt search_issues und create_issue bereit. Die Methode für die Sichtung (Duplikate prüfen, der Issue-Vorlage folgen) muss aus einem separat installierten Skill oder aus deinem Prompt kommen und kann veralten, wenn sich der Dienst ändert." }}
  after={{ label: "Ein Server, der auch einen Skill mitliefert", content: "Derselbe Server bietet auch einen Skill zur Issue-Sichtung an. Der Host sieht zunächst nur dessen Namen und Beschreibung und lädt die vollständigen Anweisungen erst, wenn eine Aufgabe sie braucht. Ändern die Betreuer den Dienst, können sie den Skill gleich mit aktualisieren." }}
/>

Wie ein Skill zum Modell gelangt, entscheidet weiterhin der Host. Das Modell kann ihn anhand von Name und Beschreibung auswählen, oder der Nutzer wählt ihn direkt. In beiden Fällen gelangen die vollständigen Anweisungen erst in den Kontext, wenn sie gebraucht werden, und das bloße Lesen einer `SKILL.md`-Datei aktiviert den Skill nicht.

<Callout type="warning" title="Ein Skill vom Server bleibt eine Anweisung">
Ein Skill von einem Server ist Text, der in den Kontext des Agents gelangt und beeinflussen kann, was der Agent als Nächstes tut. Er verdient deshalb dieselbe Prüfung wie der Server selbst. Ein sorgfältiger Host prüft den Inhalt und holt jede erforderliche Zustimmung ein, bevor er ihn lädt. Wie andere offizielle MCP-Erweiterungen, etwa MCP Apps und die gleich beschriebene Tasks-Erweiterung, ist Skills optional: Die Erweiterung wird nur genutzt, wenn Client und Server beide ihre Unterstützung erklären. Die Unterstützung in Clients steht noch am Anfang. Prüfe daher, ob deine Anwendung Skills tatsächlich von Servern lädt, bevor du dich darauf verlässt.
</Callout>

### Wenn ein Werkzeug Zeit oder eine Antwort braucht

Die meisten Werkzeugaufrufe sind kurze Wortwechsel: Der Agent fragt, der Server antwortet, und die Arbeit geht weiter. Manche Aufgaben passen nicht in diesen Takt. Eine gründliche Recherche, ein großer Berichtsexport oder ein Build kann viele Minuten dauern, und manche Arbeiten erreichen einen Punkt, an dem nur der Nutzer entscheiden kann, wie es weitergeht. MCP bietet für solche Momente zwei Ideen: **Tasks** für Arbeit, die Zeit braucht, und **Elicitation** für Arbeit, die einen Menschen braucht.

Die offizielle [Tasks-Erweiterung](https://tasks.extensions.modelcontextprotocol.io/) (`io.modelcontextprotocol/tasks`) verändert, wie ein langsamer `tools/call` endet. Statt die Anfrage offenzuhalten, bis die Arbeit erledigt ist, kann der Server sofort mit einem dauerhaften Task-Handle antworten, ein bisschen wie die Marke, die du an der Garderobe bekommst. Der Client kann mit `tasks/get` nach dem Stand sehen, mit `tasks/update` Aktualisierungen oder Antworten schicken, mit `tasks/cancel` den Task abbrechen und das Ergebnis abholen, sobald es fertig ist. In der Zwischenzeit kann der Agent weiterarbeiten und später zurückkommen. Das zählt besonders bei [Always-On-Bots](/book/28-persistent-bots), die Aufgaben erledigen, während du nicht da bist. Tasks sind auf beiden Seiten optional: Der Client erklärt seine Unterstützung bei jeder Anfrage, und der Server entscheidet von Anfrage zu Anfrage, ob er einen Task anlegt. Bestehende Werkzeuge bekommen diese Fähigkeit nicht von selbst; wer den Server entwickelt, muss sie einbauen.

<Compare
  before={{ label: "Ein blockierender Werkzeugaufruf", content: "Der Agent ruft export_report auf und wartet. Die Anfrage bleibt minutenlang offen. Bricht die Verbindung ab, weiß niemand, ob der Export fertig wurde, und bis zur Antwort kann der Agent nichts anderes tun." }}
  after={{ label: "Ein Task-Handle", content: "Der Agent ruft export_report auf und bekommt sofort ein Task-Handle zurück. Er wendet sich anderer Arbeit zu, prüft den Task mit tasks/get und holt den fertigen Bericht ab, sobald er bereit ist. Ändern sich die Pläne, stoppt tasks/cancel den Task." }}
/>

Mit [Elicitation](https://modelcontextprotocol.io/specification/latest/client/elicitation) kann ein Server innehalten und den Nutzer um strukturierte Angaben bitten: „Auf Staging deployen?“, „Diese Rückerstattung bestätigen?“ oder ein fehlendes Detail, ohne das die Arbeit nicht weitergeht. Der Host zeigt ein kleines Formular, und der Nutzer kann antworten, ablehnen oder abbrechen. Auch eine Ablehnung ist eine gültige Antwort; was dann geschieht, entscheidet der Server. Beide Ideen greifen ganz natürlich ineinander: Ein laufender Task kann im Zustand `input_required` pausieren und mitten in der Arbeit beim Nutzer nachfragen. Vor einem Schreibzugriff ist eine solche Frage ein natürlicher Kontrollpunkt, an dem ein Mensch mitentscheidet, und zwar genau dort, wo es darauf ankommt.

<Callout type="warning" title="Ein Formular vom Server ist immer noch eine Anfrage vom Server">
Eine Elicitation kommt vom Server, nicht von deiner Anwendung, und verdient deshalb dieselbe Prüfung wie jede Werkzeugausgabe. Lies, worum gebeten wird, bevor du antwortest, und gib niemals ein Passwort, einen API-Schlüssel oder ein anderes Geheimnis in ein solches Formular ein, wenn du dem Server nicht vertraust. Auch die Unterstützung unterscheidet sich je nach Anwendung: VS Code [dokumentiert die Unterstützung für Elicitation](https://code.visualstudio.com/api/extension-guides/ai/mcp), Cursor unterstützt Elicitation, und Claude Code hat [MCP Tasks und Elicitations](https://code.claude.com/docs/en/mcp) als öffentliche Beta in seiner Terminal-App eingeführt, allerdings noch nicht überall, wo es läuft. Die offizielle [Übersicht zur Client-Unterstützung](https://modelcontextprotocol.io/extensions/client-matrix) zeigt, welche Anwendungen welche Erweiterungen unterstützen. Prüfe also deine, bevor du dich auf eine der beiden Funktionen verlässt.
</Callout>

## Prompts für einen Agent mit Werkzeugen

Sage dem Agent, welche Informationen er suchen soll, wie er sie nutzen soll und welche Aktionen du erwartest. Gehe nicht einfach davon aus, dass eine Verbindung besteht oder ein Werkzeug jeden Vorgang des Dienstes unterstützt.

<Compare
  before={{ label: "Zu viel bleibt offen", content: "Schau dir die Bugs an und bring alles in Ordnung." }}
  after={{ label: "Klares Ergebnis und klare Grenzen", content: "Suche im verbundenen Projekt nach offenen Bugs zu leeren Suchergebnissen. Fasse die relevanten Issues mit ihren IDs zusammen. Entwirf bei Bedarf ein Folge-Issue, frage aber vor dem Erstellen nach. Falls die Verbindung oder das benötigte Werkzeug nicht verfügbar ist, erkläre, was fehlt. Behaupte nicht, ein Issue erstellt zu haben, solange kein erfolgreiches Werkzeugergebnis vorliegt." }}
/>

Ein wiederverwendbarer Skill zur Issue-Sichtung könnte die Methode ergänzen: Duplikate suchen, Reproduktionsschritte vergleichen, die Issue-Vorlage des Projekts befolgen und offene Fragen melden. Das Werkzeug stellt den Vorgang bereit. Der Skill erklärt, wie man ihn sinnvoll nutzt.

Werkzeugausgaben müssen weiterhin beurteilt werden. Ein Issue-Kommentar, ein Dokument oder ein Suchergebnis kann Fehler oder Text enthalten, der wie eine Anweisung aussieht. Behandle abgerufene Inhalte als Daten, statt ihnen zu erlauben, die Nutzeranfrage oder die Anwendungsregeln zu verändern. MCP-Unterstützung allein macht einen Server oder seine Inhalte nicht vertrauenswürdig.

Wenn ein Lesevorgang fehlschlägt, kann der Agent den Fehler melden oder eine sinnvolle Alternative versuchen. Läuft ein Schreibvorgang in ein Zeitlimit, sollte er vor einer Wiederholung prüfen, ob die Änderung stattgefunden hat. Sonst könnte ein erneuter Versuch ein doppeltes Issue erstellen. Zugangsdaten gehören in die Verbindungseinstellungen der Integration, nicht in den Aufgaben-Prompt. Diese Regeln sind noch wichtiger, wenn ein Bot Werkzeuge nach Zeitplan nutzt, während du nicht da bist, wie in [Always-On-Bots](/book/28-persistent-bots) beschrieben.

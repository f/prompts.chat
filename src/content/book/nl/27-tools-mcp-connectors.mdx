Je vraagt een agent om de openstaande bugs in je project te vinden en een vervolgissue op te stellen. Daarvoor zijn goede instructies alleen niet genoeg. De agent moet je issuetracker kunnen bereiken, de juiste gegevens kunnen lezen en er misschien iets kunnen aanmaken.

Hier komen **tools**, **connectors** en **MCP** in beeld. Ze hangen samen, maar beschrijven verschillende delen van de opstelling.

## Wat een tool eigenlijk bevat

Een tool heeft meestal een **naam**, een **beschrijving**, een **invoerschema** en een implementatie die het werk uitvoert. De beschrijving helpt het model te bepalen wanneer het de tool moet gebruiken. Het schema beschrijft de argumenten die de tool accepteert.

Hier is een kleine definitie van een fictieve MCP-tool:

<Collapsible title="Bekijk de definitie van search_issues">

```json
{
  "name": "search_issues",
  "description": "Zoek issues in het verbonden project. Deze tool leest alleen gegevens.",
  "inputSchema": {
    "type": "object",
    "properties": {
      "query": { "type": "string" },
      "limit": { "type": "integer", "minimum": 1, "maximum": 20 }
    },
    "required": ["query"],
    "additionalProperties": false
  }
}
```

</Collapsible>

Het model kan `search_issues` aanvragen met `{"query": "openstaande bugs", "limit": 3}`. De toepassing stuurt dat verzoek naar de implementatie. Die bevraagt de tracker en geeft resultaten of een fout terug.

De naam en het schema voeren zelf niets uit. De implementatie moet de invoer valideren, de toegang controleren en de bewerking uitvoeren. Het antwoord van een tool staat ook los van het uiteindelijke antwoord van het model: het kan issue-ID's en titels bevatten die het model daarna samenvat. De [MCP-specificatie voor tools](https://modelcontextprotocol.io/specification/latest/server/tools) beschrijft hoe tools deze bewerkingen aanbieden.

<Callout type="info" title="Een verzoek is geen resultaat">
'Ik zal een issue aanmaken' is een uitspraak. Een toolaanroep vraagt de bewerking aan. Een geslaagd antwoord met het ID van het nieuwe issue bewijst dat het is gebeurd. Houd die drie dingen uit elkaar.
</Callout>

### Een tool kan voor een hele workflow staan

Tot nu toe was elke tool één bewerking: zoeken, aanmaken, exporteren. Maar achter de naam van een tool kan veel meer schuilgaan: een compleet proces, vooraf vastgelegd en uitgevoerd door een workflow-engine. De agent beslist nog steeds **wanneer** het proces start en **welke invoer** het meekrijgt. Alles daarna verloopt precies zoals het proces voorschrijft, in dezelfde volgorde, elke keer weer.

Denk aan een terugbetaling. Een supportagent kan een gefrustreerde klant prima begrijpen, maar je wilt waarschijnlijk niet dat hij je terugbetalingsbeleid improviseert. Verpakt als één tool controleert de terugbetalingsworkflow eerst of de klant er recht op heeft, vraagt dan goedkeuring aan een leidinggevende en schrijft daarna het bedrag bij, ongeacht welk gesprek de workflow heeft gestart. Goedkeuringen, deployments en andere processen waarin de stappen zelf het beleid *zijn*, passen in hetzelfde patroon. Workflow-engines houden meestal van elke uitvoering een logboek bij. Daardoor kan de agent ook eerdere uitvoeringen opzoeken en je vertellen welke er vannacht zijn mislukt en bij welke stap, in plaats van te gokken.

AWS geeft een recent voorbeeld. Op 29 oktober 2026 [kondigde AWS aan](https://aws.amazon.com/about-aws/whats-new/2026/10/step-functions-workflows-ai-agent-tools/) dat Step Functions-workflows als tools voor agents kunnen dienen via Amazon Bedrock AgentCore Gateway, dat agents via MCP met tools verbindt. Het idee hoort niet bij één leverancier: een CI-pipeline, een goedkeuringsstroom in een ticketsysteem of een script dat je team al vertrouwt, kun je op dezelfde manier aan een agent aanbieden.

Het gaat om het verdelen van twee sterke punten. Het model is flexibel: het kan een ongebruikelijke situatie lezen en een verstandige volgende stap kiezen. De workflow is voorspelbaar: dezelfde invoer doorloopt dezelfde stappen. Wie het moment aan de agent laat en de stappen aan de workflow, zet elk sterk punt op de juiste plek. Dat verandert ook de prompt. Beschrijf het doel en wanneer de workflow moet worden aangeroepen, niet de stappen erin. Wie de stappen herhaalt, maakt een tweede versie van het beleid, die kan afwijken van het origineel en die het model misschien zelf met de hand probeert te volgen.

### Een tool kan ook een andere agent zijn

Achter één toolnaam kan nog een tweede vorm schuilgaan. In plaats van een vast proces kan de implementatie zelf een agent zijn. Die neemt een verzoek aan en draait zijn eigen lus: hij plant, zoekt, weegt wat hij vindt, schrijft en draait onderweg misschien code, en levert een afgerond resultaat op, zoals een antwoord met bronvermeldingen, een rapport of een bestand. Voor de agent die hem aanriep, ziet dat er allemaal uit als één toolaanroep en één antwoord.

Dat verandert wat de aanroepende agent moet doen. Met dunne zoektools doet de buitenste agent het onderzoek zelf. Hij beslist welke bron hij raadpleegt, leest wat er terugkomt, merkt een tegenstrijdigheid op en zoekt opnieuw. Elke stap gebeurt in zijn eigen contextvenster, en elk ruw resultaat dat hij leest blijft daar staan tot het einde van de taak. Een gespecialiseerde agent krijgt een **doel** in plaats van een reeks toolaanroepen. De gedetailleerde stappen gebeuren in de context van de specialist in plaats van in de jouwe, dus de context van de buitenste agent blijft korter en zijn aandacht blijft bij de grotere taak: wat je vroeg, wat hij al weet en wat er met het resultaat moet gebeuren.

Twee recente voorbeelden laten het idee van verschillende kanten zien. Op 4 november 2026 [introduceerde](https://www.alpha-sense.com/resources/product-articles/superanalyst-mcp/) AlphaSense SuperAnalyst MCP, dat het beschrijft als een agent waaraan je complex financieel en zakelijk onderzoek delegeert. Het plant het onderzoek, verzamelt bronnen uit de documentbibliotheek van het bedrijf, voert de analyse uit en geeft context terug met bronvermeldingen die naar de oorspronkelijke passages verwijzen, in de vorm die het verzoek vraagt: een direct antwoord, een spreadsheet of een bewijsdossier met bronnen. In de opensourcewereld doet de [GPT Researcher MCP-server](https://github.com/assafelovic/gptr-mcp) iets vergelijkbaars voor het open web. Zijn tool `deep_research` neemt één zoekvraag aan en voert een volledige onderzoeksronde uit die meerdere bronnen verkent en controleert. Volgens de [documentatie](https://docs.gptr.dev/docs/gpt-researcher/mcp-server/getting-started) duurt dat zo'n 30 tot 40 seconden, in plaats van het bijna directe antwoord van een gewone zoekopdracht. De tool geeft de verzamelde context en bronnen terug samen met een onderzoeks-ID, waarop aanvullende tools zoals `write_report` en `get_research_sources` kunnen voortbouwen. Dezelfde server biedt ook `quick_search` voor als een snelle, oppervlakkige blik genoeg is, een nuttige herinnering dat beide vormen naast elkaar kunnen bestaan.

Leg dit naast de workflow uit de vorige sectie. Een workflow is voorspelbaar: dezelfde invoer doorloopt elke keer dezelfde stappen, en daarin zit zijn waarde. Een geneste agent is flexibel: hij kiest zelf zijn volgende stap, en daarin zit ook zijn waarde. Maar flexibiliteit brengt dezelfde vragen mee die je elke agent zou stellen aan wie je tools toevertrouwt. Je ziet minder van elke stap, vaak alleen het resultaat en het spoor dat hij besluit terug te geven. Je vertrouwt op zijn bronnen, op zijn oordeel over welke ertoe doen en op zijn eigen zorgvuldigheid bij misleidende inhoud. En een lange geneste run kost nog steeds tokens en tijd, ook als die buiten je zicht worden besteed. Beslis dus door te vragen waar het oordeel thuishoort. Als het wegen van bronnen en kiezen waar je daarna naar kijkt *de expertise is*, laat dat dan aan de specialist. Als de stappen *het beleid zijn*, houd dan een vaste workflow aan.

De prompt volgt daaruit. Beschrijf het doel en de vorm die het antwoord moet hebben, en vraag om bronnen of een opmerking over onzekerheid als dat belangrijk is. Som de interne stappen van de specialist niet op. Hij heeft er zelf al, en een tweede versie in je prompt gaat er alleen mee concurreren.

### Als er geen API is, wordt het scherm de tool

Elke tool die we tot nu toe zagen, had een deur die voor software is gebouwd: een API, een connector, een MCP-server. Veel systemen hebben zo'n deur niet. Een oud intern portaal, de boekingssite van een leverancier, een desktopprogramma uit een ander decennium: mensen gebruiken ze elke dag, maar alleen via het scherm. Voor zulke systemen kunnen sommige modellen het scherm zelf als tool gebruiken. Dat heet meestal **computer use**.

Het mechanisme is de lus die je al kent, met beelden in plaats van gegevens. De toepassing waarin het model draait, stuurt de taak en een screenshot. Het model bekijkt die en antwoordt niet met lopende tekst, maar met een gestructureerde actie: klik op dit punt, typ deze tekst, scrol omlaag. Sommige tools geven elke actie ook een korte, uitgesproken bedoeling mee, zoals 'Klik op het zoekveld om de bestemming in te typen', zodat je een uitvoering makkelijker kunt volgen. Het model zelf verplaatst nog steeds niets. De eigen code van de ontwikkelaar voert de actie uit, maakt een nieuwe screenshot en stuurt die terug. Kijken, handelen, opnieuw kijken, tot de taak klaar is of iemand de lus stopt. Waar die lus draait, doet er net zoveel toe als hoe hij werkt, en daarover gaat de sectie [De computer van de bot](/book/28-persistent-bots) in het hoofdstuk Altijd-aan-bots.

Google maakte zijn Computer Use-tool op 30 oktober 2026 algemeen beschikbaar in de Gemini API ([releasenotes](https://ai.google.dev/gemini-api/docs/changelog)). De [documentatie](https://ai.google.dev/gemini-api/docs/computer-use) beschrijft omgevingen voor browser, mobiel en desktop, acties met een `intent`-veld, instelbaar veiligheidsbeleid dat een actie kan blokkeren of om bevestiging kan vragen vóór stappen zoals een betaling, en het optioneel scannen van screenshots op verborgen promptinjectie. Google raadt zelf aan belangrijke taken nauwlettend in de gaten te houden. Het idee is niet van één bedrijf: Anthropic biedt een [computer use-tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool) voor Claude, en OpenAI een [computertool](https://platform.openai.com/docs/guides/tools-computer-use) in zijn Responses API, allebei gebouwd rond dezelfde uitwisseling van screenshots en acties die jouw toepassing uitvoert.

De nadelen verdienen heldere woorden. Een scherm lezen gaat trager dan een API aanroepen, elke screenshot kost tokens, en een verschoven knop of een onverwachte pop-up kan een uitvoering laten mislukken die gisteren nog werkte. Bestaat er dus een echte API of connector, kies die dan, en bewaar computer use voor de systemen die geen andere ingang laten. Het scherm is bovendien invoer zoals alle andere: tekst op een pagina kan net zo goed promptinjectie bevatten als een document, en dat je die tekst in een afbeelding ziet, maakt hem geen haar betrouwbaarder. En omdat het model alles kan aanklikken wat een mens ook zou kunnen, horen riskante stappen zoals betalen, verwijderen of gegevens wijzigen te wachten tot een mens ze bevestigt.

Toch is een screenshot niet de enige manier om een scherm te zien. Besturingssystemen en browsers houden al een tweede, stillere beschrijving van elk venster bij: de **toegankelijkheidsboom**, de gestructureerde opbouw van knoppen, velden, menu's en labels die ze publiceren zodat schermlezers iemand die het scherm niet ziet kunnen vertellen wat er staat en waar je op kunt drukken. Ook een agent kan die opbouw lezen. In plaats van een afbeelding maakt de tool een snapshot met elk element waarop de agent iets kan doen, telkens met zijn rol, zijn naam en een korte referentie-id. Het model hoeft niet meer te raden op welke coördinaten de knop Opslaan staat; het vraagt om een klik op het element met die referentie. Daarna maakt het een verse snapshot en kijkt het opnieuw, want een klik die gelukt is, bewijst nog niet dat het scherm veranderd is. Vercel Labs heeft een voorbeeld voor desktop-apps als open source uitgebracht, [agent-desktop](https://github.com/vercel-labs/agent-desktop): een commandoregeltool en een C-bibliotheek onder de Apache-2.0-licentie, die de toegankelijkheidsinterfaces van macOS (de AX API), Windows (UI Automation) en Linux (AT-SPI) uitlezen en hun snapshots als JSON teruggeven. De [documentatie](https://agent-browser.dev/desktop) benadrukt zorgvuldig dat het een tool is die agents aanroepen, geen agent: er zit geen model in, en de lus van waarnemen, handelen en controleren blijft bij wie de tool aanroept. In de browser volgt Microsofts [Playwright MCP-server](https://github.com/microsoft/playwright-mcp) hetzelfde idee: daarmee werkt een model met webpagina's via toegankelijkheidssnapshots in plaats van screenshots.

Elke manier van kijken heeft zijn sterke kanten en zijn dode hoeken. Een lijst met benoemde elementen kost meestal minder tokens dan een afbeelding, raakt niet van slag als een knop een paar pixels opschuift, en sommige tools kunnen erdoorheen handelen zonder de muis te bewegen of de focus af te pakken van wie achter het toetsenbord zit. Maar de boom laat alleen zien wat een applicatie zelf prijsgeeft. Een programma zonder toegankelijkheidsinformatie, of een canvas, een game of iets anders dat uit kale pixels bestaat, blijft er onzichtbaar voor, en daar blijft de screenshot de weg naar binnen. Daarom combineren veel tools de twee: ze lezen eerst de opbouw en vallen terug op het beeld waar de opbouw tekortschiet. Het betekent ook dat de zorg waarmee een team zijn app labelt voor mensen die een schermlezer gebruiken zich dubbel terugbetaalt, want precies die labels leest een agent ook.

Voor het prompten gelden dezelfde regels als eerder, alleen met scherpere randen, want een website kan het model niet vertellen wat je bedoelde. Noem de precieze site en pagina, zeg waar de taak ophoudt en zeg wat er bevestigd moet worden voordat er iets gebeurt.

## Wat een connector toevoegt

Een connector bundelt de integratie met een bepaald systeem. Die kan het aanmelden, de keuze van een account of werkruimte, het zoeken van gegevens en het aanbieden van ondersteunde acties als tools regelen. Sommige connectors kunnen alleen zoeken of lezen. Andere ondersteunen ook schrijven.

**Connector is een productterm, geen universele technische standaard.** De ene connector roept rechtstreeks de API van een dienst aan. Een andere gebruikt een MCP-server. Een derde doorzoekt een index die is opgebouwd uit gesynchroniseerde documenten. Controleer wat de specifieke integratie ondersteunt. Microsofts [overzicht van connectors](https://learn.microsoft.com/en-us/azure/connectors/introduction) geeft een voorbeeld van integraties rond API's.

Een account verbinden betekent niet dat de agent elk bestand ziet, al je gegevens in zijn context laadt of elke actie mag uitvoeren. Toegang hangt af van het account, de ingestelde scopes, de toepassing en de machtigingen van de dienst zelf. Zoekresultaten kunnen ook afkomstig zijn uit een index die ouder is dan de oorspronkelijke documenten.

Houd bij de issuetracker deze vragen gescheiden: is er een verbinding ingesteld? Welk project is toegankelijk? Kan de verbinding alleen lezen, of ook issues aanmaken?

## Wat MCP standaardiseert

**MCP** staat voor **Model Context Protocol**. Het definieert een gemeenschappelijke manier waarop AI-toepassingen en externe aanbieders van mogelijkheden communiceren. Het vervangt de API van een dienst niet; een MCP-server kan die API op de achtergrond gebruiken.

De [MCP-architectuur](https://modelcontextprotocol.io/docs/learn/architecture) heeft drie hoofdrollen:

<InfoGrid columns={3} items={[
  { label: "Host", description: "De AI-toepassing waarin de gebruiker werkt. Die coördineert verbindingen, interacties met het model en machtigingen.", color: "blue" },
  { label: "Client", description: "Het onderdeel binnen de host dat een verbinding met een MCP-server onderhoudt.", color: "green" },
  { label: "Server", description: "Een programma dat tools, bronnen of prompts via MCP aanbiedt. Het kan lokaal of op afstand draaien.", color: "amber" }
]} />

Voor een toolaanroep kan de client de tools van de server ontdekken met `tools/list`. De toepassing maakt relevante tooldefinities beschikbaar voor het model. Als het model er een aanvraagt, kan de toepassing via haar MCP-client een `tools/call`-verzoek sturen. De server voert de bewerking uit of delegeert die en geeft het resultaat terug.

Het model hoeft niet zelf een netwerkverbinding te openen. De toepassing en de MCP-implementatie regelen de communicatie. Compatibiliteit blijft belangrijk: de host en server moeten de mogelijkheden ondersteunen die je wilt gebruiken. Een tool ontdekken garandeert geen toestemming om die uit te voeren; toegangscontroles blijven gelden.

### MCP biedt meer dan tools

MCP definieert ook **bronnen** en **prompts**. Deze woorden hebben specifieke betekenissen in het protocol:

<InfoGrid columns={3} items={[
  { label: "Tools", description: "Bewerkingen die het model kan aanvragen, onder de controles van de toepassing. Voorbeeld: issues zoeken.", color: "blue" },
  { label: "Bronnen", description: "Gegevens die de toepassing als context beschikbaar kan maken. Voorbeeld: een projecthandleiding met een URI.", color: "green" },
  { label: "Prompts", description: "Herbruikbare berichtsjablonen die gebruikers kunnen kiezen, met optionele argumenten. Voorbeeld: een rapport over de beoordeling van issues opstellen.", color: "amber" }
]} />

De [gids voor MCP-serverconcepten](https://modelcontextprotocol.io/docs/learn/server-concepts) beschrijft ze als tools die door het model worden aangestuurd, bronnen die door de toepassing worden aangestuurd en prompts die door de gebruiker worden aangestuurd. Dit beschrijft de bedoelde interactiepatronen. Het neemt de machtigingscontroles van de toepassing niet weg.

Een MCP-promptsjabloon is niet automatisch een skill. Een skill kan een langere procedure, referenties en scripts bundelen. Die kan de agent vertellen hoe hij tools moet gebruiken die via MCP, een directe connector of lokale functies beschikbaar zijn.

### Skills kunnen ook met de server meekomen

Tot voor kort kwamen deze twee onderdelen meestal los van elkaar binnen. Een server kon een agent zijn tools geven, maar de kennis om ze goed te gebruiken zat ergens anders: in een apart geïnstalleerde skill, in een README of in de eigen prompt van de gebruiker. Als de dienst veranderde, konden die instructies ongemerkt achterlopen.

De officiële **Skills-extensie** van MCP, sinds september 2026 definitief, dicht een groot deel van dat gat. Een server kan nu niet alleen zijn tools aanbieden, maar ook de skills die uitleggen hoe je ze gebruikt, geschreven in hetzelfde `SKILL.md`-formaat dat in [Agents en Skills](/book/25-agents-and-skills) wordt beschreven. Tools vertellen een agent wat hij kan doen. Skills vertellen hem hoe hij het werk goed doet. Nu kunnen beide van dezelfde server komen, zodat de instructies naast de dienst staan die ze beschrijven en de beheerders van die dienst ze actueel kunnen houden.

Het mechanisme bouwt voort op onderdelen die je al kent. Elk bestand in een skill wordt aangeboden als MCP-bron, meestal met een `skill://`-URI. Een client kan de skills van een server opvragen met `skills/list`, er één ophalen met `skills/get` en de bijbehorende bestanden lezen met `resources/read`.

De beoordelingsmethode (op duplicaten controleren, het issuesjabloon volgen) moet uit een apart geïnstalleerde skill of uit je eigen prompt komen, en kan verouderen als de dienst verandert." }}
  after={{ label: "Een server die ook een skill meelevert", content: "Dezelfde server biedt ook een skill voor het beoordelen van issues. De host ziet eerst alleen de naam en beschrijving, en laadt de volledige instructies pas wanneer een taak erom vraagt. Als de beheerders de dienst aanpassen, kunnen ze de skill meteen mee bijwerken." }}
/>

De host beslist nog steeds hoe een skill bij het model terechtkomt. Het model kan er een kiezen op basis van naam en beschrijving, of de gebruiker kiest hem zelf. In beide gevallen komen de volledige instructies pas in de context wanneer ze nodig zijn, en het lezen van een `SKILL.md`-bestand activeert de skill niet vanzelf.

<Callout type="warning" title="Een skill van een server blijft een instructie">
Een skill van een server is tekst die in de context van de agent terechtkomt en kan bepalen wat de agent daarna doet. Hij verdient dus dezelfde kritische blik als de server zelf. Een zorgvuldige host controleert de inhoud en vraagt om eventuele vereiste goedkeuring voordat hij die laadt. Net als andere officiële MCP-extensies, zoals MCP Apps en de Tasks-extensie die hierna aan bod komt, is Skills optioneel: de extensie wordt alleen gebruikt als zowel de client als de server ondersteuning aangeeft. Ondersteuning in clients staat nog in de kinderschoenen, dus controleer of je toepassing echt skills van servers laadt voordat je erop vertrouwt.
</Callout>

### Als een tool tijd of een antwoord nodig heeft

De meeste toolaanroepen zijn korte uitwisselingen: de agent vraagt, de server antwoordt en het werk gaat verder. Sommige klussen passen niet in dat ritme. Een grondig onderzoek, een grote rapportexport of een build kan vele minuten duren, en sommige klussen komen op een punt waarop alleen de gebruiker kan beslissen hoe het verder moet. MCP biedt voor zulke momenten twee ideeën: **Tasks**, voor werk dat tijd nodig heeft, en **elicitation**, voor werk dat een mens nodig heeft.

De officiële [Tasks-extensie](https://tasks.extensions.modelcontextprotocol.io/) (`io.modelcontextprotocol/tasks`) verandert hoe een trage `tools/call` afloopt. In plaats van het verzoek open te houden tot het werk klaar is, kan de server meteen antwoorden met een blijvende taakverwijzing (task handle), een beetje zoals het bonnetje dat je bij de garderobe krijgt. De client kan de taak bekijken met `tasks/get`, updates of antwoorden sturen met `tasks/update`, de taak stoppen met `tasks/cancel` en het resultaat ophalen zodra het klaar is. Intussen kan de agent gewoon doorwerken en later terugkomen. Dat telt vooral voor [altijd-aan-bots](/book/28-persistent-bots) die klussen uitvoeren terwijl jij weg bent. Tasks is aan beide kanten optioneel: de client geeft bij elk verzoek aan dat hij het ondersteunt, en de server beslist per verzoek of hij een taak aanmaakt. Bestaande tools krijgen dit vermogen niet vanzelf; de maker van de server moet het toevoegen.

<Compare
  before={{ label: "Een blokkerende toolaanroep", content: "De agent roept export_report aan en wacht. Het verzoek blijft minutenlang open. Valt de verbinding weg, dan weet niemand of de export klaar is, en tot het antwoord komt kan de agent niets anders doen." }}
  after={{ label: "Een taakverwijzing", content: "De agent roept export_report aan en krijgt meteen een taakverwijzing terug. Hij gaat verder met ander werk, controleert de taak met tasks/get en haalt het rapport op zodra het klaar is. Veranderen de plannen, dan stopt tasks/cancel de taak." }}
/>

Met [elicitation](https://modelcontextprotocol.io/specification/latest/client/elicitation) kan een server even pauzeren en de gebruiker om gestructureerde invoer vragen: ‘Naar staging deployen?’, ‘Deze terugbetaling bevestigen?’ of een ontbrekend gegeven waarzonder het werk niet verder kan. De host toont een klein formulier, en de gebruiker kan antwoorden, weigeren of annuleren. Weigeren is ook een geldig antwoord, en de server beslist wat er daarna gebeurt. De twee ideeën komen vanzelf samen: een lopende taak kan pauzeren in de toestand `input_required` en halverwege de gebruiker iets vragen. Vóór een schrijfactie is zo'n vraag een natuurlijk controlepunt waarop een mens meebeslist, precies op de plek waar de beslissing ertoe doet.

<Callout type="warning" title="Een formulier van een server blijft een verzoek van een server">
Een elicitation komt van de server, niet van je toepassing, en verdient dus dezelfde kritische blik als elke tooluitvoer. Lees wat er gevraagd wordt voordat je antwoordt, en typ nooit een wachtwoord, API-sleutel of ander geheim in zo'n formulier, tenzij je de server vertrouwt. Ook de ondersteuning verschilt per toepassing: VS Code [documenteert ondersteuning voor elicitation](https://code.visualstudio.com/api/extension-guides/ai/mcp), Cursor ondersteunt elicitation, en Claude Code heeft [MCP Tasks en elicitations](https://code.claude.com/docs/en/mcp) als publieke bèta toegevoegd aan zijn terminal-app, maar nog niet overal waar het draait. Het officiële [overzicht van clientondersteuning](https://modelcontextprotocol.io/extensions/client-matrix) houdt bij welke toepassingen welke extensies ondersteunen, dus controleer de jouwe voordat je op een van beide functies vertrouwt.
</Callout>

### Een server vinden en maar één keer verbinden

Voordat een agent een externe server kan gebruiken, moet iemand die server vinden, uitzoeken hoe je verbinding maakt en inloggen. Lange tijd betekende dat: een URL uit een README kopiëren, raden welk transport je nodig hebt en de installatie in elke toepassing herhalen. Nu komen er twee soorten hulp bij: informatie die een client **vóór** het verbinden kan lezen, en verbindingen die je **één keer** instelt en daarna hergebruikt.

Aan de kant van het vinden werd de **Server Cards**-extensie van MCP ([SEP-2127](https://modelcontextprotocol.io/seps/2127-mcp-server-cards)) op 6 oktober 2026 definitief. Die beschrijft een klein, statisch document over een externe server: de naam, de endpoints en transporten, en de protocolversies die hij ondersteunt. Een website kan haar cards opnemen in een AI-catalogus op `/.well-known/ai-catalog.json`, zodat een client die je naar een domein verwijst zonder handmatige installatie leert waar en hoe hij verbinding kan maken. De card laat de lijst met tools bewust weg, omdat de tools die een server aanbiedt kunnen verschillen per ingelogde gebruiker. Die komen nog steeds na het verbinden uit `tools/list`.

Aan de kant van het verbinden begon GitHub op 28 oktober 2026 met het uitrollen van [door GitHub geverifieerde MCP-servers](https://github.blog/changelog/2026-10-28-connect-your-tools-to-copilot-without-all-the-setup/) als openbare preview. GitHub noemt ze ook connectors. Je logt één keer in bij een dienst als Slack of Sentry, en de verbinding werkt in de Copilot-app, Copilot CLI, VS Code, Copilot in de cloud en GitHub Mobile.

Tools zijn bovendien niet alleen webdiensten. Op dezelfde dag [kondigde Google](https://developer.android.com/blog/posts/build-it-your-way-a-next-era-of-android-development) op de Android Dev Summit aan dat **AppFunctions**, door Google omschreven als de uniforme laag voor toolaanroepen in Android, nu in bèta is. Via Android MCP kan een app op je telefoon functies zoals een notitie maken of een bericht versturen aanbieden aan een eigen agent op het apparaat of aan agents op systeemniveau, zonder dat iemand de app hoeft te openen.

Dat brengt ons terug bij een eerder punt: **connector** is een productterm. Een server card, een verificatiebadge en één keer inloggen maken de installatie makkelijker en helpen je te vertrouwen *met wie* je verbinding maakt. Ze beslissen niet *wat* je toestaat. Je kiest nog steeds zelf welk account je koppelt, welke machtigingen je geeft en welke acties op goedkeuring moeten wachten. Noch vindbaarheidsgegevens noch verificatie vervangen het nalopen van wat de tools werkelijk kunnen zodra ze in de lijst staan.

### Als niemand de server opzoekt

Alles hierboven gaat ervan uit dat iemand de server echt opzoekt, of dat nu een mens is die een overzicht doorbladert of een client die een server card leest. Vaak doet niemand dat. Je zegt tegen een codeeragent "zet een GitHub-MCP op", en de agent moet zelf een pakket kiezen. Grijpt hij naar een naam die hij zich herinnert in plaats van een naam die hij heeft gecontroleerd, dan komt die keuze uit de trainingsdata van het model. Die data zijn een momentopname van een moment dat al voorbij is. Intussen kan de eigenaar van een dienst de server hebben vervangen of gearchiveerd, en het model kan dat op geen enkele manier weten.

Onderzoekers van Glow Labs (Glow Security) [beschreven precies dit](https://www.helpnetsecurity.com/2026/11/03/mcphantom-deprecated-mcp-servers/) in november 2026, nadat ze transcripten van echte codeersessies hadden bekeken. Ze noemden het patroon MCPhantom. In de sessies waarin een agent een verouderde MCP-server installeerde of voorstelde, lijkt de agent de pakketnaam in 98% van de gevallen uit zijn trainingsdata te hebben ingevuld; in de overige 2% had de gebruiker zelf om het oude pakket gevraagd. In hun GitHub-voorbeeld liet de agent de server die GitHub zelf onderhoudt links liggen en koos hij een gearchiveerde referentieserver die hij zich herinnerde. Het lag niet aan één product: het patroon dook op in meerdere harnesses, waaronder Claude Code, Cursor en Codex CLI, en bij modellen van meerdere aanbieders. De onderzoekers vonden in die gearchiveerde servers ook vier ernstige kwetsbaarheden. De ernstigste is een lek in de Puppeteer-server waarmee via een prompt injection op afstand code kan worden uitgevoerd. Omdat de repositories gearchiveerd zijn, komen er geen patches, al vermeldt het rapport dat er geen misbruik was waargenomen.

Twee details maken het probleem makkelijk over het hoofd te zien. Het pakket opzoeken is niet altijd genoeg: in één sessie zag de agent op npm "This package is deprecated", installeerde het pakket toch en zei er niets over tegen de gebruiker. En omdat zulke servers meestal via `npx` draaien, verschijnen ze nooit in een afhankelijkhedenbestand; niets in het project legt vast dat ze er zijn. Zoals een van de onderzoekers het zei: "Het geheugen van het model is nu een pakketbeheerder die nooit hoort wat er verouderd is."

<Callout type="warning" title="Een installatie is ook een actie">
Vraag een agent, voordat hij een server toevoegt, welk pakket hij heeft gekozen en waar het vandaan komt. Geef de voorkeur aan de officiële server van de eigenaar van de dienst als die bestaat, controleer of hij nog wordt onderhouden en niet verouderd of gearchiveerd is, en kies één server per dienst. Behandel de installatie als iets wat jij goedkeurt, net als elke andere actie van de agent. Het eenvoudigst is om de server die je wilt meteen in de prompt te noemen. Dan hoeft de agent niets uit zijn geheugen in te vullen.
</Callout>

### Verbinden is al een kwestie van vertrouwen

MCPhantom gaat over het kiezen van de verkeerde server. Aan de andere kant van die keuze wacht een stiller risico: ook als je een remote server zorgvuldig kiest, kan het verbinden zelf al schade aanrichten. Een remote server draait op de machine van iemand anders, dus zijn code komt nooit op de jouwe terecht, en daardoor voelt een eerste verbinding als vrijblijvend rondkijken. Helemaal waar is dat niet. Je client draait nog steeds op jouw machine, en die leest en verwerkt alles wat de server terugstuurt, ook de adressen die de server meegeeft wanneer hij je vraagt in te loggen.

Op 5 november 2026 [liet Pillar Security zien hoeveel dat uitmaakt](https://www.pillar.security/blog/inspecting-the-inspector-rce-in-mcps-official-debugging-tool). Het onderzoek ging over de MCP Inspector (`@modelcontextprotocol/inspector`), de officiële debugtool van het MCP-project. Ontwikkelaars richten hem op lokale en remote servers die ze nog niet vertrouwen, om de tools, resources en prompts te bekijken voordat ze een echte agent in de buurt laten komen. Op Windows en WSL konden Inspector-versies van vóór 2.12.0 ertoe worden gebracht willekeurige code uit te voeren tijdens het inloggen via OAuth bij een remote server, nog voordat er één tool was opgesomd en zonder dat iemand ergens toestemming voor had gegeven.

De keten is kort, en elke schakel ziet er op zichzelf onschuldig uit. Als een remote server de client vraagt in te loggen, noemt hij zijn eigen `authorization_endpoint`, het adres van zijn inlogpagina, en dat adres is een tekenreeks die de server zelf kiest. De client opent het automatisch met `open`, een veelgebruikt npm-pakket om de browser te starten. Op Windows en WSL zetten versies van `open` van vóór 11.0.0 dat adres zonder escaping in een PowerShell-opdracht, zodat PowerShell code kon uitvoeren die verstopt zat in een verder volkomen geldige https-URL. De code draaide terwijl de ontwikkelaar gewoon verbinding maakte, nog voordat de browser was opengegaan.

De maintainers erkenden de melding en losten het probleem op in Inspector 2.12.0, uitgebracht op 21 oktober 2026: die versie stapt over op `open` 11 en zorgt ervoor dat de URL die wordt geopend precies de URL is die is gecontroleerd. Ze publiceerden ook het beveiligingsadvies [GHSA-q978-78c7-phqw](https://github.com/modelcontextprotocol/inspector/security/advisories/GHSA-q978-78c7-phqw). De Inspector stond niet alleen. Twee weken eerder had Pillar [dezelfde keten beschreven](https://www.pillar.security/blog/open-and-shut-remote-code-execution-in-opencode-via-mcp-oauth) in de codeeragent OpenCode (`opencode-ai`). Omdat de oorzaak ligt in de manier waarop beide tools het adres van een server aan `open` doorgaven, dekt nu één registratie, CVE-2026-119025, `open`, de Inspector en OpenCode samen.

De les gaat verder dan deze ene bug. De Inspector bestaat zodat je een vijandige server kunt bekijken zonder er zelf schade van te ondervinden. Door een vijandige remote server bij zijn eigen referentietool als serieus scenario te behandelen, de bug te verhelpen en een advies te publiceren, heeft het MCP-project een verwachting neergelegd voor elke client die dezelfde OAuth-flow gebruikt: een remote MCP-server is onbetrouwbare invoer. Een server hoeft bovendien niet vanaf het begin kwaadaardig te zijn. Een naam die sprekend op een andere lijkt, een verlopen domein of een latere overname kan een kwaadaardig antwoord achter een adres zetten dat je ooit vertrouwde, en dat antwoord komt bij elke verbinding opnieuw binnen. De server cards en verificatiebadges van eerder helpen je kiezen *met wie* je verbinding maakt. Wat je client met het antwoord doet, veranderen ze niet.

<Callout type="warning" title="De handshake hoort bij de vertrouwensgrens">
Weet, voordat je verbinding maakt met een remote server, zeker een die je nog aan het beoordelen bent, welke client je gebruikt en in welke versie, en houd die bij. Op Windows en WSL betekent dat MCP Inspector 2.12.0 of nieuwer, OpenCode 1.18.33 of nieuwer en `open` 11.0.0 of nieuwer als je eigen code het gebruikt. Vraag je een agent om een server voor je toe te voegen of uit te proberen, dan is zijn harness de client en gelden dezelfde vragen. Bovenal: behandel verbinden als een beslissing en niet als vrijblijvend rondkijken. De inloghandshake draait al op jouw machine voordat de eerste tool verschijnt.
</Callout>

## Prompts voor een agent met tools

Vertel de agent welke informatie hij moet zoeken, hoe hij die moet gebruiken en welke acties je verwacht. Neem niet zomaar aan dat er een verbinding is of dat een tool elke bewerking van de dienst ondersteunt.

Een herbruikbare skill voor het beoordelen van issues kan de methode toevoegen: zoek naar duplicaten, vergelijk reproductiestappen, volg het issuesjabloon van het project en meld openstaande vragen. De tool levert de bewerking. De skill legt uit hoe je die goed gebruikt.

Tooluitvoer moet nog steeds worden beoordeeld. Een issueopmerking, document of zoekresultaat kan fouten bevatten of tekst die op een instructie lijkt. Behandel opgehaalde inhoud als gegevens en laat die niet het verzoek van de gebruiker of de regels van de toepassing veranderen. Ondersteuning voor MCP alleen maakt een server of zijn inhoud niet betrouwbaar.

Als lezen mislukt, kan de agent de fout melden of een redelijk alternatief proberen. Als een schrijfactie een time-out geeft, moet hij vóór een nieuwe poging controleren of de wijziging is uitgevoerd. Anders kan een nieuwe poging een dubbel issue aanmaken. Inloggegevens horen bij de verbindingsinstellingen van de integratie, niet in de taakprompt. Deze regels zijn nog belangrijker wanneer een bot volgens een schema tools gebruikt terwijl jij weg bent, zoals beschreven in [Altijd-aan-bots](/book/28-persistent-bots).

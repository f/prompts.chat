Je vraagt een agent om de openstaande bugs in je project te vinden en een vervolgissue op te stellen. Daarvoor zijn goede instructies alleen niet genoeg. De agent moet je issuetracker kunnen bereiken, de juiste gegevens kunnen lezen en er misschien iets kunnen aanmaken.

Hier komen **tools**, **connectors** en **MCP** in beeld. Ze hangen samen, maar beschrijven verschillende delen van de opstelling.

Een tool kan ook lokaal werken. Een rekenmachine heeft geen accountverbinding nodig. Een tool om bestanden te lezen kan volledig op je computer werken. Een externe dienst is maar één mogelijke bron van tools.

## Wat een tool eigenlijk bevat

Een tool heeft meestal een **naam**, een **beschrijving**, een **invoerschema** en een implementatie die het werk uitvoert. De beschrijving helpt het model te bepalen wanneer het de tool moet gebruiken. Het schema beschrijft de argumenten die de tool accepteert.

Hier is een kleine definitie van een fictieve MCP-tool:

<Collapsible title="Bekijk de definitie van search_issues">

```json
{
  "name": "search_issues",
  "description": "Zoek issues in het verbonden project. Deze tool leest alleen gegevens.",
  "inputSchema": {
    "type": "object",
    "properties": {
      "query": { "type": "string" },
      "limit": { "type": "integer", "minimum": 1, "maximum": 20 }
    },
    "required": ["query"],
    "additionalProperties": false
  }
}
```

</Collapsible>

Het model kan `search_issues` aanvragen met `{"query": "openstaande bugs", "limit": 3}`. De toepassing stuurt dat verzoek naar de implementatie. Die bevraagt de tracker en geeft resultaten of een fout terug.

De naam en het schema voeren zelf niets uit. De implementatie moet de invoer valideren, de toegang controleren en de bewerking uitvoeren. Het antwoord van een tool staat ook los van het uiteindelijke antwoord van het model: het kan issue-ID's en titels bevatten die het model daarna samenvat. De [MCP-specificatie voor tools](https://modelcontextprotocol.io/specification/latest/server/tools) beschrijft hoe tools deze bewerkingen aanbieden.

<Callout type="info" title="Een verzoek is geen resultaat">
'Ik zal een issue aanmaken' is een uitspraak. Een toolaanroep vraagt de bewerking aan. Een geslaagd antwoord met het ID van het nieuwe issue bewijst dat het is gebeurd. Houd die drie dingen uit elkaar.
</Callout>

## Wat een connector toevoegt

Een connector bundelt de integratie met een bepaald systeem. Die kan het aanmelden, de keuze van een account of werkruimte, het zoeken van gegevens en het aanbieden van ondersteunde acties als tools regelen. Sommige connectors kunnen alleen zoeken of lezen. Andere ondersteunen ook schrijven.

**Connector is een productterm, geen universele technische standaard.** De ene connector roept rechtstreeks de API van een dienst aan. Een andere gebruikt een MCP-server. Een derde doorzoekt een index die is opgebouwd uit gesynchroniseerde documenten. Controleer wat de specifieke integratie ondersteunt. Microsofts [overzicht van connectors](https://learn.microsoft.com/en-us/azure/connectors/introduction) geeft een voorbeeld van integraties rond API's.

Een account verbinden betekent niet dat de agent elk bestand ziet, al je gegevens in zijn context laadt of elke actie mag uitvoeren. Toegang hangt af van het account, de ingestelde scopes, de toepassing en de machtigingen van de dienst zelf. Zoekresultaten kunnen ook afkomstig zijn uit een index die ouder is dan de oorspronkelijke documenten.

Houd bij de issuetracker deze vragen gescheiden: is er een verbinding ingesteld? Welk project is toegankelijk? Kan de verbinding alleen lezen, of ook issues aanmaken?

## Wat MCP standaardiseert

**MCP** staat voor **Model Context Protocol**. Het definieert een gemeenschappelijke manier waarop AI-toepassingen en externe aanbieders van mogelijkheden communiceren. Het vervangt de API van een dienst niet; een MCP-server kan die API op de achtergrond gebruiken.

De [MCP-architectuur](https://modelcontextprotocol.io/docs/learn/architecture) heeft drie hoofdrollen:

<InfoGrid columns={3} items={[
  { label: "Host", description: "De AI-toepassing waarin de gebruiker werkt. Die coördineert verbindingen, interacties met het model en machtigingen.", color: "blue" },
  { label: "Client", description: "Het onderdeel binnen de host dat een verbinding met een MCP-server onderhoudt.", color: "green" },
  { label: "Server", description: "Een programma dat tools, bronnen of prompts via MCP aanbiedt. Het kan lokaal of op afstand draaien.", color: "amber" }
]} />

Voor een toolaanroep kan de client de tools van de server ontdekken met `tools/list`. De toepassing maakt relevante tooldefinities beschikbaar voor het model. Als het model er een aanvraagt, kan de toepassing via haar MCP-client een `tools/call`-verzoek sturen. De server voert de bewerking uit of delegeert die en geeft het resultaat terug.

Het model hoeft niet zelf een netwerkverbinding te openen. De toepassing en de MCP-implementatie regelen de communicatie. Compatibiliteit blijft belangrijk: de host en server moeten de mogelijkheden ondersteunen die je wilt gebruiken. Een tool ontdekken garandeert geen toestemming om die uit te voeren; toegangscontroles blijven gelden.

### MCP biedt meer dan tools

MCP definieert ook **bronnen** en **prompts**. Deze woorden hebben specifieke betekenissen in het protocol:

<InfoGrid columns={3} items={[
  { label: "Tools", description: "Bewerkingen die het model kan aanvragen, onder de controles van de toepassing. Voorbeeld: issues zoeken.", color: "blue" },
  { label: "Bronnen", description: "Gegevens die de toepassing als context beschikbaar kan maken. Voorbeeld: een projecthandleiding met een URI.", color: "green" },
  { label: "Prompts", description: "Herbruikbare berichtsjablonen die gebruikers kunnen kiezen, met optionele argumenten. Voorbeeld: een rapport over de beoordeling van issues opstellen.", color: "amber" }
]} />

De [gids voor MCP-serverconcepten](https://modelcontextprotocol.io/docs/learn/server-concepts) beschrijft ze als tools die door het model worden aangestuurd, bronnen die door de toepassing worden aangestuurd en prompts die door de gebruiker worden aangestuurd. Dit beschrijft de bedoelde interactiepatronen. Het neemt de machtigingscontroles van de toepassing niet weg.

Een MCP-promptsjabloon is niet automatisch een skill. Een skill kan een langere procedure, referenties en scripts bundelen. Die kan de agent vertellen hoe hij tools moet gebruiken die via MCP, een directe connector of lokale functies beschikbaar zijn.

### Skills kunnen ook met de server meekomen

Tot voor kort kwamen deze twee onderdelen meestal los van elkaar binnen. Een server kon een agent zijn tools geven, maar de kennis om ze goed te gebruiken zat ergens anders: in een apart geïnstalleerde skill, in een README of in de eigen prompt van de gebruiker. Als de dienst veranderde, konden die instructies ongemerkt achterlopen.

De officiële **Skills-extensie** van MCP, sinds september 2026 definitief, dicht een groot deel van dat gat. Een server kan nu niet alleen zijn tools aanbieden, maar ook de skills die uitleggen hoe je ze gebruikt, geschreven in hetzelfde `SKILL.md`-formaat dat in [Agents en Skills](/book/25-agents-and-skills) wordt beschreven. Tools vertellen een agent wat hij kan doen. Skills vertellen hem hoe hij het werk goed doet. Nu kunnen beide van dezelfde server komen, zodat de instructies naast de dienst staan die ze beschrijven en de beheerders van die dienst ze actueel kunnen houden.

Het mechanisme bouwt voort op onderdelen die je al kent. Elk bestand in een skill wordt aangeboden als MCP-bron, meestal met een `skill://`-URI. Een client kan de skills van een server opvragen met `skills/list`, er één ophalen met `skills/get` en de bijbehorende bestanden lezen met `resources/read`.

<Compare
  before={{ label: "Een server met alleen tools", content: "De trackerserver biedt search_issues en create_issue aan. De beoordelingsmethode (op duplicaten controleren, het issuesjabloon volgen) moet uit een apart geïnstalleerde skill of uit je eigen prompt komen, en kan verouderen als de dienst verandert." }}
  after={{ label: "Een server die ook een skill meelevert", content: "Dezelfde server biedt ook een skill voor het beoordelen van issues. De host ziet eerst alleen de naam en beschrijving, en laadt de volledige instructies pas wanneer een taak erom vraagt. />

De host beslist nog steeds hoe een skill bij het model terechtkomt. Het model kan er een kiezen op basis van naam en beschrijving, of de gebruiker kiest hem zelf. In beide gevallen komen de volledige instructies pas in de context wanneer ze nodig zijn, en het lezen van een `SKILL.md`-bestand activeert de skill niet vanzelf.

<Callout type="warning" title="Een skill van een server blijft een instructie">
Een skill van een server is tekst die in de context van de agent terechtkomt en kan bepalen wat de agent daarna doet. Hij verdient dus dezelfde kritische blik als de server zelf. Een zorgvuldige host controleert de inhoud en vraagt om eventuele vereiste goedkeuring voordat hij die laadt. Net als andere officiële MCP-extensies, zoals MCP Apps en de Tasks-extensie die hierna aan bod komt, is Skills optioneel: de extensie wordt alleen gebruikt als zowel de client als de server ondersteuning aangeeft. Ondersteuning in clients staat nog in de kinderschoenen, dus controleer of je toepassing echt skills van servers laadt voordat je erop vertrouwt.
</Callout>

### Als een tool tijd of een antwoord nodig heeft

De meeste toolaanroepen zijn korte uitwisselingen: de agent vraagt, de server antwoordt en het werk gaat verder. Sommige klussen passen niet in dat ritme. Een grondig onderzoek, een grote rapportexport of een build kan vele minuten duren, en sommige klussen komen op een punt waarop alleen de gebruiker kan beslissen hoe het verder moet. MCP biedt voor zulke momenten twee ideeën: **Tasks**, voor werk dat tijd nodig heeft, en **elicitation**, voor werk dat een mens nodig heeft.

De officiële [Tasks-extensie](https://tasks.extensions.modelcontextprotocol.io/) (`io.modelcontextprotocol/tasks`) verandert hoe een trage `tools/call` afloopt. In plaats van het verzoek open te houden tot het werk klaar is, kan de server meteen antwoorden met een blijvende taakverwijzing (task handle), een beetje zoals het bonnetje dat je bij de garderobe krijgt. De client kan de taak bekijken met `tasks/get`, updates of antwoorden sturen met `tasks/update`, de taak stoppen met `tasks/cancel` en het resultaat ophalen zodra het klaar is. Intussen kan de agent gewoon doorwerken en later terugkomen. Dat telt vooral voor [altijd-aan-bots](/book/28-persistent-bots) die klussen uitvoeren terwijl jij weg bent. Tasks is aan beide kanten optioneel: de client geeft bij elk verzoek aan dat hij het ondersteunt, en de server beslist per verzoek of hij een taak aanmaakt. Bestaande tools krijgen dit vermogen niet vanzelf; de maker van de server moet het toevoegen.

<Compare
  before={{ label: "Een blokkerende toolaanroep", content: "De agent roept export_report aan en wacht. Het verzoek blijft minutenlang open. Valt de verbinding weg, dan weet niemand of de export klaar is, en tot het antwoord komt kan de agent niets anders doen." }}
  after={{ label: "Een taakverwijzing", content: "De agent roept export_report aan en krijgt meteen een taakverwijzing terug. Hij gaat verder met ander werk, controleert de taak met tasks/get en haalt het rapport op zodra het klaar is. Veranderen de plannen, dan stopt tasks/cancel de taak." }}
/>

Met [elicitation](https://modelcontextprotocol.io/specification/latest/client/elicitation) kan een server even pauzeren en de gebruiker om gestructureerde invoer vragen: ‘Naar staging deployen?’, ‘Deze terugbetaling bevestigen?’ of een ontbrekend gegeven waarzonder het werk niet verder kan. De host toont een klein formulier, en de gebruiker kan antwoorden, weigeren of annuleren. Weigeren is ook een geldig antwoord, en de server beslist wat er daarna gebeurt. De twee ideeën komen vanzelf samen: een lopende taak kan pauzeren in de toestand `input_required` en halverwege de gebruiker iets vragen. Vóór een schrijfactie is zo'n vraag een natuurlijk controlepunt waarop een mens meebeslist, precies op de plek waar de beslissing ertoe doet.

<Callout type="warning" title="Een formulier van een server blijft een verzoek van een server">
Een elicitation komt van de server, niet van je toepassing, en verdient dus dezelfde kritische blik als elke tooluitvoer. Lees wat er gevraagd wordt voordat je antwoordt, en typ nooit een wachtwoord, API-sleutel of ander geheim in zo'n formulier, tenzij je de server vertrouwt. Ook de ondersteuning verschilt per toepassing: VS Code [documenteert ondersteuning voor elicitation](https://code.visualstudio.com/api/extension-guides/ai/mcp), Cursor ondersteunt elicitation, en Claude Code heeft [MCP Tasks en elicitations](https://code.claude.com/docs/en/mcp) als publieke bèta toegevoegd aan zijn terminal-app, maar nog niet overal waar het draait. Het officiële [overzicht van clientondersteuning](https://modelcontextprotocol.io/extensions/client-matrix) houdt bij welke toepassingen welke extensies ondersteunen, dus controleer de jouwe voordat je op een van beide functies vertrouwt.
</Callout>

## Prompts voor een agent met tools

Vertel de agent welke informatie hij moet zoeken, hoe hij die moet gebruiken en welke acties je verwacht. Neem niet zomaar aan dat er een verbinding is of dat een tool elke bewerking van de dienst ondersteunt.

<Compare
  before={{ label: "Te veel om te raden", content: "Bekijk de bugs en regel alles." }}
  after={{ label: "Duidelijke uitkomst en grenzen", content: "Zoek in het verbonden project naar openstaande bugs over lege zoekresultaten. Vat de relevante issues samen en vermeld hun ID's. Stel zo nodig een vervolgissue op, maar vraag het voordat je het aanmaakt. Als de verbinding of de benodigde tool niet beschikbaar is, leg dan uit wat er ontbreekt. Beweer niet dat een issue is aangemaakt zonder een geslaagd toolresultaat." }}
/>

Een herbruikbare skill voor het beoordelen van issues kan de methode toevoegen: zoek naar duplicaten, vergelijk reproductiestappen, volg het issuesjabloon van het project en meld openstaande vragen. De tool levert de bewerking. De skill legt uit hoe je die goed gebruikt.

Tooluitvoer moet nog steeds worden beoordeeld. Een issueopmerking, document of zoekresultaat kan fouten bevatten of tekst die op een instructie lijkt. Behandel opgehaalde inhoud als gegevens en laat die niet het verzoek van de gebruiker of de regels van de toepassing veranderen. Ondersteuning voor MCP alleen maakt een server of zijn inhoud niet betrouwbaar.

Als lezen mislukt, kan de agent de fout melden of een redelijk alternatief proberen. Als een schrijfactie een time-out geeft, moet hij vóór een nieuwe poging controleren of de wijziging is uitgevoerd. Anders kan een nieuwe poging een dubbel issue aanmaken. Inloggegevens horen bij de verbindingsinstellingen van de integratie, niet in de taakprompt. Deze regels zijn nog belangrijker wanneer een bot volgens een schema tools gebruikt terwijl jij weg bent, zoals beschreven in [Altijd-aan-bots](/book/28-persistent-bots).

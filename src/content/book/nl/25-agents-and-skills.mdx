## Wat zijn AI-agents?

Een **AI-agent** is een AI-systeem dat autonoom taken kan plannen, uitvoeren en herhalen. In tegenstelling tot eenvoudige prompt-respons interacties kunnen agents:

- **Plannen** - Complexe doelen opdelen in uitvoerbare stappen
- **Uitvoeren** - Tools gebruiken en acties ondernemen in de echte wereld
- **Observeren** - Feedback van hun acties verwerken
- **Aanpassen** - Hun aanpak bijstellen op basis van resultaten
- **Volhouden** - Context en geheugen behouden over interacties heen

Deze prompttypes stapelen samen om compleet agent-gedrag te vormen:

### Systeemprompts (De identiteit van de agent)

De fundamentele prompt die vaststelt wie de agent is en hoe deze zich gedraagt:

```markdown
You are a code review assistant. Your role is to:
- Analyze code for bugs, security issues, and performance problems
- Suggest improvements following best practices
- Explain your reasoning clearly
- Be constructive and educational in feedback

You have access to tools for reading files, searching code, and running tests.
```

### Planningsprompts (Hoe te denken)

Instructies die het redeneer- en planningsproces van de agent begeleiden:

```markdown
Before taking action, always:
1. Understand the complete request
2. Break it into smaller, verifiable steps
3. Identify which tools you'll need
4. Consider edge cases and potential issues
5. Execute step by step, validating as you go
```

### Tool-use prompts (Hoe te handelen)

Richtlijnen over wanneer en hoe beschikbare tools te gebruiken:

```markdown
When you need to understand a codebase:
- Use grep_search for finding specific patterns
- Use read_file to examine file contents
- Use list_dir to explore directory structure
- Always verify your understanding before making changes
```

### Herstelprompts (Hoe om te gaan met fouten)

Instructies voor wanneer dingen misgaan:

```markdown
If an action fails:
1. Analyze the error message carefully
2. Consider alternative approaches
3. Ask for clarification if the task is ambiguous
4. Never repeat the same failed action without changes
```

<Callout type="info" title="De prompt-stack">
Het gedrag van een agent ontstaat uit lagen van prompts die samenwerken. De systeemprompt legt de basis, planningsprompts begeleiden het redeneren, tool-prompts maken actie mogelijk, en herstelprompts behandelen fouten. Samen creëren ze coherent, capabel gedrag.
</Callout>

## Wat zijn skills?

Als prompts de atomen zijn, dan zijn **skills de moleculen**—herbruikbare bouwstenen die agents specifieke capaciteiten geven.

Een **skill** is een uitgebreid, draagbaar pakket van instructies dat een AI-agent expertise geeft in een specifiek domein of taak. Skills zijn de herbruikbare blokken van agents: je bouwt ze eenmaal, en elke agent kan ze gebruiken.

<Callout type="tip" title="Skills = Herbruikbare agentblokken">
Schrijf eenmaal een skill voor code review. Nu kan elke coding-agent—of het nu voor Python, JavaScript of Rust is—direct een expert code reviewer worden door die skill te laden. Skills laten je agent-capaciteiten bouwen als LEGO-blokken.
</Callout>

Het `SKILL.md`-bestand definieert de algemene aanpak:

```markdown
---
name: code-review
description: Comprehensive code review with security, performance, and style analysis
---

# Code Review Skill

You are an expert code reviewer. When reviewing code:

## Process
1. **Understand Context** - What does this code do? What problem does it solve?
2. **Check Correctness** - Does it work? Are there logic errors?
3. **Security Scan** - Reference security-checklist.md for common vulnerabilities
4. **Performance Review** - Check performance-tips.md for optimization opportunities
5. **Style & Maintainability** - Is the code readable and maintainable?

## Output Format
Provide feedback in categories:
- 🔴 **Critical** - Must fix before merge
- 🟡 **Suggested** - Recommended improvements
- 🟢 **Nice to have** - Optional enhancements

Always explain *why* something is an issue, not just *what* is wrong.
```

## Effectieve skills bouwen

### 1. Definieer de expertise duidelijk

Begin met een duidelijke beschrijving van wat de skill mogelijk maakt:

```markdown
---
name: api-design
description: Design RESTful APIs following industry best practices, 
  including versioning, error handling, and documentation standards
---
```

### 2. Structureer kennis hiërarchisch

Organiseer informatie van algemeen naar specifiek:

```markdown
# API Design Skill

## Core Principles
- Resources should be nouns, not verbs
- Use HTTP methods semantically
- Version your APIs from day one

## Detailed Guidelines
[More specific rules...]

## Reference Materials
- See `rest-conventions.md` for naming conventions
- See `error-codes.md` for standard error responses
```

### 3. Voeg concrete voorbeelden toe

Abstracte regels worden duidelijk met voorbeelden:

```markdown
## Endpoint Naming

✅ Good:
- GET /users/{id}
- POST /orders
- DELETE /products/{id}/reviews/{reviewId}

❌ Avoid:
- GET /getUser
- POST /createNewOrder
- DELETE /removeProductReview
```

### 4. Bied besliskaders

Help de agent keuzes te maken in onduidelijke situaties:

```markdown
## When to Use Pagination

Use pagination when:
- Collection could exceed 100 items
- Response size impacts performance
- Client may not need all items

Use full response when:
- Collection is always small (<20 items)
- Client typically needs everything
- Real-time consistency is critical
```

### 5. Voeg herstelpatronen toe

Anticipeer op wat mis kan gaan:

```markdown
## Common Issues

**Problem**: Client needs fields not in standard response
**Solution**: Implement field selection: GET /users?fields=id,name,email

**Problem**: Breaking changes needed
**Solution**: Create new version, deprecate old with timeline
```

Bij het combineren van skills, zorg ervoor dat ze niet conflicteren. Skills moeten zijn:

- **Modulair** - Elke skill behandelt één domein goed
- **Compatibel** - Skills mogen geen tegenstrijdige instructies geven
- **Geprioriteerd** - Wanneer skills overlappen, definieer welke voorrang heeft

## Wanneer skills leren van ervaring

Tot nu toe is elke skill in dit hoofdstuk door een mens geschreven. Iemand merkt dat een taak steeds terugkomt, gaat ervoor zitten en zet de kennis op papier. Maar een agent die dag in dag uit met je samenwerkt, houdt ondertussen ook stilletjes bij hoe dat werk verliep: welke instructies hij volgde, waar je moest ingrijpen om hem te corrigeren, welke stappen hij twee keer moest doen. Een nieuwer patroon maakt gebruik van dat verslag. In plaats van te wachten tot iemand de skill schrijft, kijkt het systeem van de agent zelf terug op zijn ervaring en schrijft het op eigen houtje nieuwe skills, of herziet het bestaande. Je kunt het zien als een lus, sterk verwant aan de agent-lus aan het begin van dit hoofdstuk, alleen trager en naar binnen gekeerd:

Perplexity beschrijft deze lus uitgebreid voor **Brain**, het zelfverbeterende geheugensysteem achter zijn agent Computer ([What is Brain?](https://www.perplexity.ai/help-center/en/articles/19700001-what-is-brain)). In een blogpost van november 2026 ([Self-improving skills](https://www.perplexity.ai/hub/blog/self-improving-skills)) legt het bedrijf uit hoe Brain put uit het geheugen en de sessiegeschiedenis van een gebruiker om *persoonlijke* skills te schrijven en te verfijnen. In de bewijsfase zoekt het eerdere sessies waarin een skill werd gebruikt, vooral die waarin hij tekortschoot. Tijdens de reflectie bestudeert een verbeteragent die sessies en stelt hij wijzigingen voor. De verificatie controleert of het voorstel goed is opgebouwd en de resultaten waarschijnlijk verbetert, en de activering voert het door, zodat de sessies die volgen bewijs worden voor de volgende ronde. Wat de lus betrouwbaar maakt, is de terughoudendheid die erin is ingebouwd. Een nieuwe skill vereist twee onafhankelijke keren dat hetzelfde herbruikbare gedrag voorkomt, terwijl een update van een bestaande skill kan rusten op één goed onderbouwd geval. De verbeteragent past een skill nooit rechtstreeks aan: hij schrijft een voorstel met zijn redenering en bewijs, doet per run hooguit één wijziging per skill en ziet ervan af als het bewijs geen wijziging rechtvaardigt. Bovendien zijn automatisch gemaakte skills beperkt tot tien per gebruiker, dus er kan alleen een nieuwe bij als er een oude verdwijnt, met een onderbouwing voor die ruil.

**Hermes Agent** van Nous Research benadert hetzelfde idee vanuit een team. Naarmate iemand terugkerend werk aan Hermes overdraagt, maakt het van een geslaagde aanpak een herbruikbare skill: een geschreven beschrijving, gekoppeld aan code die de vaste stappen elke keer op dezelfde manier uitvoert ([Nous Research](https://nousresearch.com/press/hermes-enterprise-in-microsoft-teams)). De plugin Collective Wisdom neemt het moment voor zijn rekening waarop een skill de computer van één persoon verlaat. Hermes kan voorstellen dat een skill het delen waard is, maar de beslissing blijft bij de maker, die precies de bestanden bekijkt die in de bibliotheek van het team worden gepubliceerd. Collega's installeren vervolgens één specifieke versie, niet hoe de skill er vandaag toevallig uitziet ([Collective Wisdom](https://github.com/NousResearch/hermes-collective-wisdom)). Het hoofdstuk over [altijd actieve bots](/book/28-persistent-bots) laat nog een manier zien waarop Hermes een skill oppikt: door stap voor stap door een taak geleid te worden.

Naast elkaar gelegd leren de twee voorbeelden dezelfde les. Een skill die zichzelf herschrijft, blijft een set instructies die een agent zal opvolgen, en verdient dus dezelfde zorg als een skill die met de hand is geschreven. Vraag om bewijs voordat er iets verandert, liefst uit meer dan één sessie. Houd een menselijk controlepunt overal waar een skill van één persoon naar anderen gaat. Bewaar versies, zodat een slechte wijziging teruggedraaid kan worden in plaats van dat je erover blijft discussiëren. En let op afdrijven: een skill die vaak genoeg wordt bijgewerkt, kan langzaam overhellen naar de gewoonten van één persoon of naar één slechte sessie, tot hij eerder een voorbijgaande stemming beschrijft dan het werk zelf.

Hoe hoog je de lat legt, hangt af van wie de skill bereikt. Een persoonlijke skill, geleerd voor één gebruiker, mag snel bewegen, want een fout raakt alleen die gebruiker, en die kan hem ook het best opmerken. Een gedeelde of ingebouwde skill raakt iedereen die hem laadt. Ook Perplexity trekt deze grens: wijzigingen aan de ingebouwde skills die elke gebruiker krijgt, moeten gepaarde replaytests en een interne menselijke review doorstaan voordat ze in de officiële versie terechtkomen. Een team kan hetzelfde instinct overnemen: persoonlijke skills vrij laten leren en van gedeelde skills vragen dat ze elke wijziging verdienen.

Je hebt geen zelfverbeterend systeem nodig om deze lus uit te proberen. Je kunt hem ook met de hand doorlopen, zolang je de agent vraagt om voor te stellen in plaats van door te voeren:

## Skills delen en ontdekken

Skills zijn het meest waardevol wanneer ze gedeeld worden. Platformen zoals [prompts.chat](https://prompts.chat/skills) stellen je in staat om:

- **Ontdekken** - door de community gemaakte skills voor veelvoorkomende taken
- **Downloaden** - skills direct naar je projecten
- **Delen** - je eigen expertise als herbruikbare skills
- **Itereren** - op skills op basis van praktijkgebruik

Op dezelfde manier kun je ook grotere eenheden dan één skill delen: hele bots met hun instructies en routines, en teams van bots die werk aan elkaar overdragen, zoals in de catalogi [Bots](https://prompts.chat/bots) en [Teams](https://prompts.chat/bots/teams). Beide ideeën bekijken we in het hoofdstuk over [bots die altijd aan staan](/book/28-persistent-bots).

De agent biedt het uitvoeringsraamwerk—planning, toolgebruik en geheugen—terwijl skills domeinexpertise bieden. Deze scheiding betekent:

- **Skills zijn draagbaar** - Dezelfde skill werkt met verschillende agents
- **Agents zijn uitbreidbaar** - Voeg nieuwe capaciteiten toe door skills toe te voegen
- **Expertise is deelbaar** - Domeinexperts kunnen skills bijdragen zonder volledige agents te bouwen

## Best practices

### Voor het bouwen van skills

1. **Begin specifiek, generaliseer dan** - Bouw eerst een skill voor jouw exacte gebruikssituatie, maak dan abstract
2. **Neem faalgevallen op** - Documenteer wat de skill niet kan en hoe daarmee om te gaan
3. **Versiebeheer van je skills** - Houd wijzigingen bij zodat agents kunnen vertrouwen op stabiele versies
4. **Test met echte taken** - Valideer skills tegen daadwerkelijk werk, niet alleen theorie

### Voor het gebruiken van skills met agents

1. **Lees de skill eerst** - Begrijp wat een skill doet voordat je deze inzet
2. **Pas doordacht aan** - Overschrijf skill-standaarden alleen wanneer nodig
3. **Monitor prestaties** - Houd bij hoe goed skills presteren in jouw context
4. **Draag verbeteringen bij** - Wanneer je een skill verbetert, overweeg dit terug te delen

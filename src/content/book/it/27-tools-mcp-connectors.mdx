Chiedi a un agente di trovare i bug aperti nel tuo progetto e preparare una bozza di issue di follow-up. Per farlo, non bastano buone istruzioni. Gli serve un modo per accedere al sistema di gestione delle issue, leggere i dati giusti ed eventualmente creare qualcosa al suo interno.

Qui entrano in gioco **strumenti**, **connettori** e **MCP**. Sono collegati, ma descrivono parti diverse della configurazione.

Uno strumento può anche funzionare localmente. Una calcolatrice non richiede la connessione a un account. Uno strumento per leggere file può funzionare interamente sul tuo computer. Un servizio esterno è solo una possibile fonte di strumenti.

## Cosa contiene davvero uno strumento

Uno strumento ha di solito un **nome**, una **descrizione**, uno **schema di input** e un'implementazione che svolge il lavoro. La descrizione aiuta il modello a decidere quando usarlo. Lo schema descrive gli argomenti che accetta.

Ecco una piccola definizione di uno strumento MCP immaginario:

<Collapsible title="Esamina la definizione di search_issues">

```json
{
  "name": "search_issues",
  "description": "Cerca issue nel progetto collegato. Questo strumento legge solo dati.",
  "inputSchema": {
    "type": "object",
    "properties": {
      "query": { "type": "string" },
      "limit": { "type": "integer", "minimum": 1, "maximum": 20 }
    },
    "required": ["query"],
    "additionalProperties": false
  }
}
```

</Collapsible>

Il modello potrebbe richiedere `search_issues` con `{"query": "bug aperti", "limit": 3}`. L'applicazione inoltra la richiesta all'implementazione. Questa interroga il gestore e restituisce risultati o un errore.

Il nome e lo schema non eseguono nulla da soli. L'implementazione deve convalidare gli input, verificare l'accesso ed eseguire l'operazione. La risposta dello strumento è anche distinta dalla risposta finale del modello: può contenere ID e titoli delle issue che il modello poi riassume. La [specifica degli strumenti MCP](https://modelcontextprotocol.io/specification/latest/server/tools) descrive come gli strumenti rendono disponibili queste operazioni.

<Callout type="info" title="Una richiesta non è un risultato">
«Creerò una issue» è un'affermazione. Una chiamata a uno strumento richiede l'operazione. Una risposta riuscita con l'ID della nuova issue è una prova che l'operazione è avvenuta. Tieni separate queste tre cose.
</Callout>

## Cosa aggiunge un connettore

Un connettore raccoglie l'integrazione con un sistema specifico. Può gestire l'accesso, la scelta di un account o di uno spazio di lavoro, la ricerca di dati e la disponibilità delle azioni supportate come strumenti. Alcuni connettori consentono solo di cercare o leggere. Altri supportano anche la scrittura.

**Connettore è un termine di prodotto, non uno standard tecnico universale.** Un connettore può chiamare direttamente l'API di un servizio. Un altro può usare un server MCP. Un terzo può cercare in un indice costruito da documenti sincronizzati. Controlla cosa supporta l'integrazione specifica. La [panoramica dei connettori di Microsoft](https://learn.microsoft.com/en-us/azure/connectors/introduction) offre un esempio di integrazioni basate su API.

Collegare un account non significa che l'agente veda ogni file, carichi tutti i tuoi dati nel contesto o abbia il permesso di eseguire ogni azione. L'accesso dipende dall'account, dagli ambiti configurati, dall'applicazione e dai permessi del servizio. I risultati di ricerca possono anche riflettere un indice meno recente dei documenti originali.

Per il gestore di issue, tieni separate queste domande: è configurata una connessione? A quale progetto può accedere? Può solo leggere o anche creare issue?

## Cosa standardizza MCP

**MCP** sta per **Model Context Protocol**. Definisce un modo comune di comunicare tra applicazioni IA e fornitori di capacità esterne. Non sostituisce l'API di un servizio; un server MCP può usare quell'API dietro le quinte.

L'[architettura MCP](https://modelcontextprotocol.io/docs/learn/architecture) ha tre ruoli principali:

<InfoGrid columns={3} items={[
  { label: "Host", description: "L'applicazione IA in cui lavora l'utente. Coordina connessioni, interazioni con il modello e permessi.", color: "blue" },
  { label: "Client", description: "La parte all'interno dell'host che mantiene una connessione con un server MCP.", color: "green" },
  { label: "Server", description: "Un programma che rende disponibili strumenti, risorse o prompt tramite MCP. Può funzionare localmente o da remoto.", color: "amber" }
]} />

Per una chiamata a uno strumento, il client può scoprire gli strumenti del server con `tools/list`. L'applicazione rende disponibili al modello le definizioni degli strumenti pertinenti. Se il modello ne richiede uno, l'applicazione può inviare una richiesta `tools/call` tramite il proprio client MCP. Il server esegue o delega l'operazione e restituisce il risultato.

Il modello non deve aprire una connessione di rete da solo. L'applicazione e l'implementazione MCP gestiscono la comunicazione. La compatibilità resta importante: host e server devono supportare le capacità che vuoi usare. Scoprire uno strumento non garantisce il permesso di eseguirlo; i controlli di accesso si applicano comunque.

### MCP offre più degli strumenti

MCP definisce anche **risorse** e **prompt**. Queste parole hanno significati specifici nel protocollo:

<InfoGrid columns={3} items={[
  { label: "Strumenti", description: "Operazioni che il modello può richiedere, soggette ai controlli dell'applicazione. Esempio: cercare issue.", color: "blue" },
  { label: "Risorse", description: "Dati che l'applicazione può rendere disponibili come contesto. Esempio: una guida al progetto identificata da un URI.", color: "green" },
  { label: "Prompt", description: "Modelli di messaggi riutilizzabili che gli utenti possono selezionare, con argomenti facoltativi. Esempio: preparare un rapporto di classificazione delle issue.", color: "amber" }
]} />

La [guida ai concetti del server MCP](https://modelcontextprotocol.io/docs/learn/server-concepts) li descrive come strumenti controllati dal modello, risorse controllate dall'applicazione e prompt controllati dall'utente. Questi termini descrivono i modi di interazione previsti. Non eliminano i controlli dei permessi dell'applicazione.

Un modello di prompt MCP non è automaticamente una skill. Una skill può raccogliere una procedura più lunga, riferimenti e script. Può spiegare all'agente come usare strumenti forniti tramite MCP, un connettore diretto o funzioni locali.

### Le skill possono arrivare anche dal server

Fino a poco tempo fa, questi due pezzi arrivavano di solito separati. Un server poteva dare all'agente i suoi strumenti, ma il saper fare necessario per usarli bene stava altrove: in una skill installata a parte, in un README o nel prompt dell'utente. Quando il servizio cambiava, quelle istruzioni potevano restare indietro senza che nessuno se ne accorgesse.

L'**estensione Skills** ufficiale di MCP, diventata definitiva a settembre 2026, colma buona parte di questa distanza. Ora un server può offrire non solo i suoi strumenti, ma anche le skill che spiegano come usarli, scritte nello stesso formato `SKILL.md` descritto in [Agenti e Skill](/book/25-agents-and-skills). Gli strumenti dicono all'agente che cosa può fare. Le skill gli dicono come fare bene il lavoro. Adesso entrambi possono arrivare dallo stesso server: le istruzioni vivono accanto al servizio che descrivono e chi lo mantiene può tenerle aggiornate.

Il meccanismo si basa su elementi che conosci già. Ogni file di una skill è esposto come risorsa MCP, di solito con un URI `skill://`. Un client può elencare le skill di un server con `skills/list`, recuperarne una con `skills/get` e leggerne i file di supporto con `resources/read`.

<Compare
  before={{ label: "Un server con soli strumenti", content: "Il server del tracker espone search_issues e create_issue. Il metodo di classificazione (cercare duplicati, seguire il modello di issue) deve arrivare da una skill installata a parte o dal tuo prompt, e può diventare obsoleto quando il servizio cambia." }}
  after={{ label: "Un server che include anche una skill", content: "Lo stesso server offre anche una skill per classificare le issue. All'inizio l'host vede solo il suo nome e la sua descrizione, e carica le istruzioni complete solo quando un'attività ne ha bisogno. Quando i manutentori cambiano il servizio, possono aggiornare la skill insieme a esso." }}
/>

È sempre l'host a decidere come una skill arriva al modello. Il modello può sceglierla in base al nome e alla descrizione, oppure l'utente può selezionarla direttamente. In entrambi i casi le istruzioni complete entrano nel contesto solo quando servono, e leggere un file `SKILL.md` non basta ad attivare la skill.

<Callout type="warning" title="Una skill fornita da un server resta un'istruzione">
Una skill che arriva da un server è testo che entra nel contesto dell'agente e può orientare ciò che farà dopo. Merita quindi lo stesso esame del server stesso. Un host attento verifica il contenuto e chiede ogni approvazione necessaria prima di caricarlo. Come altre estensioni ufficiali di MCP, per esempio MCP Apps e MCP Tasks, Skills è facoltativa: viene usata solo quando sia il client sia il server dichiarano di supportarla. Il supporto nei client è ancora agli inizi, quindi verifica che la tua applicazione carichi davvero skill dai server prima di farci affidamento.
</Callout>

## Dare istruzioni a un agente con strumenti

Spiega all'agente quali informazioni cercare, come usarle e quali azioni ti aspetti. Non dare per scontato che esista una connessione o che uno strumento supporti tutte le operazioni del servizio.

<Compare
  before={{ label: "Troppe cose da indovinare", content: "Controlla i bug e sistema tutto." }}
  after={{ label: "Risultato e limiti chiari", content: "Cerca nel progetto collegato i bug aperti sui risultati di ricerca vuoti. Riassumi le issue pertinenti e includi i loro ID. Prepara una bozza di issue di follow-up se serve, ma chiedi prima di crearla. Se la connessione o lo strumento necessario non sono disponibili, spiega cosa manca. Non affermare che una issue è stata creata senza un risultato riuscito dello strumento." }}
/>

Una skill riutilizzabile di classificazione potrebbe aggiungere il metodo: cercare duplicati, confrontare i passaggi per riprodurre il problema, seguire il modello di issue del progetto e riportare le domande irrisolte. Lo strumento fornisce l'operazione. La skill spiega come usarla bene.

L'output degli strumenti richiede comunque giudizio. Un commento a una issue, un documento o un risultato di ricerca può contenere errori o testo che sembra un'istruzione. Tratta il contenuto recuperato come dati, senza permettergli di cambiare la richiesta dell'utente o le regole dell'applicazione. Il solo supporto a MCP non rende affidabile un server o il suo contenuto.

Se una lettura fallisce, l'agente può segnalare l'errore o provare un'alternativa ragionevole. Se una scrittura va in timeout, dovrebbe controllare se la modifica è avvenuta prima di ripeterla. Altrimenti, un nuovo tentativo potrebbe creare una issue duplicata. Le credenziali appartengono alla configurazione della connessione dell'integrazione, non al prompt dell'attività. Queste regole contano ancora di più quando un bot usa strumenti secondo una pianificazione mentre sei via, come descritto in [Bot sempre attivi](/book/28-persistent-bots).

## ما هي وكلاء الذكاء الاصطناعي؟

**وكيل الذكاء الاصطناعي** هو نظام ذكاء اصطناعي يمكنه التخطيط والتنفيذ والتكرار على المهام بشكل مستقل. على عكس التفاعلات البسيطة للتعليمة والاستجابة، يمكن للوكلاء:

- **التخطيط** - تقسيم الأهداف المعقدة إلى خطوات قابلة للتنفيذ
- **التنفيذ** - استخدام الأدوات واتخاذ إجراءات في العالم الحقيقي
- **الملاحظة** - معالجة التغذية الراجعة من إجراءاتهم
- **التكيف** - تعديل نهجهم بناءً على النتائج
- **الاستمرارية** - الحفاظ على السياق والذاكرة عبر التفاعلات

### تعليمات النظام (هوية الوكيل)

التعليمة التأسيسية التي تحدد من هو الوكيل وكيف يتصرف:

```markdown
You are a code review assistant. Your role is to:
- Analyze code for bugs, security issues, and performance problems
- Suggest improvements following best practices
- Explain your reasoning clearly
- Be constructive and educational in feedback

You have access to tools for reading files, searching code, and running tests.
```

### تعليمات التخطيط (كيفية التفكير)

التعليمات التي توجه عملية التفكير والتخطيط لدى الوكيل:

```markdown
Before taking action, always:
1. Understand the complete request
2. Break it into smaller, verifiable steps
3. Identify which tools you'll need
4. Consider edge cases and potential issues
5. Execute step by step, validating as you go
```

### تعليمات استخدام الأدوات (كيفية التصرف)

التوجيهات حول متى وكيف يتم استخدام الأدوات المتاحة:

```markdown
When you need to understand a codebase:
- Use grep_search for finding specific patterns
- Use read_file to examine file contents
- Use list_dir to explore directory structure
- Always verify your understanding before making changes
```

### تعليمات التعافي (كيفية التعامل مع الفشل)

التعليمات عندما تسوء الأمور:

```markdown
If an action fails:
1. Analyze the error message carefully
2. Consider alternative approaches
3. Ask for clarification if the task is ambiguous
4. Never repeat the same failed action without changes
```

## ما هي المهارات؟

إذا كانت التعليمات هي الذرات، فإن **المهارات هي الجزيئات** — لبنات بناء قابلة لإعادة الاستخدام تمنح الوكلاء قدرات محددة.

**المهارة** هي حزمة شاملة ومحمولة من التعليمات التي تمنح وكيل الذكاء الاصطناعي خبرة في مجال أو مهمة معينة. المهارات هي الكتل القابلة لإعادة الاستخدام للوكلاء: تبنيها مرة واحدة، ويمكن لأي وكيل استخدامها.

<Callout type="tip" title="المهارات = كتل وكلاء قابلة لإعادة الاستخدام">
اكتب مهارة لمراجعة الكود مرة واحدة. الآن يمكن لكل وكيل برمجة — سواء كان لـ Python أو JavaScript أو Rust — أن يصبح فوراً خبيراً في مراجعة الكود عن طريق تحميل تلك المهارة. تتيح لك المهارات بناء قدرات الوكلاء مثل مكعبات LEGO.
</Callout>

## بناء مهارات فعالة

### 1. حدد الخبرة بوضوح

ابدأ بوصف واضح لما تمكّنه المهارة:

```markdown
---
name: api-design
description: Design RESTful APIs following industry best practices, 
  including versioning, error handling, and documentation standards
---
```

### 2. نظّم المعرفة بشكل هرمي

نظّم المعلومات من العام إلى الخاص:

```markdown
# API Design Skill

## Core Principles
- Resources should be nouns, not verbs
- Use HTTP methods semantically
- Version your APIs from day one

## Detailed Guidelines
[More specific rules...]

## Reference Materials
- See `rest-conventions.md` for naming conventions
- See `error-codes.md` for standard error responses
```

### 3. أدرج أمثلة ملموسة

تصبح القواعد المجردة واضحة مع الأمثلة:

```markdown
## Endpoint Naming

✅ Good:
- GET /users/{id}
- POST /orders
- DELETE /products/{id}/reviews/{reviewId}

❌ Avoid:
- GET /getUser
- POST /createNewOrder
- DELETE /removeProductReview
```

### 4. قدم أطر اتخاذ القرار

ساعد الوكيل على اتخاذ الخيارات في المواقف الغامضة:

```markdown
## When to Use Pagination

Use pagination when:
- Collection could exceed 100 items
- Response size impacts performance
- Client may not need all items

Use full response when:
- Collection is always small (<20 items)
- Client typically needs everything
- Real-time consistency is critical
```

### 5. أضف أنماط التعافي

توقع ما يمكن أن يسوء:

```markdown
## Common Issues

**Problem**: Client needs fields not in standard response
**Solution**: Implement field selection: GET /users?fields=id,name,email

**Problem**: Breaking changes needed
**Solution**: Create new version, deprecate old with timeline
```

عند تركيب المهارات، تأكد من أنها لا تتعارض. يجب أن تكون المهارات:

- **نمطية** - كل مهارة تتعامل مع مجال واحد بشكل جيد
- **متوافقة** - يجب ألا تعطي المهارات تعليمات متناقضة
- **مرتبة حسب الأولوية** - عندما تتداخل المهارات، حدد أيها تأخذ الأسبقية

## حين تتعلم المهارات من التجربة

كل مهارة رأيناها في هذا الفصل حتى الآن كتبها إنسان. يلاحظ أحدهم أن مهمة ما تتكرر مرة بعد مرة، فيجلس ويصوغ طريقة إنجازها في كلمات. لكن الوكيل الذي يعمل معك يوماً بعد يوم يحتفظ أيضاً، في هدوء، بسجلّ لما جرى في ذلك العمل: أي التعليمات اتبع، وأين اضطررت إلى التدخل لتصحيحه، وأي الخطوات أعادها مرتين. ويستثمر نمط أحدث هذا السجل. فبدلاً من انتظار أن يكتب أحدٌ المهارة، يعود نظام الوكيل نفسه إلى تجربته ويصوغ مهارات جديدة أو يراجع القديمة من تلقاء نفسه. يمكنك أن تتصور ذلك حلقةً تشبه كثيراً حلقة الوكيل في مطلع هذا الفصل، غير أنها أبطأ وموجّهة نحو الداخل:

تصف Perplexity هذه الحلقة بالتفصيل في **Brain**، نظام الذاكرة الذي يحسّن نفسه بنفسه ويقف خلف وكيلها Computer ([What is Brain?](https://www.perplexity.ai/help-center/en/articles/19700001-what-is-brain)). وفي مقال نُشر في نوفمبر 2026 ([Self-improving skills](https://www.perplexity.ai/hub/blog/self-improving-skills))، تشرح الشركة كيف يستند Brain إلى ذاكرة المستخدم وسجل جلساته ليكتب مهارات *شخصية* ويصقلها. ففي مرحلة الأدلة، يبحث عن الجلسات السابقة التي استُخدمت فيها مهارة ما، ولا سيما تلك التي قصّرت فيها. وفي مرحلة التأمل، يدرس وكيلُ تحسينٍ تلك الجلسات ويقترح تعديلات. ثم يتأكد التحقق من أن الاقتراح سليم البنية ومن المرجح أن يحسّن النتائج، ويطبّقه التفعيل، فتصير الجلسات التالية أدلةً للجولة التي بعدها. وما يجعل هذه الحلقة جديرة بالثقة هو التحفّظ المبني فيها. فإنشاء مهارة جديدة يتطلب ظهور السلوك نفسه القابل لإعادة الاستخدام مرتين مستقلتين، بينما قد يكفي لتحديث مهارة قائمة حدوثٌ واحد له أساس واضح. ولا يعدّل وكيل التحسين أي مهارة مباشرة أبداً: بل يكتب اقتراحاً يضم تعليله وأدلته، ولا يُجري أكثر من تعديل واحد لكل مهارة في كل تشغيل، ويمتنع عن الاقتراح حين لا تسند الأدلة أي تغيير. كما أن المهارات المنشأة تلقائياً محدودة بعشر لكل مستخدم، فلا تدخل مهارة جديدة إلا إذا خرجت قديمة، مع تبرير لهذا الاستبدال.

أما **Hermes Agent** من Nous Research فيتناول الفكرة نفسها من زاوية الفريق. فكلما أوكل إليه شخصٌ عملاً متكرراً، حوّل Hermes النهج الناجح إلى مهارة قابلة لإعادة الاستخدام: تعريف مكتوب يرافقه كود ينفّذ الخطوات الثابتة بالطريقة نفسها في كل مرة ([Nous Research](https://nousresearch.com/press/hermes-enterprise-in-microsoft-teams)). وتتولى إضافة Collective Wisdom اللحظة التي تغادر فيها المهارة جهاز شخص واحد. قد يقترح Hermes أن مهارة ما تستحق المشاركة، لكن القرار يبقى بيد كاتبها، الذي يراجع بدقة الملفات نفسها التي ستُنشر في مكتبة الفريق. ثم يثبّت الزملاء نسخة محددة بعينها، لا ما تبدو عليه المهارة اليوم مصادفةً ([Collective Wisdom](https://github.com/NousResearch/hermes-collective-wisdom)). ويعرض فصل [البوتات الدائمة العمل](/book/28-persistent-bots) طريقة أخرى يكتسب بها Hermes مهارة: حين يُقاد خطوة بخطوة عبر مهمة.

إذا وضعنا المثالين جنباً إلى جنب، خرجنا بالدرس نفسه. فالمهارة التي تعيد كتابة نفسها تبقى مجموعة تعليمات سيتّبعها وكيل، ولذلك تستحق العناية نفسها التي تستحقها مهارة كُتبت باليد. اطلب أدلة قبل أي تعديل، ويُفضّل أن تأتي من أكثر من جلسة. واحرص على وجود نقطة مراجعة بشرية في كل موضع تنتقل فيه مهارة من شخص إلى آخرين. واحتفظ بالنسخ، كي يمكن التراجع عن تعديل سيئ بدلاً من الجدال حوله. وانتبه إلى الانجراف: فالمهارة التي تُراجَع بما يكفي من التكرار قد تميل شيئاً فشيئاً نحو عادات شخص واحد أو نحو جلسة سيئة واحدة، حتى تصير تصف مزاجاً عابراً أكثر مما تصف العمل نفسه.

أما مدى ارتفاع المعيار فيتوقف على من تصل إليه المهارة. فالمهارة الشخصية، التي تعلّمها النظام لمستخدم واحد، تستطيع أن تتحرك بسرعة، لأن الخطأ لا يمسّ إلا ذلك المستخدم، وهو الأقدر على ملاحظته. أما المهارة المشتركة أو المدمجة فتؤثر في كل من يحمّلها. وتضع Perplexity هذا الحد أيضاً: فالتعديلات على المهارات المدمجة التي يحصل عليها كل مستخدم يجب أن تجتاز اختبارات إعادة تشغيل مزدوجة ومراجعة بشرية داخلية قبل أن تصل إلى النسخة المعتمدة. ويمكن للفريق أن يتبنى الحسّ نفسه: أن يترك المهارات الشخصية تتعلم بحرية، وأن يطالب المهارات المشتركة بأن تستحق كل تعديل.

لا تحتاج إلى نظام يحسّن نفسه بنفسه لتجرّب هذه الحلقة. يمكنك أن تمرّ بها يدوياً، ما دمت تطلب من الوكيل أن يقترح لا أن يطبّق:

## مشاركة واكتشاف المهارات

تكون المهارات أكثر قيمة عند مشاركتها. تتيح لك منصات مثل [prompts.chat](https://prompts.chat/skills):

- **اكتشاف** مهارات أنشأها المجتمع للمهام الشائعة
- **تنزيل** المهارات مباشرة إلى مشاريعك
- **مشاركة** خبرتك الخاصة كمهارات قابلة لإعادة الاستخدام
- **التكرار** على المهارات بناءً على الاستخدام الفعلي

ويمكن مشاركة وحدات أكبر من المهارة الواحدة بالطريقة نفسها: بوتات كاملة بتعليماتها ومهامها الروتينية، وفرق من البوتات يسلّم بعضها العمل لبعض، كما في كتالوجَي [Bots](https://prompts.chat/bots) و[Teams](https://prompts.chat/bots/teams). نتناول الفكرتين في فصل [البوتات الدائمة](/book/28-persistent-bots).

<Callout type="tip" title="ابدأ بمهارات المجتمع">
قبل بناء مهارة من الصفر، تحقق مما إذا كان شخص ما قد حل مشكلتك بالفعل. مهارات المجتمع مختبرة وغالباً ما تكون أفضل من البدء من الصفر.
</Callout>

يوفر الوكيل إطار التنفيذ — التخطيط واستخدام الأدوات والذاكرة — بينما توفر المهارات خبرة المجال. هذا الفصل يعني:

- **المهارات قابلة للنقل** - نفس المهارة تعمل مع وكلاء مختلفين
- **الوكلاء قابلة للتوسيع** - أضف قدرات جديدة بإضافة مهارات
- **الخبرة قابلة للمشاركة** - يمكن لخبراء المجال المساهمة بالمهارات دون بناء وكلاء كاملين

## أفضل الممارسات

### لبناء المهارات

1. **ابدأ محدداً، ثم عمّم** - ابنِ مهارة لحالة استخدامك الدقيقة أولاً، ثم جردها
2. **أدرج حالات الفشل** - وثّق ما لا تستطيع المهارة فعله وكيفية التعامل معه
3. **أنشئ إصدارات لمهاراتك** - تتبع التغييرات حتى يتمكن الوكلاء من الاعتماد على إصدارات مستقرة
4. **اختبر مع مهام حقيقية** - تحقق من صحة المهارات مقابل العمل الفعلي، وليس النظرية فقط

### لاستخدام المهارات مع الوكلاء

1. **اقرأ المهارة أولاً** - افهم ما تفعله المهارة قبل نشرها
2. **خصص بعناية** - تجاوز الإعدادات الافتراضية للمهارة فقط عند الضرورة
3. **راقب الأداء** - تتبع مدى جودة أداء المهارات في سياقك
4. **ساهم بالتحسينات** - عندما تحسن مهارة، فكر في مشاركتها مرة أخرى

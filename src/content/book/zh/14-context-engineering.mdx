理解上下文对于构建真正有效的 AI 应用程序至关重要。本章涵盖了你需要了解的关于在正确时间为 AI 提供正确信息的所有内容。

<Callout type="info" title="为什么上下文很重要">
AI 模型是无状态的。它们不会记住过去的对话。每次发送消息时，你都需要包含 AI 需要知道的所有信息。这就是所谓的"上下文工程"。
</Callout>

## 什么是上下文？

上下文是你在提问时一并提供给 AI 的所有信息。可以这样理解：

## AI 是无状态的

<Callout type="warning" title="重要概念">
AI 不会在对话之间记住任何东西。模型每次处理 API 调用时，记忆都是一片空白。如果你想让 AI "记住"某些内容，它就必须每次都出现在上下文里，而且总得有人把它放进去。这个人通常就是你的应用，哪怕服务商会替你把对话暂存一段时间。
</Callout>

这就是为什么聊天机器人通常会在每条消息中发送你的整个对话历史。不是 AI 记住了，而是应用程序重新发送了所有内容。

<TryIt compact prompt={`假设这是一个没有历史记录的新对话。

我刚才问了你什么？`} />

AI 会说它不知道，因为它确实无法访问任何先前的上下文。

### 谁来携带对话历史？

很长一段时间里，故事到这里就讲完了：每个请求都要带上整段对话，从第一声问候一直到最新的问题。不过最近，有几家模型 API 提供了一种更省力的方式。服务商可以把对话在自己的服务器上保留一段时间。你的应用第一次把请求完整发过去，之后只需发送新消息，再附上一个指向上一次回复的小标记。在另一端，服务商会在模型读取之前，把这些片段重新拼接成完整的对话。

值得把变化说清楚。模型依然是无状态的。它自己什么也不记得，每一轮仍会把整个上下文从头到尾重新读一遍。改变的是由谁来携带历史：这副担子如今有一部分由服务商来挑，而不再全压在你的应用身上。所以上下文窗口填满的速度不变，token 也照样计算。收获主要在速度和更轻的流量上：通过网络传输的数据更少，回答的第一个字出现前的等待也更短。对长时间运行的智能体来说，这一点最为明显，比如不断累积工具结果的编程助手、一张接一张截屏的计算机操作智能体，以及满是文档和图片的工作流。

你会以不同的名字遇到这个想法。Anthropic 的 Messages API 把它叫作 **message threads**（消息线程），在撰写本文时处于公开测试阶段：第一个请求创建一个线程，之后的每个请求都从上一次回复的 id 接着往下走，只发送新消息。Anthropic 表示，对于五十万 token 及以上的超大请求，等到第一个 token 的中位时间缩短了约 35%。在 OpenAI 的 Responses API 中，你可以用 `previous_response_id` 把新一轮接到之前的回复上；Google 的 Gemini Interactions API 则用 `previous_interaction_id` 做着几乎相同的事。各家的细节并不相同，所以在依赖其中任何一种之前，请先查阅最新的文档。

<Callout type="warning" title="借来的线程">
保存在服务器上的对话只是一种便利，而不是档案。它可能会过期：Anthropic 的消息线程在大约五分钟没有请求后就会失效；其他服务商也只会在有限的时间内保留已存储的回复，如果你关闭存储，就根本不会保留。线程一旦消失，就必须重新发送完整的对话。因此，你的应用，或者包裹着智能体的运行框架（harness），应当始终保留一份自己的历史副本，并随时准备重新发送。至于你希望 AI 记住几天甚至几周的内容，仍然是你自己的事：可以像下文“摘要”一节介绍的那样做成摘要，也可以像[常驻机器人：持续工作的智能体](/book/28-persistent-bots)一章中的机器人那样，把它存为长期记忆。
</Callout>

## RAG：检索增强生成

RAG 是一种让 AI 访问其训练数据之外知识的技术。与其试图将所有内容都放入 AI 的训练中，你可以：

1. **存储** 你的文档到可搜索的数据库中
2. **搜索** 用户提问时的相关文档
3. **检索** 最相关的片段
4. **增强** 你的提示词，加入这些片段
5. **生成** 使用该上下文的答案

## Embeddings：搜索的工作原理

RAG 如何知道哪些文档是"相关的"？它使用 **embeddings**——一种将文本转换为能捕获含义的数字的方法。

### 什么是 Embeddings？

Embedding 是一个表示文本含义的数字列表（"向量"）。相似的含义 = 相似的数字。

### 语义搜索

使用 embeddings，你可以按含义搜索，而不仅仅是关键词：

## Function Calling / Tool Use

Function calling 让 AI 可以使用外部工具——比如搜索网络、查询数据库或调用 API。

<Callout type="tip" title="也被称为">
不同的 AI 提供商对此有不同的叫法："function calling"（OpenAI）、"tool use"（Anthropic/Claude）或 "tools"（通用术语）。它们都是同一个意思。
</Callout>

### 工作原理

1. 你告诉 AI 有哪些工具可用
2. AI 决定是否需要工具来回答
3. AI 输出对工具的结构化请求
4. 你的代码运行工具并返回结果
5. AI 使用结果形成答案

## MCP：模型上下文协议

MCP（Model Context Protocol）是一种将 AI 连接到外部数据和工具的标准方式。MCP 提供了一个通用接口，而不是为每个 AI 提供商构建自定义集成。

### 为什么使用 MCP？

<InfoGrid columns={2} items={[
  { label: "没有 MCP", description: "为 ChatGPT、Claude、Gemini 分别构建集成... 维护多个代码库。API 变化时会出问题。", color: "red" },
  { label: "有 MCP", description: "构建一次，到处可用。标准协议。AI 可以自动发现和使用你的工具。", color: "green" },
]} />

### MCP 提供

- **Resources**：AI 可以读取的数据（文件、数据库记录、API 响应）
- **Tools**：AI 可以执行的操作（搜索、创建、更新、删除）
- **Prompts**：预构建的提示模板

## 总结

上下文工程是关于为 AI 提供正确的信息：

- **AI 是无状态的** - 模型什么都不记得，所以它需要的一切每次都必须出现在上下文中，即使服务商会替你短暂保存对话
- **RAG** 检索相关文档来增强提示词
- **Embeddings** 实现语义搜索（按含义，而非仅关键词）
- **Function calling** 让 AI 可以使用外部工具
- **摘要** 管理长对话
- **MCP** 标准化 AI 连接数据和工具的方式

<Callout type="tip" title="记住">
AI 输出的质量取决于你提供的上下文质量。更好的上下文 = 更好的答案。
</Callout>

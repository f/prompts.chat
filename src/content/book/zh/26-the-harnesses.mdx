你让 AI 修复一个 bug。它读取项目、编辑文件、运行测试，看到失败后再试一次。模型是这个过程的一部分。但还需要有东西负责打开文件、执行命令，再把结果带回来。

这套外围软件就是**运行框架（harness）**。了解了智能体和技能后，我们再来看看让它们协同工作的系统。

## 什么是 Harness？

**智能体运行框架（agent harness）**是运行 AI 智能体的软件。它准备模型的上下文，提供可用工具，处理工具请求，并管理任务的各个步骤。根据应用的不同，它还可以管理权限、已保存的进度、重试和各种限制。

人们有时会比较宽泛地使用*智能体*、*框架*和 *harness* 这些词。在本章中，我们按下面的方式区分：

## 循环是如何工作的

假设任务是改善没有搜索结果时的页面。典型的循环如下：

1. **准备上下文。** 加入用户请求、项目指令、相关技能指令和可用工具的定义。
2. **调用模型。** 模型可能直接回答，也可能请求使用工具，比如读取搜索组件。
3. **检查并执行。** 在工具运行前，harness 验证请求并检查权限。
4. **返回观察结果。** 文件内容、命令输出或错误信息会回到模型的上下文中。
5. **继续或停止。** 模型根据这些证据决定下一步。harness 也会执行限制，并且可以暂停以等待用户输入。

在回复里写“运行测试”不会真的执行任何操作。必须有实际的工具执行命令，并把结果返回。这样的反馈让智能体可以根据实际发生的情况作出反应。可以参考 Anthropic 对[智能体工作流的介绍](https://www.anthropic.com/engineering/building-effective-agents)。

## 当模型自己编写循环

上面的循环有一种稳定的节奏：模型请求一个工具，运行框架执行它，结果再加入模型的上下文。只有几步时，这样做很好。但如果任务要处理几百个文件，每一步都会变成又一次完整的模型请求，上下文也会被那些模型只看过一次的输出塞满。

有些运行框架提供了另一种方式：模型不再逐个请求工具，而是写一个小程序，由程序自己调用这些工具。程序在沙箱中运行，文件、日志、搜索结果等原始数据都留在程序的变量里，回到模型那里的只有程序打印出来的内容。这种做法叫作**程序化工具调用**（programmatic tool calling），它源自 [CodeAct](https://arxiv.org/abs/2402.01030)（Wang 等，2024）等研究。

  after={{ label: "一个调用工具的程序", content: "搜索整个项目，读取每个匹配的文件，留下仍在使用旧 API 的文件，然后打印一份简短的列表。运行框架执行程序，只把这份列表返回给模型。" }}
/>

上下文会更干净，因为模型面对的是一份摘要。模型请求会更少，因为指令和历史不必每隔几次调用就重新发送一遍。循环和检查都在代码里运行，模型原本打算处理的情况也就不会悄无声息地漏掉。

Factory 在 2026 年 10 月 29 日发布的 [Droid 1.0](https://factory.com/news/frontier-harness) 中把这种方式设为默认。它的 Script 工具在沙箱里运行 JavaScript，一次模型请求就能完成数百次工具调用。互不依赖的调用会同时执行；耗时较长的脚本可以在后台运行，结束后再唤醒模型。Factory 把 CodeAct 视为这一思路的起点，并提到 Cloudflare 和 Anthropic 在 2025 年底把它带进了生产环境，Codex 又把它带进了编程智能体。在 Factory 自己举的例子里，修复一个失败的测试时，同样的 15 次工具调用只用了 5 次模型调用，而不是 10 次。这些是 Factory 针对自家运行框架公布的数据。

这种做法也有代价。沙箱本身没有文件、网络或系统访问权限，只能使用运行框架开放的工具。权限和审批仍然必须作用于程序调用的每一个工具。打印输出有长度上限。而且对人来说，读懂一段程序比看懂一串单独的步骤更难。

### 工作流：同一个思路，再往上一层

同样的做法也可以用在整个智能体上。在 Anthropic 的 [Claude Managed Agents](https://platform.claude.com/docs/en/managed-agents/workflow-runs)（测试版）和 [Claude Code](https://code.claude.com/docs/en/workflows) 中，智能体可以编写**工作流**（workflow）：一个让许多智能体分阶段工作的程序，它能把任务并行分发出去，把一个智能体的结果交给另一个，反复执行某一步直到通过审查，最后把返回的结果汇总起来。工作流在后台运行，主对话在此期间仍然可以自由使用。

使用子智能体时，每一步怎么走由智能体自己决定；在工作流里，则由程序决定。不过，什么时候启动工作流仍由智能体选择，所以你要在系统提示词或指令中引导这个选择。预算同样重要：一次运行里的每个智能体都会消耗 token。

### 为程序写提示词

当模型要规划一个程序时，你的提示词就成了这个程序的需求说明。把整件事讲清楚：要覆盖哪些条目，每一条都必须通过哪些检查，某一条失败时怎么办，最终报告要包含什么。对于有风险的操作，请它先给你看一份程序摘要。

<TryIt compact prompt={`请用一个程序完成整项工作，而不是一步一步来。

任务：\${job:检查每个会修改数据的 API 路由是否都要求用户已登录}
范围：\${items:src/app/api 下的所有路由文件}
每一项都要检查：\${checks:路由在读取或写入任何内容之前都会验证会话}
某一项不通过时：\${failure:记录文件路径和原因，然后继续}
最终报告：\${report:未通过的路由、通过的数量，以及无法读取的文件}

在运行任何会修改文件的操作之前，先向我概述这个程序，并等待我的批准。`} />

并不是每个任务都需要程序。如果每一步都要根据上一步的结果来判断，一次调用一个工具往往更清楚。当工作量大、重复多、又容易检查时，程序才最能发挥作用。

### 旁观者清：从空白开始的审阅者

子智能体的上下文是空的，这一点通常被说成是节省空间的办法：嘈杂的工作在别处完成，回来的只有一份摘要。但它同样是 Harness 能提供的最好的审阅工具之一。一个在某个问题上耗了很长一段会话的智能体，会带着一路上做过的每一个假设。当它重读自己的计划时，会凭记忆把每个空缺补上，根本察觉不到那里原本有个空缺。而在全新上下文中启动的审阅者，手里只有文档和文档所指向的文件。作者知道却从没写下来的东西，都会以“看不懂”的形式暴露出来。纸面上的“看不懂”，修起来比代码里的便宜得多。

Google 开源的 [Elephant-Goldfish Model](https://github.com/google/elephant-goldfish-model)（EGM）插件于 [2026 年 10 月发布](https://opensource.googleblog.com/2026/10/introducing-elephant-goldfish-model-plugin.html)，正是围绕这种分工构建的。“大象”是一段长会话，掌握项目的上下文并起草规格说明，但不写一行代码。“金鱼”是没有记忆的子智能体，只能看到草稿以及草稿引用的源代码。权衡取舍、批准设计的是你。在任何批评开始之前，先要有一条金鱼用自己的话把计划复述一遍；如果它复述不出来，就说明文档有歧义，需要回去重写。其他审阅者各有分工，分别寻找边界情况、隐藏的依赖，以及实现者仍不得不独自拍板的地方。他们的意见按阻断、重要、细微分级，再送回大象那里。Google 表示，有数千名自家工程师在使用这个插件。它不是 Google 官方支持的产品，也没有公布任何准确率评测。

<Compare
  before={{ label: "作者重读自己的计划", content: "“投递失败时，以逐步拉长的间隔重试。”这句话看起来很完整，因为作者记得自己已经决定了最多重试几次，也决定了同一个事件到达两次时该怎么办。可这些都没有写在纸面上。" }}
  after={{ label: "新的审阅者只读文档", content: "“最多重试几次？最后一次也失败了怎么办？同一个事件到达两次，会投递两次吗？这两点我都只能靠猜。”作者凭记忆填上的空缺，变成了问题回到面前。" }}

这种做法并不属于某一个产品。Anthropic 的 [Claude Code 最佳实践指南](https://code.claude.com/docs/en/best-practices)把 `/code-review` 描述为在一个从未见过对话的全新子智能体中进行的审阅，因此它不会被产生这段代码的推理牵着走。指南划出的界线和本节一样：把任务交给子智能体，并不会让答案变得更好；但一个没见过你推理过程的审阅者，确实有帮助。指南还建议只给这样的审阅者只读工具，并让它跳过文风问题，因为被要求找问题的审阅者，总能找出点什么。开源 Harness [Code Copilot Team](https://github.com/gosha70/code-copilot-team) 则把审阅交给第二个模型：它在只读沙箱中检查改动，给出 PASS、FAIL 或 INCONCLUSIVE 的结论。被判为 FAIL 的阶段无法完成。

有两点提醒能让这个想法保持诚实。第一，在同一上下文里进行的审阅不是独立审阅，无论提示词把要求写得多么坚决。EGM 的 [Harness 指南](https://github.com/google/elephant-goldfish-model/blob/main/docs/harnesses.md)把“启动一个子智能体”对应到每个 Harness 自己的子智能体工具上；如果某个 Harness 没有这种工具，审阅就会停下来，而不是在作者的会话里悄悄继续。第二，全新的对话并不总等于空白的上下文，所以隔离必须去检查，而不能想当然。Harness 自动加载的指令文件，可能会跟着审阅者一起溜进来。[Issue #237](https://github.com/google/elephant-goldfish-model/issues/237) 报告说，Codex 和 Antigravity 中的 EGM 审阅者从未看到父级对话，却仍然收到了项目的 `AGENTS.md`。团队的假设，就这样被带进了本该质疑这些假设的审阅里。此外，每多一个审阅者，就多花一份 token 和时间。旁观者能看到作者已经看不见的东西，却替代不了测试，也替代不了你自己的判断。

想试一试，可以打开一个没有历史记录的新会话或子智能体，并只给它只读工具；这一点要在 Harness 的设置里限定，而不是在提示词里请求。然后把它指向文档本身，而不是产生这份文档的对话，这样问：

<TryIt compact prompt={`请像第一次看到这份计划的人那样阅读它。只使用这份文档和它提到的文件：\${document:docs/designs/webhook-delivery.md}

1. 用你自己的话把计划复述一遍：它要构建什么，各部分如何衔接，以及将如何验证。
2. 列出所有你不得不猜测的地方，以及你猜了什么。
3. 把每个空缺分为阻断、重要或细微，并说明作者应该补充什么。

不要评论文风，也不要修改任何文件。`} />

### 一个 Harness，多个模型

每一次调用由哪个模型来回答，是 Harness 决定的，而没有哪条规定说每次都必须是同一个模型。一项长任务里的各个步骤并不相同。有的需要判断力：选定思路，察觉计划已经跑偏，判断工作是否真的完成。有的则边界清楚、反复出现：读这几个文件，提取这几个字段，把这个模块移植过去并跑一遍测试。Harness 可以为每一步匹配最合适的模型，而这种做法会朝两个方向出现。

  { label: "向上求助", description: "由一个更快、更便宜的模型推进整个任务。遇到难关时，它向更强的模型请教。强模型读完此前的工作记录，自己不动用工具，只返回一份计划或一处纠正。", color: "purple" }
]} />

Meta 于 2026 年 11 月 9 日发布的 Muse Ember，就是为第一个方向打造的。Meta [介绍说](https://research.meta.ai/blog/muse-ember)，它面向“智能体整天重复的工作：工具调用、编程子任务、路由、信息提取和长文档解析”，并用一句话概括它与更大模型的搭配：“Muse Wonder 负责规划，Muse Ember 负责扛下工作量。”Meta 的[开发者文章](https://dev.meta.ai/resources/blog/build-with-muse-ember)用三步勾勒了一个编程流程。大模型规划一项横跨整个代码仓库的改动。每个 Ember 工作者领取一个边界清楚的子任务，有自己负责的文件、约束和检查方法。最后，大模型与开发者一起审阅合并后的结果。在 Cookbook 的示例里，16 个 Ember 智能体各自把语法高亮工具 Pygments 的一个词法分析器（lexer）从 Python 移植到 Rust，每个都在自己的一份仓库副本里工作；规划者只负责写任务说明，从头到尾没有亲自打开过源代码。Meta 指出，为每次调用挑选模型、在步骤之间传递上下文，都是 Harness 的事；而工作者如果发现了更大范围的依赖或含糊不清的需求，应当先把它交回给规划者，再继续往下做。据 Meta 报告，移植后的 16 个词法分析器在其测试中全部与 Python 原版结果一致；公司也提醒，结果每次运行都会有所不同。

Anthropic 的[顾问策略](https://claude.com/resources/articles/the-advisor-strategy)则反其道而行，Anthropic 自己也称之为常见模式的翻转：通常是一个编排者带着许多工作者。在这里，一个更快的模型担任执行者（例如 Sonnet 或 Haiku），从头到尾负责整个任务：调用工具，读取结果，继续推进。当它碰到一个自己难以合理做出的决定时，就去请教一个更强的模型，也就是顾问，比如 Opus。根据 [Claude Code 文档](https://code.claude.com/docs/en/advisor)，这种请教通常发生在确定思路之前、同一个错误反复出现时，以及宣布任务完成之前。顾问会收到完整的对话，包括每一次工具调用和每一个结果，然后返回一份计划、一处纠正，或者一个停下来的信号。正如 [API 文档](https://platform.claude.com/docs/en/agents-and-tools/tool-use/advisor-tool)所说，顾问自己从不调用工具，送到执行者手里的只有它的建议。这里没有一群工作者需要协调，更强的模型只在真正需要它的时刻出场。建议也不是命令。在 Claude Code 中，执行者通常会采纳建议，但如果某个文件或某个失败的步骤与建议相矛盾，它会把冲突明确指出来，而不是盲目照办。

两个方向都让提示词的分量更重，而不是更轻。向下委派时，任务说明就是工作者所知道的全部世界。Meta 列出了其中应当包含的内容：任务本身、相关上下文、工作者可以改动的文件、证明工作完成的检查方法，以及要交回什么。拿到一份含糊说明的小模型，没法借用规划者的判断力来填补空白；它只会去猜，而且猜得又快又多。向上求助时，什么时候求助，则由你的指令来决定。Anthropic 提到，如果系统提示词里没有引导，执行者在编程任务中请教顾问的次数往往太少，因此建议明确告诉它们什么时候该问。

这种分工最适合的情形，是工作能切成边界清楚的小块，而且每一块都能检查。如果每一步都取决于对上一步的判断，或者每一步反正都需要最强的模型，那么来回交接只会增加成本，也多出更多让上下文丢失的环节。省钱也并非板上钉钉。规划、合并以及每一次请教顾问都要消耗 token，而且 Anthropic 观察到，小模型自身的能力越接近顾问，收益就越小。最诚实的检验是你自己的工作：用同样的检查方法，把同样的任务分别交给小模型单独完成、两者搭配完成、大模型单独完成，再做比较。另外，选择由哪个模型来负责某一步，与让一个模型想得多深，是两个不同的旋钮；这一区别在[用 AI 开发软件](/book/28a-software-development-with-ai)一章的“推理强度不等于选模型”一节中有专门讨论。

想练习第一个方向，可以写一份规划者会交给某一个工作者的任务说明，然后站在这个工作者的角度重读一遍。一个能干但对项目一无所知的人，单凭这一页能把活干完吗？

<TryIt compact prompt={`你是参与一项更大改动的几个工作者之一。只完成下面这项任务。

任务：\${task:把发票模块里的日期格式化改为使用共享的 formatDate 辅助函数}
上下文：\${context:辅助函数已经在 src/lib/format.ts 中；其他工作者正在更新订单模块和报表模块}

## 为什么提示词在 Harness 中很重要

harness 为模型提供行动的方法。你的提示词说明什么样的行动才有用。如果目标不清楚，智能体可能花很多步骤去做你并不需要的工作。

当前请求只是指令的一部分。应用还可能提供系统提示词、项目指南、工具说明和已加载技能的指令。harness 决定如何把这些内容放入上下文；模型则遵循该系统采用的指令优先级。

<Compare
  before={{ label: "不清楚的任务", content: "修复搜索。让它更好用。" }}
  after={{ label: "智能体可以检查的任务", content: "当搜索没有匹配结果时，展示有帮助的空状态。不要改变匹配行为。遵循已有 UI 模式，新文案使用翻译。运行相关测试。报告修改了什么、哪些检查通过了，以及哪些内容无法验证。" }}
/>

你不需要说明每一次点击或每一条命令。定义结果、相关约束和完成标准即可。如果保留灵活性更有帮助，就让智能体选择常规步骤。

工具说明也是提示词设计的一部分。输入、输出和限制清楚的工具，更容易被模型正确使用。不断添加工具却不解释它们，可能造成混乱。

## 技能放在哪里

提示词通常描述当前任务。**技能**则记录你想跨任务复用的方法，比如如何审查变更、调查 bug 或准备报告。

在 [Agent Skills 格式](https://agentskills.io/specification)中，技能包含一个 `SKILL.md` 文件，也可以包含脚本、参考资料和资源。兼容的 harness 会让技能可以被发现。它可以先提供名称和描述，在相关时加载所选技能的指令，只在需要时读取支持文件。这叫做**渐进式披露**。

<Collapsible title="查看一个小型 bug 修复技能">

```markdown
---
name: verify-bug-fix
description: 在现有项目中修复可复现的 bug 时使用。
---

1. 阅读项目指令和相关代码。
2. 复现报告中的行为，或者解释为什么无法复现。
3. 进行能够解决原因的最小修改。
4. 运行相关检查，包括一个应当仍能正常工作的相近场景。
5. 报告修改、证据和仍不确定的部分。

如果需要的工具不可用，说明这个限制。
不要把没有运行的检查说成已经通过。
```

</Collapsible>

harness 仍然需要技能所预期的工具和环境。描述浏览器测试的技能不会安装浏览器。脚本可能需要依赖项。迁移到使用不同工具的 harness 时，指令可能需要调整。加载技能也不会训练模型，更不能保证专业能力。

今天特有的要求写进任务提示词。重复的流程放进技能。项目的共同规则放在 harness 支持的指令文件中。这样就不用在每次请求中复制一份很长、又略有不同的清单。

## 指令和权限承担不同职责

“不要编辑此项目以外的文件”是一条有用的指令。能够阻止这些写入的文件系统边界，则是强制执行的控制。可靠的配置会同时使用两者。

权限、沙箱和审批检查必须由 harness、其工具或底层环境实现。提示词本身无法强制执行这些限制。[VS Code 智能体安全文档](https://code.visualstudio.com/docs/agents/run/security)给出了具体示例。

对于工具返回的信息，这个区别也很重要。网页或代码仓库中的文件可能包含看起来像指令的文字。除非它来自可信的指令来源，否则应把它当作任务数据。只授予工作所需的访问权限。

每个智能体都运行在某个 harness 里，但总得有人来构建它、托管它，并让它持续运转。由谁来做这件事，决定了你能掌控多少，又要自己维护多少。如今，harness 通常通过以下四种方式来到你手中：

2026 年 10 月下旬，后三种方式各自出现了一个清晰的例子。Cursor 的 [Agent SDK](https://cursor.com/blog/agent-sdk) 自 10 月 20 日起正式可用，它把智能体当作一个小项目来对待：提示词用 Markdown 编写，工具是 TypeScript 函数，评估（evals）就放在旁边。你可以在本地运行这样的智能体，把它部署到 Cursor 的基础设施上，也可以作为单个 Node 进程在自己的服务器上运行。10 月 28 日，Microsoft 以公开预览形式推出了 [Foundry Agent Service 中的 Copilot harness](https://devblogs.microsoft.com/foundry/microsoft-copilot-harness-in-foundry/)。驱动 GitHub Copilot 应用、CLI 和 VS Code 的正是[同一个 harness](https://blogs.microsoft.com/blog/2026/10/28/introducing-the-microsoft-copilot-harness-unlocking-the-potential-of-truly-multi-model-agentic-work/)。智能体循环和沙箱由 Microsoft 运行；你带来技能、MCP 工具，以及可以放进版本控制的智能体定义。同一天，[GitHub Agentic Workflows](https://github.blog/changelog/2026-10-28-github-agentic-workflows-generally-available/) 正式可用。你在 Markdown 文件里描述一项工作，比如给新 issue 分类，它会被编译成一个普通的 GitHub Actions 工作流，运行 Copilot 或其他编码智能体。

harness 运行在哪里，也决定了它的边界在哪里被强制执行。指令负责引导，权限负责约束。在你自己的循环里，这些强制机制要由你亲手搭建。在托管服务或自动化平台上，则由平台提供、由你配置。Agentic Workflows 展示了这可能意味着多少层防护：智能体默认只有只读权限，运行在防火墙后的沙箱容器中；它们提出的改动在真正生效之前，要先通过经过验证的“安全输出”（safe outputs）机制，以及一个独立的威胁检测扫描。告诉智能体做什么的，仍然是你的提示词；限制一次失误能造成多大破坏的，是平台。

你自己编写的部分，通常比循环本身更容易迁移。技能和 MCP 都是开放标准，Microsoft 的公告也把对它们的支持视为一个合格 harness 的标志。一个清晰的技能或写得好的工具描述，往往只需稍作调整就能搬到另一个 harness 上；而围绕某个特定循环写的代码，很少能做到这一点。前面我们建议，在比较 harness 时保持模型不变。多模型 harness 则让你可以做相反的实验：Foundry 允许你选择受支持的模型而无需重写编排逻辑，Agentic Workflows 允许每个工作流选择自己的模型提供方。你可以只换模型，其余一切保持不动。

无论选择哪条路，有些东西永远不会交给提供方：你想要的结果、描述它的指令和技能、你授予的工具和访问权限，以及证明工作已经完成的检查。harness 可以替你运行循环，却无法替你决定什么才算“完成”。

### 当模型是为某个 harness 训练的

到目前为止，我们一直把模型当作可以随时替换的零件。很多时候确实如此，但模型和 harness 之间的契合可能更深。每个 harness 都有自己的工具、自己的系统提示词，以及自己推进步骤的节奏。当一个模型在某个 harness 里通过强化学习训练时，它在学会做事的同时，也学会了这个 harness 的习惯。把它换到另一个 harness，它可能不那么会调用工具，多走一些不必要的步骤，或者在任务完成前就停下来。

OpenAI 对 Codex 模型就坦率地说明了这一点。它称 GPT-5-Codex 是为 Codex ["purpose-built"](https://openai.com/index/introducing-upgrades-to-codex/)，也就是专门打造的，并建议只在 Codex 或类似 Codex 的环境中把它用于智能体编程。它的 [Codex Prompting Guide](https://developers.openai.com/cookbook/examples/gpt-5/codex_prompting_guide) 建议自己搭建 harness 的人以 Codex 的标准提示词为起点，并使用模型在训练中用惯了的 `apply_patch` 和 shell 工具。指南还要求删掉所有让模型先给出计划、或在运行过程中汇报进度的提示，因为这可能让模型在工作完成前突然停下。Cursor 则从另一侧讲述了同样的磨合：在[为这些模型调整自家 harness](https://cursor.com/blog/codex-model-harness) 时，它让工具名称更接近对应的 shell 命令，比如 `rg`；它还发现，只给出 lint 工具的定义并不够，模型需要一条明确写出何时调用它的指令。

开放模型也在走同一条路。2026 年 11 月 6 日，Hugging Face 介绍了 [harness adapters](https://huggingface.co/blog/harness-hub/harness-adapters)：每个模型和 harness 的组合各配一个小型 LoRA 适配器，在未经修改的 harness（pi、opencode 和 hermes）里，用可验证的任务通过强化学习训练，全部由同一个基础模型提供服务。在团队称为冒烟测试（smoke tests）的初步试验中，这些适配器在未参与训练的任务上比基础模型调用工具更少，准确率则保持不变或有所提高。训练期间，一个名为 safeagents 的代理会按固定规则检查每一次工具调用，拦下骗取奖励的尝试，比如修改测试或去查找现成答案。只要一次运行里有被拦下的调用，就记零分。即使在模型学习的阶段，检查也属于 harness 的职责。

对写提示词的人来说，这里的启示很实际。如果你要在一个并非为它打造的 harness 里使用某个模型，先读一读厂商为这个模型写的提示词指南。让工具的名称和描述贴近模型已经熟悉的样子，删掉那些和它训练出来的习惯相冲突的指令。与其规定它一路上怎么汇报，不如讲清你要的结果和它该在什么时候停下。比较不同 harness 时也要记住，模型可能偏向它受训时所在的那个；下结论之前，先用你自己的任务试一试。

  before={{ label: "一个通用的 harness 提示词", content: "先写一份计划发给我。每完成一步，都给我发一次进度更新。用 edit_file 工具编辑文件。" }}
  after={{ label: "为在 harness 中训练过的模型调整后的提示词", content: "修复失败的搜索测试，但不要改变查找匹配结果的方式。用 apply_patch 进行修改。一直做到测试通过或遇到阻碍为止，然后告诉我改了什么、运行了哪些检查，以及哪些内容未能验证。" }}

## 什么样的 Harness 才有用？

只有系统能够检查工作并从问题中恢复时，更高的自主性才有用。对于长任务，要关注 harness 如何处理以下事项：

- **上下文：** 保留相关指令和证据。总结旧步骤可以节省空间，但也可能丢失细节。
- **进度：** 保存决定和未完成的工作，让下次会话可以继续。保存的状态仍然需要加载到上下文中。
- **失败：** 清楚地返回错误，限制重试次数，避免盲目重复有副作用的操作。
- **限制：** 达到时间、费用或步骤预算时停止，或者在需要用户输入时停止。停止不代表成功。
- **验证：** 检查实际文件、测试结果或其他成果。最终回复很自信，并不够。

比较配置时，尝试相同的实际任务，同时检查结果和执行记录。如果想研究 harness 的变化，就保持模型不变。每次只修改一个提示词、技能或工具设置，并重复执行任务，因为每次运行可能不同。

### 当 Harness 变小

Harness 往往越长越大。每加一个新功能，就会多出一条专用路径、一套专用指令，以及一种对“完成”的独特理解；每一样在加进来的那天都有它的道理。随着模型越来越强，一些团队开始反其道而行之，把部件拆掉。Apple 的研究人员提出了 [How Much of a Harness Does a Strong Agent Need?](https://machinelearning.apple.com/research/harness-autonomous-ml-engineering)（2026 年 10 月）这个问题，并发现：在机器学习工程任务中，在模型相同、时间预算相同的条件下，复杂的开源 harness 并不比只配备最少工具的单个编程智能体会话表现更好。不过，拆掉部件很容易。要知道变小后的 harness 是否仍然把活干好，就得靠测量。

Pogl 让人们通过与 AI 对话来制作和编辑游戏，它在 [We rebuilt our harness from scratch](https://about.pogl.com/blog/one-loop-harness)（2026 年 11 月 11 日）中讲述了这样一次重建。旧 harness 建立在开源编程智能体 OpenCode 之上，随着时间推移，每个新功能都作为一条新路径加在它周围，于是同一个问题得在每条路径上分别修一遍。新 harness 让所有请求都走同一个循环，核心代码只有 715 行。每个项目只保留一份对话历史，每一步都在日志里留下一行。这样，重启后的工作进程能根据日志重建对话，从中断的地方接着做，而不是从头再来。

最有启发的是测量方式。两个 harness 判断“完成”的标准不同，它们各自给出的结论没法直接比较。于是 Pogl 重新运行了 54 对过去的请求，用同一个评判者给两边重新打分。整体质量相近：新 harness 在 8 个请求上更好，旧 harness 在 5 个请求上更好。据 Pogl 报告，每次编辑的未缓存输入减少约 65%，输出减少约 52%，运行超过 40 分钟的任务也消失了。它同样坦率地写出了另一面：节省的大部分来自旧 harness 上少数几个特别大的任务，而在典型任务上，新 harness 从缓存中重读的内容更多，写出的输出更多，耗时也更长。其中一次重跑揭示了任何平均值都看不出的事：旧 harness 把一个没有修好的事项标成了“完成”，新 harness 则如实报告为“未完成”。随后，Pogl 为一半用户开启了新 harness，按人划分，这样没有人会在任务进行到一半时换 harness；只要改一个设置，就能在一分钟内让所有人回到旧 harness。

Framer 从另一个方向走向了更小的循环，见 [Harness 2: executing agent code as it streams](https://www.framer.com/blog/harness-2/)（2026 年 11 月 2 日）。它建立在本章前面“当模型自己编写循环”一节讲过的程序化工具调用之上：智能体可以把整个工作流写成一个 JavaScript 程序。Framer 在模型还在写这个程序时，就按单元逐段执行，因此一旦某个假设落空，就能提早停止生成，而不必等整个程序写完才发现。Framer 报告称，每条消息的工具步骤减少一半，缓存输入 token 减少 39%，且没有测出质量下降。

这些数字都来自各公司自己的报告，你的任务结果也会不同。但其中的经验可以带走。路径越少，要修的地方就越集中：所有请求都走同一个循环时，发现一次的问题只需修一次。只有让同一个评判者给两个 harness 打分，比较才算公平，因为每个 harness 对“完成”的理解本身就是你在测试的内容之一。平均值会掩盖缓慢的长尾，比如偶尔要跑四十分钟的那个任务，也会掩盖一次虚假的“完成”，所以要看看耗时最长的运行，并把几份执行记录从头读到尾。最后，新 harness 最稳妥的做法是逐步推给用户，并留好一条一分钟就能退回的路，而不是要花一周。

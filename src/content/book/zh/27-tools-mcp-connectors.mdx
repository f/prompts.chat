你让智能体找出项目中尚未解决的 bug，并起草一个后续事项。要完成这件事，光有好的指令还不够。它需要能够访问问题跟踪系统，读取正确的数据，并且可能在那里创建新内容。

这就需要**工具**、**连接器**和 **MCP**。它们相互关联，但描述的是配置中的不同部分。

## 工具实际包含什么

工具通常有**名称**、**描述**、**输入模式**，以及真正执行工作的实现。描述帮助模型决定何时使用它。输入模式说明它接受哪些参数。

下面是一个虚构的 MCP 工具定义：

<Collapsible title="查看 search_issues 的定义">

```json
{
  "name": "search_issues",
  "description": "搜索已连接项目中的问题。此工具只读取数据。",
  "inputSchema": {
    "type": "object",
    "properties": {
      "query": { "type": "string" },
      "limit": { "type": "integer", "minimum": 1, "maximum": 20 }
    },
    "required": ["query"],
    "additionalProperties": false
  }
}
```

</Collapsible>

模型可能使用 `{"query": "未解决的 bug", "limit": 3}` 请求 `search_issues`。外围应用把请求转发给具体实现。实现查询跟踪系统，然后返回结果或错误。

名称和输入模式本身不会执行任何操作。实现必须验证输入、检查访问权限，并执行实际操作。工具响应也不同于模型的最终回答：响应可能包含问题 ID 和标题，再由模型进行总结。[MCP 工具规范](https://modelcontextprotocol.io/specification/latest/server/tools)介绍了工具如何提供这些操作。

<Callout type="info" title="请求不等于结果">
“我会创建一个问题”是一句话。工具调用是在请求执行操作。包含新问题 ID 的成功响应，才是操作确实发生的证据。请把这三件事分开。
</Callout>

### 一个工具可以代表一整套工作流

到目前为止，每个工具都只是一个操作：搜索、创建、导出。但工具名称背后的实现可以大得多。它可以是一整套流程，事先写好，由工作流引擎来运行。智能体依然决定**何时**启动它、传入**什么输入**。之后的一切都严格按照流程的定义进行，顺序相同，次次如此。

以退款为例。客服智能体也许很擅长理解一位恼火的顾客，但你大概不希望它临场发挥你的退款政策。把退款工作流封装成一个工具后，无论是哪段对话触发了它，它都会先核实是否符合退款条件，再请主管审批，最后把款项退回账户。审批、部署，以及其他那些步骤本身*就是*政策的流程，也都适用同样的形式。工作流引擎通常会记录每一次运行，所以智能体还能查阅过去的运行记录，告诉你昨晚哪些运行失败了、卡在哪一步，而不是靠猜。

AWS 提供了一个最近的例子。2026 年 10 月 29 日，AWS [宣布](https://aws.amazon.com/about-aws/whats-new/2026/10/step-functions-workflows-ai-agent-tools/) Step Functions 工作流可以通过 Amazon Bedrock AgentCore Gateway 作为智能体的工具来使用，而 AgentCore Gateway 正是通过 MCP 把智能体与工具连接起来的。不过，这个思路并不属于某一家厂商：一条 CI 流水线、工单系统里的一套审批流程，或者团队早已信任的一个脚本，都可以用同样的方式交给智能体。

这其实是在分配两种长处。模型是灵活的：它能读懂不寻常的情况，选出合理的下一步。工作流是可预测的：相同的输入总会走过相同的步骤。把启动的时机交给智能体，把步骤交给工作流，两种长处就各得其所。这也改变了提示词的写法。要描述的是目标，以及何时调用工作流，而不是工作流内部的步骤。在提示词里重复这些步骤，等于给政策多造了一份副本。这份副本可能慢慢偏离真正的政策，模型也可能试图亲手去执行它。

### 工具背后也可以是另一个智能体

一个工具名称的背后，还可能藏着第二种形态。实现部分可以不是一套固定的流程，而是一个独立的智能体。它接收请求，运行自己的循环：制定计划、搜索、权衡找到的内容，必要时在途中编写并运行代码，最后交回一个完成的结果，比如一份附有引用的回答、一份报告或一个文件。在调用它的智能体看来，这一切只是一次工具调用和一次响应。

这改变了调用方智能体需要做的事。使用只负责取数据的轻量工具时，研究工作由外层智能体亲自完成。它决定查询哪个来源，阅读返回的内容，发现矛盾，再次搜索。每一步都发生在它自己的上下文窗口里，它读过的每一条原始结果都会一直留在那里，直到任务结束。专门的智能体接收的是一个**目标**，而不是一串工具调用。具体的每一步都发生在专家的上下文中，而不是你的上下文中，因此外层智能体的上下文保持得更短，注意力也始终放在更大的任务上：你要的是什么，它已经知道什么，以及拿到结果后该做什么。

两个近期的例子从不同角度展示了这个思路。2026 年 11 月 4 日，AlphaSense [推出](https://www.alpha-sense.com/resources/product-articles/superanalyst-mcp/)了 SuperAnalyst MCP，并将其描述为一个可以托付复杂金融与商业研究的智能体。它规划研究，从该公司的文档库中收集来源，执行分析，并返回附有引用的上下文，引用指向原始段落。结果的形式随请求而定：一个直接的回答、一张电子表格，或一份附有来源的证据包。在开源领域，[GPT Researcher MCP 服务器](https://github.com/assafelovic/gptr-mcp)为开放网络做着类似的事。它的 `deep_research` 工具接收一个查询，完整地执行一轮研究，探索并核实多个来源。根据其[文档](https://docs.gptr.dev/docs/gpt-researcher/mcp-server/getting-started)，这大约需要 30 到 40 秒，而不是普通搜索那种几乎即时的回复。它会把收集到的上下文和来源连同一个研究 ID 一起返回，`write_report` 和 `get_research_sources` 等配套工具可以基于这个 ID 继续工作。同一个服务器还提供 `quick_search`，用于快速浅显的查找就已足够的场合，这也提醒我们，两种形态可以并存。

把它和上一节的工作流放在一起看。工作流是可预测的：相同的输入每次都走过相同的步骤，这正是它的价值。嵌套的智能体是灵活的：它自己选择下一步，这同样是它的价值。但灵活也带来了同样的问题，就是你对任何一个托付了工具的智能体都应该问的那些问题。你看到的每一步更少了，常常只有结果，以及它选择返回的那部分痕迹。你信任的是它的来源、它对哪些来源更重要的判断，以及它自己面对误导性内容时的谨慎。而一次漫长的嵌套运行仍然要花费 token 和时间，即使这些花费发生在你看不到的地方。所以，做决定时要问：判断应该归谁？当权衡来源、选择下一步看什么*本身就是*专业能力时，就交给专家。当步骤*本身就是*政策时，就继续使用固定的工作流。

提示词也由此而来。描述目标，以及答案应该以什么形式呈现；在重要的时候，要求提供来源或对不确定性的说明。不要罗列专家内部的步骤。它已经有自己的步骤，你写进提示词的第二份副本只会和它们相互竞争。

### 没有 API 时，屏幕就成了工具

到目前为止，每个工具都有一扇专为软件开的门：API、连接器、MCP 服务器。可许多系统并没有这样的门。一个老旧的内部门户、一家供应商的预订网站、一个上个年代的桌面程序：人们每天都在用它们，却只能隔着屏幕去用。面对这些系统，有些模型可以把屏幕本身当作工具。这通常被称为**计算机使用**（computer use）。

它的机制就是你已经熟悉的那个循环，只不过来回传递的是图片，而不是数据。运行模型的应用发送任务和一张截图。模型看过之后，回答的不是一段文字，而是一个结构化的操作：点击这个位置、输入这段文字、向下滚动。有些工具还会给每个操作附上一句简短的意图说明，比如“点击搜索框，输入目的地”，让一次运行更容易看懂。模型依然不会亲手去动任何东西。执行操作、截取新的截图并把它发回去的，是开发者自己的代码。看，动手，再看，直到任务完成，或者有人叫停这个循环。这个循环在哪里运行，和它如何运作同样重要，《常驻机器人》一章中的“[机器人的电脑](/book/28-persistent-bots)”一节会讨论这个问题。

2026 年 10 月 30 日，Google 在 Gemini API 中正式推出了 Computer Use 工具（[发布说明](https://ai.google.dev/gemini-api/docs/changelog)）。它的[文档](https://ai.google.dev/gemini-api/docs/computer-use)介绍了浏览器、移动设备和桌面三种环境，带有 `intent` 字段的操作，可配置的安全策略（可以拦下某个操作，或在付款之类的步骤前要求确认），以及需要主动开启的截图扫描，用来发现隐藏的提示词注入。Google 自己也建议，重要任务要密切监督。这个思路并非一家独有：Anthropic 为 Claude 提供了[计算机使用工具](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool)，OpenAI 在其 Responses API 中提供了[计算机工具](https://platform.openai.com/docs/guides/tools-computer-use)，两者都建立在同样的交换之上：截图和操作来回传递，而操作由你的应用来执行。

其中的取舍值得说得直白些。读屏幕比调用 API 慢，每张截图都要花费 token，一个挪了位置的按钮或一个意外弹出的窗口，就可能让昨天还好好的运行今天出错。所以，只要有真正的 API 或连接器，就优先用它们，把计算机使用留给那些别无入口的系统。屏幕也和其他任何输入一样：页面上的文字可能像文档一样藏着提示词注入，出现在图片里并不会让它更可信。而且，因为模型能点击一个人能点的任何东西，付款、删除、修改数据这类有风险的步骤，都应该等人来确认。

不过，截图并不是看见屏幕的唯一方式。操作系统和浏览器早已为每个窗口保留了第二份更安静的描述：**无障碍树**。它是由按钮、输入框、菜单和标签组成的结构化提纲，系统把它公开出来，好让屏幕阅读器告诉看不见屏幕的人，那里有什么、哪些东西可以按。智能体也能读这份提纲。工具拍下的不是图片，而是一份快照，列出智能体可以操作的每一个元素，每个元素都带着自己的角色、名称和一个简短的引用编号。模型不必再去猜“保存”按钮落在哪组坐标上，只要请求点击带有那个引用的元素即可。随后它会再拍一份新的快照，重新看一遍，因为一次点击顺利执行，并不能证明屏幕真的变了。Vercel Labs 为桌面应用开源了一个例子：[agent-desktop](https://github.com/vercel-labs/agent-desktop)。它是一个采用 Apache-2.0 许可的命令行工具和 C 库，读取 macOS（AX API）、Windows（UI Automation）和 Linux（AT-SPI）的无障碍接口，并以 JSON 返回快照。它的[文档](https://agent-browser.dev/desktop)特意说明，这是供智能体调用的工具，而不是智能体本身：里面没有模型，观察、行动、验证的循环始终留在调用它的一方。在浏览器里，微软的 [Playwright MCP 服务器](https://github.com/microsoft/playwright-mcp)沿用了同样的思路，让模型通过无障碍快照而不是截图来操作网页。

每一种看的方式都有长处，也有盲区。一份带名称的元素清单，通常比一张图片花的 token 少；按钮挪动几个像素，它也不会乱了阵脚；有些工具还能借助它完成操作，既不移动鼠标，也不抢走键盘前那个人的焦点。可是，这棵树只呈现应用愿意公开的东西。没有提供无障碍信息的程序，或者画布、游戏这类纯粹由像素画出来的内容，对它来说都是看不见的，在那里，截图依然是进去的路。所以很多工具会把两者结合起来：先读提纲，提纲不够用的地方再去看图。这也意味着，一个团队为使用屏幕阅读器的人认真给应用加上标签，这份用心会得到双重回报，因为智能体读的，正是这些标签。

写提示词的规则和之前一样，只是棱角更加锋利，因为网站没法告诉模型你本来是什么意思。说清楚是哪个网站、哪个页面，说明任务在哪里结束，并讲明做任何事之前必须先确认什么。

## 连接器增加了什么

连接器把与特定系统的集成打包在一起。它可能负责登录、选择账户或工作区、查找数据，以及把支持的操作作为工具提供。有些连接器只能搜索或读取，另一些也支持写入。

**连接器是产品用语，不是统一的技术标准。** 有的连接器直接调用服务的 API，有的使用 MCP 服务器，还有的搜索由同步文档建立的索引。要确认具体集成支持什么。微软的[连接器概述](https://learn.microsoft.com/en-us/azure/connectors/introduction)提供了基于 API 的集成示例。

连接账户并不意味着智能体能看到每个文件、把所有数据加载到上下文中，或者有权执行每种操作。访问能力取决于账户、配置的权限范围、应用以及服务自身的权限。搜索结果还可能来自比原始文档更旧的索引。

对于问题跟踪系统，要把这些问题分开：是否配置了连接？它可以访问哪个项目？只能读取，还是也能创建问题？

## MCP 标准化了什么

**MCP** 是 **Model Context Protocol（模型上下文协议）**的缩写。它规定了 AI 应用与外部能力提供方之间的通用通信方式。它不会取代服务的 API；MCP 服务器可以在内部使用这个 API。

[MCP 架构](https://modelcontextprotocol.io/docs/learn/architecture)有三个主要角色：

<InfoGrid columns={3} items={[
  { label: "宿主", description: "用户使用的 AI 应用。它协调连接、模型交互和权限。", color: "blue" },
  { label: "客户端", description: "位于宿主内部，负责维持与 MCP 服务器连接的部分。", color: "green" },
  { label: "服务器", description: "通过 MCP 提供工具、资源或提示词的程序。可以在本地或远程运行。", color: "amber" }
]} />

调用工具时，客户端可以通过 `tools/list` 发现服务器的工具。应用将相关工具定义提供给模型。如果模型请求其中一个工具，应用可以通过 MCP 客户端发送 `tools/call` 请求。服务器执行操作或委托其他实现执行，再返回结果。

模型不需要自己建立网络连接。应用和 MCP 实现负责通信。但兼容性仍然重要：宿主和服务器必须支持你想使用的能力。发现工具并不保证有权运行它，访问检查仍然需要进行。

### MCP 不只有工具

MCP 还定义了**资源**和**提示词**。这些词在协议中有特定含义：

<InfoGrid columns={3} items={[
  { label: "工具", description: "模型可以请求的操作，受应用控制。例子：搜索问题。", color: "blue" },
  { label: "资源", description: "应用可以作为上下文提供的数据。例子：通过 URI 标识的项目指南。", color: "green" },
  { label: "提示词", description: "用户可以选择的可复用消息模板，也可以接受可选参数。例子：准备问题分类报告。", color: "amber" }
]} />

[MCP 服务器概念指南](https://modelcontextprotocol.io/docs/learn/server-concepts)将它们描述为由模型控制的工具、由应用控制的资源，以及由用户控制的提示词。这描述的是预期的交互方式，并不取消应用的权限检查。

MCP 提示词模板不会自动成为技能。技能可以打包更长的流程、参考资料和脚本。它可以告诉智能体如何使用通过 MCP、直接连接器或本地函数提供的工具。

### 技能也可以随服务器一起到来

直到不久前，这两部分通常是分开到来的。服务器可以把工具交给智能体，但用好这些工具的经验却放在别处：单独安装的技能、一份 README，或者用户自己的提示词。服务一旦变化，这些说明就可能在不知不觉中过时。

MCP 官方的 **Skills 扩展**已于 2026 年 9 月定稿，它在很大程度上弥合了这道缝隙。现在，服务器不仅可以提供工具，还可以提供说明如何使用这些工具的技能，它们采用的正是[代理和技能](/book/25-agents-and-skills)中介绍的 `SKILL.md` 格式。工具告诉智能体它能做什么，技能告诉它怎样把事情做好。如今两者可以来自同一台服务器，于是说明就和它所描述的服务放在一起，由维护这项服务的人保持更新。

这一机制建立在你已经见过的部件之上。技能中的每个文件都作为 MCP 资源公开，按惯例使用以 `skill://` 开头的 URI。客户端可以用 `skills/list` 列出服务器的技能，用 `skills/get` 获取其中一个，再用 `resources/read` 读取它的辅助文件。

  after={{ label: "同时附带技能的服务器", content: "同一台服务器还提供一个问题分类技能。宿主起初只看到它的名称和描述，只有在任务需要时才加载完整说明。维护者修改服务时，可以同步更新这个技能。" }}

技能如何到达模型，仍由宿主决定。模型可以根据名称和描述选择技能，也可以由用户直接选择。无论哪种方式，完整说明都只在需要时才进入上下文；仅仅读取 `SKILL.md` 文件，并不会激活这个技能。

<Callout type="warning" title="来自服务器的技能依然是指令">
来自服务器的技能是进入智能体上下文的文本，可能左右它接下来的行动。因此，它值得像服务器本身一样被仔细审视。谨慎的宿主会在加载前验证内容，并在需要时征得批准。和 MCP Apps 以及下文介绍的 Tasks 扩展等其他官方 MCP 扩展一样，Skills 是可选的：只有客户端和服务器都声明支持时才会启用。客户端支持仍处于早期阶段，因此在依赖它之前，请先确认你的应用确实会从服务器加载技能。
</Callout>

### 当工具需要时间或答案时

大多数工具调用都是简短的往来：智能体提出请求，服务器给出回应，工作继续向前。但有些工作不合这个节奏。一次深入的调研、一份大型报告的导出或一次构建，可能要花上好几分钟；还有些工作会走到一个只有用户才能决定下一步的节点。针对这些时刻，MCP 提供了两种思路：面向需要时间的工作的 **Tasks**，以及面向需要人来参与的工作的**引导式询问**（elicitation）。

官方的 [Tasks 扩展](https://tasks.extensions.modelcontextprotocol.io/)（`io.modelcontextprotocol/tasks`）改变了耗时的 `tools/call` 的收尾方式。服务器不必一直挂着请求直到工作完成，而是可以立即返回一个持久的任务句柄，有点像寄存大衣时拿到的号码牌。客户端可以用 `tasks/get` 查看任务进展，用 `tasks/update` 发送更新或回答，用 `tasks/cancel` 取消任务，并在结果就绪后取回它。与此同时，智能体可以继续做别的事，稍后再回来。这对在你离开时仍在执行工作的[常驻机器人](/book/28-persistent-bots)尤其重要。Tasks 对双方都是可选的：客户端在每个请求中声明是否支持，服务器则逐个请求决定是否创建任务。现有工具不会自动获得这种能力，需要服务器的作者自行添加。

<Compare
  before={{ label: "阻塞的工具调用", content: "智能体调用 export_report 后只能等待。请求一连几分钟都挂着。如果连接中断，没人知道导出是否完成，而在收到回应之前，智能体什么别的事都做不了。" }}
  after={{ label: "任务句柄", content: "智能体调用 export_report 后立即拿到一个任务句柄。它转去处理别的工作，用 tasks/get 查看任务，等报告完成后再取回。如果计划有变，tasks/cancel 可以取消任务。" }}
/>

[引导式询问](https://modelcontextprotocol.io/specification/latest/client/elicitation)让服务器可以暂停下来，向用户索取结构化的输入：“要部署到 staging 吗？”“确认这笔退款吗？”，或者补上一个缺了就无法继续的细节。宿主会显示一个小表单，用户可以回答、拒绝或取消。拒绝同样是有效的回答，接下来怎么做由服务器决定。这两种思路会自然地交汇：正在运行的任务可以停在 `input_required` 状态，在中途向用户提问。在写入操作之前，这样的提问就是一个天然的人工把关点，恰好设在决定真正要紧的地方。

<Callout type="warning" title="来自服务器的表单，依然是来自服务器的请求">
引导式询问来自服务器，而不是你的应用，因此它和任何工具输出一样需要仔细审视。回答之前先看清它在问什么；除非你信任该服务器，否则绝不要在这类表单中输入密码、API 密钥或其他机密信息。各个应用的支持情况也不尽相同：VS Code [在文档中说明了对引导式询问的支持](https://code.visualstudio.com/api/extension-guides/ai/mcp)，Cursor 支持引导式询问，Claude Code 则以公开测试版的形式在其终端应用中加入了 [MCP Tasks 和引导式询问](https://code.claude.com/docs/en/mcp)，但尚未覆盖它运行的所有环境。官方的[客户端支持矩阵](https://modelcontextprotocol.io/extensions/client-matrix)列出了哪些应用支持哪些扩展，所以在依赖这两项功能之前，请先确认你的应用是否支持。
</Callout>

### 当服务器带来自己的界面

到目前为止，本章里的每一个工具都是用文字或数据作答。搜索返回问题编号，导出返回一个文件，至于怎样呈现结果，则由宿主决定，通常是作为对话中的一段文本。就连 elicitation 表单，也是宿主依据服务器发来的一段简短描述画出来的。对一句话或一张短短的列表来说，这已经够用。可换成一块销售仪表盘、一张项目看板或一份长文档，就远远不够了，因为这时的答案是你想亲眼查看、排序、亲手修改的东西，否则每一处小小的调整都要再多发一条消息。

**MCP Apps** 扩展让服务器可以带上自己的界面。一个工具可以指向一个界面资源：服务器在以 `ui://` 开头的地址上提供的一个小网页。工具运行时，宿主取来这个网页，把它显示在对话之中，通常放在一个沙箱化的框里，与应用的其余部分隔开。此后，网页和宿主通过一条狭窄的消息通道交谈。视图可以展示工具的结果，请求更多工具调用，也可以告诉模型这个人刚刚做了什么。[MCP Apps 概览](https://modelcontextprotocol.io/extensions/apps/overview)详细介绍了这套机制。这样一来，仪表盘、任务看板、设计画布或文档编辑器都可以直接出现在 AI 应用里，模型和人在同一个视图中处理同一件事。

这个想法并非出自某一家公司。社区项目 [MCP-UI](https://mcpui.dev/) 很早就开始探索 MCP 服务器的交互式视图；2025 年 10 月 6 日，OpenAI [推出了 ChatGPT 中的应用](https://openai.com/index/introducing-apps-in-chatgpt/)，同时发布了构建在 MCP 之上的 Apps SDK。下个月，MCP 项目以这两者为基础提出了一个共同标准，并在 2026 年 1 月 26 日[宣布 MCP Apps](https://blog.modelcontextprotocol.io/posts/2026-01-26-mcp-apps/) 成为它的第一个官方扩展。Claude、ChatGPT、Goose 和 Visual Studio Code 都在最早支持它的宿主之列。OpenAI 的[当前文档](https://developers.openai.com/plugins/build/chatgpt-ui)写道，ChatGPT 实现了这一开放标准，因此同一个界面也可以在其他兼容的宿主中运行。这正是开放扩展的实际价值：建立在它之上的应用，不会被绑在某一个 AI 应用上。如今有哪些应用支持它，可以查看[客户端支持矩阵](https://modelcontextprotocol.io/extensions/client-matrix)。

Anthropic 在 Claude 中推出的交互式连接器，展示了这个想法能延伸多远。它们在同一年 1 月[上线](https://claude.com/resources/articles/interactive-tools-in-claude)，最初是对话中的小型视图：一条可以在发送前检查的 Slack 消息、一条 Asana 时间线、一张来自 Hex 的图表。2026 年 11 月 10 日，Anthropic 对它们做了[扩展](https://claude.com/resources/articles/interactive-connectors-full-tool)：只要连接器支持，整个工具现在都可以在聊天旁边打开，或者铺满整个屏幕。对 Confluence 或 Notion 来说，这意味着你拿到的是用自己账号登录的完整编辑器，而不是一个功能受限的预览。你可以打开 Box 里的文件，在保留改动之前对比各个版本；可以用 Adobe 修饰照片或遮盖 PDF 中的内容；也可以在 Canva 里做设计。当你请 Claude 修改某处时，它的编辑会随着它的操作实时出现在工具里，而你批准这些操作的方式，和批准其他任何连接器操作一样。据 Anthropic 介绍，这一切都运行在 MCP Apps 之上，而扩展中较新的部分，例如应用工具和嵌入式网站，目前以公开预览的形式向开发者提供。

变化最大的，是协作本身的样子。你不再阅读模型对自己做了什么的转述，而是在一个早已熟悉的工具里亲眼看着它发生。改动可以由你亲手完成，也可以交给模型，两者都落在同一个页面上，所以一次修正往往只是点一下，而不必再写一段解释。你的提示词也会随之改变：既然你们都看得见屏幕，就不必再描述屏幕上有什么。不过，有些东西没有变。Claude 的[帮助页面](https://support.claude.com/en/articles/13454812-use-interactive-connectors-in-claude)指出，模型只能执行连接器开发者开放的操作，而视图使用的，正是你连接工具时授予的那些权限。窗户变得更丰富，并不意味着门变得更宽。

MCP App 是一段不是你写的代码，运行在一个你信任的应用里。这个扩展在设计时就考虑到了这一点：视图运行在沙箱化的框中，服务器要事先声明自己需要哪些外部域名，宿主可以在显示之前审查视图，视图和宿主之间的消息可以记录下来，宿主还可以在执行由视图发起的工具调用之前请求批准。这些层层防护限制了代码能触及的范围，却不能保证它展示的内容是真的。视图里的文字和任何文档一样，可能误导人，也可能夹带注入的指令。所以，界面和服务器本身属于同一个决定；正如后面一节会讲到的，连接本身就是一次信任决定。各个应用的支持程度也不尽相同，每个宿主都会自行决定实现这个扩展的多少部分，所以在依赖它之前，请先确认你的应用到底做了什么。
</Callout>

服务器正在学着随身携带的，不只是界面。2026 年 11 月 10 日，MCP 项目[介绍了](https://blog.modelcontextprotocol.io/posts/exploring-file-uploads-and-downloads-in-mcp/)一个实验性的文件扩展 `io.modelcontextprotocol/files`，用于在客户端和工具之间传递文件，例如把对话里的一份大 PDF 存到云存储中，而文件的字节完全不经过模型。作者们把它描述为一项刚刚起步、还没有参考实现的工作，所以请把它看作一个方向，而不是今天就可以在上面搭建东西的基础。

### 找到服务器，只连接一次

在智能体能够使用一台远程服务器之前，总得有人先找到它、弄清怎样连接，并完成登录。长期以来，这意味着从 README 里复制一个 URL，猜测该用哪种传输方式（transport），再在每个应用里重复一遍同样的设置。现在有两种帮助正在到来：客户端在连接**之前**就能读取的信息，以及只需设置**一次**就能反复使用的连接。

在发现这一侧，MCP 的 **Server Cards** 扩展（[SEP-2127](https://modelcontextprotocol.io/seps/2127-mcp-server-cards)）已于 2026 年 10 月 6 日定稿。它描述了一份关于远程服务器的小型静态文档：服务器的名称、端点与传输方式，以及它支持的协议版本。网站可以把自己的卡片列在 `/.well-known/ai-catalog.json` 处的 AI 目录中，这样，被指向某个域名的客户端无需手动设置，就能知道该连到哪里、怎样连接。卡片有意不包含工具列表，因为一台服务器提供哪些工具，可能随登录用户的不同而变化。工具依然要在连接之后通过 `tools/list` 获取。

在连接这一侧，GitHub 于 2026 年 10 月 28 日开始以公开预览的形式推出 [经 GitHub 验证的 MCP 服务器](https://github.blog/changelog/2026-10-28-connect-your-tools-to-copilot-without-all-the-setup/)，GitHub 也称之为连接器。你只需在 Slack 或 Sentry 这样的服务上登录一次，这个连接就能在 Copilot 应用、Copilot CLI、VS Code、云端的 Copilot 和 GitHub Mobile 中通用。

而且，工具也不只是网络服务。同一天，Google 在 Android Dev Summit 上 [宣布](https://developer.android.com/blog/posts/build-it-your-way-a-next-era-of-android-development)，被它称为 Android 统一工具调用层的 **AppFunctions** 已进入测试版（beta）。通过 Android MCP，手机上的应用可以把创建笔记、发送消息之类的功能，提供给应用自己的设备端智能体或系统级智能体，而不需要任何人打开这个应用。

这又回到了前面提过的一点：**连接器**是产品用语。服务器卡片、验证标识和一次性登录让设置更轻松，也帮助你信任自己连接的是*谁*。但它们不会替你决定授予*什么*。连接哪个账户、允许哪些权限、哪些操作需要等待批准，仍然由你来选。无论是用于发现的元数据还是验证，都不能代替你在工具列出之后，去查看它们实际能做什么。

### 当没有人去查找服务器时

前面所说的一切，都假定有人真的会去查找服务器：可能是翻阅目录的人，也可能是读取服务器卡片的客户端。但很多时候，根本没有人去查。你对编程智能体说一句“帮我配置一个 GitHub MCP”，选哪个包就落到了智能体自己头上。如果它用的是记忆中的名字，而不是核实过的名字，那么这个选择就来自模型的训练数据，而训练数据只是某个早已过去的时刻留下的快照。在那之后，服务的所有者也许已经换掉了服务器，或者把它归档了，而模型无从得知。

Glow Labs（Glow Security）的研究人员在审阅真实的编程会话记录后，于 2026 年 11 月[描述了正是这种情况](https://www.helpnetsecurity.com/2026/11/03/mcphantom-deprecated-mcp-servers/)，并把这种模式称为 MCPhantom。在智能体安装或推荐了已弃用 MCP 服务器的会话中，98% 的情况下智能体似乎是凭训练数据补全了包名；其余 2% 则是用户自己点名要了旧包。在他们举的 GitHub 例子里，智能体绕过了 GitHub 自己维护的服务器，转而选择了它记忆中一个已归档的参考服务器。问题并不出在某一个产品上：这种模式出现在多个运行框架中，包括 Claude Code、Cursor 和 Codex CLI，也出现在多家提供商的模型上。研究人员还在这些已归档的服务器中发现了四个高危漏洞，其中最严重的是 Puppeteer 服务器中的远程代码执行漏洞，通过提示词注入（prompt injection）就能触及。由于这些仓库已经归档，补丁不会再有了；不过报告也指出，目前尚未发现被利用的情况。

有两个细节让这个问题很容易被忽视。其一，事先查一查并不总是够用：在一次会话中，智能体在 npm 上看到了“This package is deprecated”的提示，却照样安装了这个包，也没有告诉用户。其二，这类服务器通常通过 `npx` 运行，因此从不出现在任何依赖文件里，项目中也就没有任何记录表明它们的存在。正如一位研究人员所说：“模型的记忆如今成了一个包管理器，却永远收不到哪些包已被弃用的消息。”

<Callout type="warning" title="安装也是一种操作">
在智能体添加服务器之前，问问它选的是哪个包、来自哪里。如果服务的所有者提供了官方服务器，就优先使用它；确认它仍在维护，没有被弃用或归档；并且每项服务只认定一个服务器。把安装当作需要你批准的事情来对待，就像智能体的其他任何操作一样。最简单的办法，是直接在提示词里写明你要用哪个服务器，这样智能体就没有什么需要凭记忆去补全的了。
</Callout>

### 连接本身就是一次信任决定

MCPhantom 讲的是选错服务器。而在这个选择的另一面，还藏着一种更不易察觉的风险：即使你精心挑选了一个远程服务器，连接它这个动作本身就可能带来危害。远程服务器运行在别人的机器上，它的代码从不会落到你的电脑里，所以第一次连接给人的感觉就像随便看一眼，不必付出任何代价。事实并非完全如此。你的客户端仍然运行在你自己的机器上，它会读取服务器发回的一切并据此行动，其中也包括服务器在要求你登录时交过来的地址。

2026 年 11 月 5 日，Pillar Security [展示了这一点有多重要](https://www.pillar.security/blog/inspecting-the-inspector-rce-in-mcps-official-debugging-tool)。他们研究的对象是 MCP Inspector（`@modelcontextprotocol/inspector`），也就是 MCP 项目官方的调试工具。开发者会用它去连接那些自己还不信任的本地或远程服务器，在让真正的智能体接触它们之前，先看看它们提供的工具、资源和提示词。在 Windows 和 WSL 上，2.12.0 之前的 Inspector 版本可能在与远程服务器进行 OAuth 登录的过程中被诱导执行任意代码，而此时连一个工具都还没有列出来，也没有任何人批准过任何操作。

这条链很短，单看其中每一环都平平无奇。远程服务器要求客户端登录时，会给出自己的 `authorization_endpoint`，也就是它的登录页地址，而这个地址是服务器自己决定的一段字符串。客户端会用 `open` 自动打开它，这是一个常用来启动浏览器的 npm 包。在 Windows 和 WSL 上，11.0.0 之前的 `open` 会不加转义地把这个地址放进一条 PowerShell 命令里，于是 PowerShell 就可能执行藏在一个其他方面完全合法的 https URL 里的代码。这段代码在开发者仅仅是连接的时候就已经运行了，甚至赶在浏览器打开之前。

维护者接受了这份报告，并在 2026 年 10 月 21 日发布的 Inspector 2.12.0 中修复了问题：新版本改用 `open` 11，并确保最终打开的 URL 正是经过检查的那一个。他们还发布了安全公告 [GHSA-q978-78c7-phqw](https://github.com/modelcontextprotocol/inspector/security/advisories/GHSA-q978-78c7-phqw)。中招的并不只有 Inspector。两周前，Pillar 已经在编程智能体 OpenCode（`opencode-ai`）中[描述过同一条链](https://www.pillar.security/blog/open-and-shut-remote-code-execution-in-opencode-via-mcp-oauth)。由于根本原因在于这两个工具把服务器地址交给 `open` 的方式，如今一条记录 CVE-2026-119025 就同时涵盖了 `open`、Inspector 和 OpenCode。

这里的教训不止于一个漏洞。Inspector 存在的意义，就是让你能安全地查看一个怀有敌意的服务器。MCP 项目把怀有敌意的远程服务器视为自家参考工具必须认真应对的情形，修复了漏洞，并发布了公告，这就为每一个实现同样 OAuth 流程的客户端立下了一个预期：远程 MCP 服务器是不可信的输入。而且，服务器不一定一开始就心怀恶意。一个与正牌几乎一模一样的名字、一个过期的域名，或者后来发生的接管，都可能让一个你曾经信任的地址背后藏着恶意的响应，而这个响应会在每次连接时重新送达。前面提到的服务器卡片和验证标识，能帮你选择连接的是*谁*。但它们改变不了你的客户端如何处理收到的响应。

<Callout type="warning" title="握手也在信任边界之内">
在连接远程服务器之前，尤其是你还在审查的服务器，要清楚自己用的是哪个客户端、哪个版本，并让它保持最新。在 Windows 和 WSL 上，这意味着 MCP Inspector 2.12.0 或更高版本、OpenCode 1.18.33 或更高版本，如果你自己的代码用到了 `open`，则需要 11.0.0 或更高版本。当你让智能体替你添加或试用某个服务器时，它所在的运行框架就是客户端，同样的问题也适用。最重要的是，把连接当作一次需要你做出的决定，而不是随便看一眼：在第一个工具出现之前，登录握手就已经在你的机器上运行了。
</Callout>

## 如何给有工具的智能体写提示词

告诉智能体要找什么信息、如何使用信息，以及你期待哪些操作。不要假设连接一定存在，也不要假设工具支持服务中的全部操作。

<Compare
  before={{ label: "太多内容需要猜", content: "看看 bug，把所有事情处理好。" }}
  after={{ label: "清晰的结果和边界", content: "搜索已连接项目中与空搜索结果相关的未解决 bug。总结相关问题并附上 ID。如有需要，起草一个后续问题，但在创建前先询问我。如果连接或需要的工具不可用，说明缺少什么。没有成功的工具结果时，不要声称问题已经创建。" }}
/>

可复用的问题分类技能可以补充方法：检查重复项、比较复现步骤、遵循项目的问题模板，以及报告未解决的疑问。工具提供操作，技能说明如何把它用好。

工具输出仍然需要判断。问题评论、文档或搜索结果可能包含错误，或者看起来像指令的文字。把检索到的内容当作数据，不要让它改变用户的请求或应用的规则。支持 MCP 并不意味着服务器或其内容就可信。

如果读取失败，智能体可以报告错误，或尝试合理的替代方案。如果写入超时，应先检查改动是否已经发生，再决定是否重试。否则，重试可能创建重复问题。凭据应放在集成的连接配置中，而不是任务提示词里。当机器人在你离开时按计划使用工具，这些规则就更加重要，详见[常驻机器人](/book/28-persistent-bots)。

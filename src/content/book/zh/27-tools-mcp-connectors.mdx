你让智能体找出项目中尚未解决的 bug，并起草一个后续事项。要完成这件事，光有好的指令还不够。它需要能够访问问题跟踪系统，读取正确的数据，并且可能在那里创建新内容。

这就需要**工具**、**连接器**和 **MCP**。它们相互关联，但描述的是配置中的不同部分。

## 工具实际包含什么

工具通常有**名称**、**描述**、**输入模式**，以及真正执行工作的实现。描述帮助模型决定何时使用它。输入模式说明它接受哪些参数。

下面是一个虚构的 MCP 工具定义：

<Collapsible title="查看 search_issues 的定义">

```json
{
  "name": "search_issues",
  "description": "搜索已连接项目中的问题。此工具只读取数据。",
  "inputSchema": {
    "type": "object",
    "properties": {
      "query": { "type": "string" },
      "limit": { "type": "integer", "minimum": 1, "maximum": 20 }
    },
    "required": ["query"],
    "additionalProperties": false
  }
}
```

</Collapsible>

模型可能使用 `{"query": "未解决的 bug", "limit": 3}` 请求 `search_issues`。外围应用把请求转发给具体实现。实现查询跟踪系统，然后返回结果或错误。

名称和输入模式本身不会执行任何操作。实现必须验证输入、检查访问权限，并执行实际操作。工具响应也不同于模型的最终回答：响应可能包含问题 ID 和标题，再由模型进行总结。[MCP 工具规范](https://modelcontextprotocol.io/specification/latest/server/tools)介绍了工具如何提供这些操作。

<Callout type="info" title="请求不等于结果">
“我会创建一个问题”是一句话。工具调用是在请求执行操作。包含新问题 ID 的成功响应，才是操作确实发生的证据。请把这三件事分开。
</Callout>

### 一个工具可以代表一整套工作流

到目前为止，每个工具都只是一个操作：搜索、创建、导出。但工具名称背后的实现可以大得多。它可以是一整套流程，事先写好，由工作流引擎来运行。智能体依然决定**何时**启动它、传入**什么输入**。之后的一切都严格按照流程的定义进行，顺序相同，次次如此。

以退款为例。客服智能体也许很擅长理解一位恼火的顾客，但你大概不希望它临场发挥你的退款政策。把退款工作流封装成一个工具后，无论是哪段对话触发了它，它都会先核实是否符合退款条件，再请主管审批，最后把款项退回账户。审批、部署，以及其他那些步骤本身*就是*政策的流程，也都适用同样的形式。工作流引擎通常会记录每一次运行，所以智能体还能查阅过去的运行记录，告诉你昨晚哪些运行失败了、卡在哪一步，而不是靠猜。

AWS 提供了一个最近的例子。2026 年 10 月 29 日，AWS [宣布](https://aws.amazon.com/about-aws/whats-new/2026/10/step-functions-workflows-ai-agent-tools/) Step Functions 工作流可以通过 Amazon Bedrock AgentCore Gateway 作为智能体的工具来使用，而 AgentCore Gateway 正是通过 MCP 把智能体与工具连接起来的。不过，这个思路并不属于某一家厂商：一条 CI 流水线、工单系统里的一套审批流程，或者团队早已信任的一个脚本，都可以用同样的方式交给智能体。

这其实是在分配两种长处。模型是灵活的：它能读懂不寻常的情况，选出合理的下一步。工作流是可预测的：相同的输入总会走过相同的步骤。把启动的时机交给智能体，把步骤交给工作流，两种长处就各得其所。这也改变了提示词的写法。要描述的是目标，以及何时调用工作流，而不是工作流内部的步骤。在提示词里重复这些步骤，等于给政策多造了一份副本。这份副本可能慢慢偏离真正的政策，模型也可能试图亲手去执行它。

  after={{ label: "描述目标和调用时机", content: "帮助顾客解决账单问题。当顾客要求退款且你已拿到订单号时，用这个订单号和退款原因调用退款工作流。报告它返回的结果。在工作流确认之前，不要承诺退款。" }}

## 连接器增加了什么

连接器把与特定系统的集成打包在一起。它可能负责登录、选择账户或工作区、查找数据，以及把支持的操作作为工具提供。有些连接器只能搜索或读取，另一些也支持写入。

**连接器是产品用语，不是统一的技术标准。** 有的连接器直接调用服务的 API，有的使用 MCP 服务器，还有的搜索由同步文档建立的索引。要确认具体集成支持什么。微软的[连接器概述](https://learn.microsoft.com/en-us/azure/connectors/introduction)提供了基于 API 的集成示例。

连接账户并不意味着智能体能看到每个文件、把所有数据加载到上下文中，或者有权执行每种操作。访问能力取决于账户、配置的权限范围、应用以及服务自身的权限。搜索结果还可能来自比原始文档更旧的索引。

对于问题跟踪系统，要把这些问题分开：是否配置了连接？它可以访问哪个项目？只能读取，还是也能创建问题？

## MCP 标准化了什么

**MCP** 是 **Model Context Protocol（模型上下文协议）**的缩写。它规定了 AI 应用与外部能力提供方之间的通用通信方式。它不会取代服务的 API；MCP 服务器可以在内部使用这个 API。

[MCP 架构](https://modelcontextprotocol.io/docs/learn/architecture)有三个主要角色：

<InfoGrid columns={3} items={[
  { label: "宿主", description: "用户使用的 AI 应用。它协调连接、模型交互和权限。", color: "blue" },
  { label: "客户端", description: "位于宿主内部，负责维持与 MCP 服务器连接的部分。", color: "green" },
  { label: "服务器", description: "通过 MCP 提供工具、资源或提示词的程序。可以在本地或远程运行。", color: "amber" }
]} />

调用工具时，客户端可以通过 `tools/list` 发现服务器的工具。应用将相关工具定义提供给模型。如果模型请求其中一个工具，应用可以通过 MCP 客户端发送 `tools/call` 请求。服务器执行操作或委托其他实现执行，再返回结果。

模型不需要自己建立网络连接。应用和 MCP 实现负责通信。但兼容性仍然重要：宿主和服务器必须支持你想使用的能力。发现工具并不保证有权运行它，访问检查仍然需要进行。

### MCP 不只有工具

MCP 还定义了**资源**和**提示词**。这些词在协议中有特定含义：

<InfoGrid columns={3} items={[
  { label: "工具", description: "模型可以请求的操作，受应用控制。例子：搜索问题。", color: "blue" },
  { label: "资源", description: "应用可以作为上下文提供的数据。例子：通过 URI 标识的项目指南。", color: "green" },
  { label: "提示词", description: "用户可以选择的可复用消息模板，也可以接受可选参数。例子：准备问题分类报告。", color: "amber" }
]} />

[MCP 服务器概念指南](https://modelcontextprotocol.io/docs/learn/server-concepts)将它们描述为由模型控制的工具、由应用控制的资源，以及由用户控制的提示词。这描述的是预期的交互方式，并不取消应用的权限检查。

MCP 提示词模板不会自动成为技能。技能可以打包更长的流程、参考资料和脚本。它可以告诉智能体如何使用通过 MCP、直接连接器或本地函数提供的工具。

### 技能也可以随服务器一起到来

直到不久前，这两部分通常是分开到来的。服务器可以把工具交给智能体，但用好这些工具的经验却放在别处：单独安装的技能、一份 README，或者用户自己的提示词。服务一旦变化，这些说明就可能在不知不觉中过时。

MCP 官方的 **Skills 扩展**已于 2026 年 9 月定稿，它在很大程度上弥合了这道缝隙。现在，服务器不仅可以提供工具，还可以提供说明如何使用这些工具的技能，它们采用的正是[代理和技能](/book/25-agents-and-skills)中介绍的 `SKILL.md` 格式。工具告诉智能体它能做什么，技能告诉它怎样把事情做好。如今两者可以来自同一台服务器，于是说明就和它所描述的服务放在一起，由维护这项服务的人保持更新。

这一机制建立在你已经见过的部件之上。技能中的每个文件都作为 MCP 资源公开，按惯例使用以 `skill://` 开头的 URI。客户端可以用 `skills/list` 列出服务器的技能，用 `skills/get` 获取其中一个，再用 `resources/read` 读取它的辅助文件。

<Compare
  before={{ label: "只提供工具的服务器", content: "问题跟踪服务器提供 search_issues 和 create_issue。问题分类的方法（检查重复项、遵循问题模板）只能来自单独安装的技能或你自己的提示词，而且服务变化后可能过时。" }}
  after={{ label: "同时附带技能的服务器", content: "同一台服务器还提供一个问题分类技能。宿主起初只看到它的名称和描述，只有在任务需要时才加载完整说明。维护者修改服务时，可以同步更新这个技能。" }}
/>

技能如何到达模型，仍由宿主决定。模型可以根据名称和描述选择技能，也可以由用户直接选择。无论哪种方式，完整说明都只在需要时才进入上下文；仅仅读取 `SKILL.md` 文件，并不会激活这个技能。

<Callout type="warning" title="来自服务器的技能依然是指令">
来自服务器的技能是进入智能体上下文的文本，可能左右它接下来的行动。因此，它值得像服务器本身一样被仔细审视。谨慎的宿主会在加载前验证内容，并在需要时征得批准。和 MCP Apps 以及下文介绍的 Tasks 扩展等其他官方 MCP 扩展一样，Skills 是可选的：只有客户端和服务器都声明支持时才会启用。客户端支持仍处于早期阶段，因此在依赖它之前，请先确认你的应用确实会从服务器加载技能。
</Callout>

### 当工具需要时间或答案时

大多数工具调用都是简短的往来：智能体提出请求，服务器给出回应，工作继续向前。但有些工作不合这个节奏。一次深入的调研、一份大型报告的导出或一次构建，可能要花上好几分钟；还有些工作会走到一个只有用户才能决定下一步的节点。针对这些时刻，MCP 提供了两种思路：面向需要时间的工作的 **Tasks**，以及面向需要人来参与的工作的**引导式询问**（elicitation）。

官方的 [Tasks 扩展](https://tasks.extensions.modelcontextprotocol.io/)（`io.modelcontextprotocol/tasks`）改变了耗时的 `tools/call` 的收尾方式。服务器不必一直挂着请求直到工作完成，而是可以立即返回一个持久的任务句柄，有点像寄存大衣时拿到的号码牌。客户端可以用 `tasks/get` 查看任务进展，用 `tasks/update` 发送更新或回答，用 `tasks/cancel` 取消任务，并在结果就绪后取回它。与此同时，智能体可以继续做别的事，稍后再回来。这对在你离开时仍在执行工作的[常驻机器人](/book/28-persistent-bots)尤其重要。Tasks 对双方都是可选的：客户端在每个请求中声明是否支持，服务器则逐个请求决定是否创建任务。现有工具不会自动获得这种能力，需要服务器的作者自行添加。

<Compare
  before={{ label: "阻塞的工具调用", content: "智能体调用 export_report 后只能等待。请求一连几分钟都挂着。如果连接中断，没人知道导出是否完成，而在收到回应之前，智能体什么别的事都做不了。" }}
  after={{ label: "任务句柄", content: "智能体调用 export_report 后立即拿到一个任务句柄。它转去处理别的工作，用 tasks/get 查看任务，等报告完成后再取回。如果计划有变，tasks/cancel 可以取消任务。" }}
/>

[引导式询问](https://modelcontextprotocol.io/specification/latest/client/elicitation)让服务器可以暂停下来，向用户索取结构化的输入：“要部署到 staging 吗？”“确认这笔退款吗？”，或者补上一个缺了就无法继续的细节。宿主会显示一个小表单，用户可以回答、拒绝或取消。拒绝同样是有效的回答，接下来怎么做由服务器决定。这两种思路会自然地交汇：正在运行的任务可以停在 `input_required` 状态，在中途向用户提问。在写入操作之前，这样的提问就是一个天然的人工把关点，恰好设在决定真正要紧的地方。

<Callout type="warning" title="来自服务器的表单，依然是来自服务器的请求">
引导式询问来自服务器，而不是你的应用，因此它和任何工具输出一样需要仔细审视。回答之前先看清它在问什么；除非你信任该服务器，否则绝不要在这类表单中输入密码、API 密钥或其他机密信息。各个应用的支持情况也不尽相同：VS Code [在文档中说明了对引导式询问的支持](https://code.visualstudio.com/api/extension-guides/ai/mcp)，Cursor 支持引导式询问，Claude Code 则以公开测试版的形式在其终端应用中加入了 [MCP Tasks 和引导式询问](https://code.claude.com/docs/en/mcp)，但尚未覆盖它运行的所有环境。官方的[客户端支持矩阵](https://modelcontextprotocol.io/extensions/client-matrix)列出了哪些应用支持哪些扩展，所以在依赖这两项功能之前，请先确认你的应用是否支持。
</Callout>

### 找到服务器，只连接一次

在智能体能够使用一台远程服务器之前，总得有人先找到它、弄清怎样连接，并完成登录。长期以来，这意味着从 README 里复制一个 URL，猜测该用哪种传输方式（transport），再在每个应用里重复一遍同样的设置。现在有两种帮助正在到来：客户端在连接**之前**就能读取的信息，以及只需设置**一次**就能反复使用的连接。

在发现这一侧，MCP 的 **Server Cards** 扩展（[SEP-2127](https://modelcontextprotocol.io/seps/2127-mcp-server-cards)）已于 2026 年 10 月 6 日定稿。它描述了一份关于远程服务器的小型静态文档：服务器的名称、端点与传输方式，以及它支持的协议版本。网站可以把自己的卡片列在 `/.well-known/ai-catalog.json` 处的 AI 目录中，这样，被指向某个域名的客户端无需手动设置，就能知道该连到哪里、怎样连接。卡片有意不包含工具列表，因为一台服务器提供哪些工具，可能随登录用户的不同而变化。工具依然要在连接之后通过 `tools/list` 获取。

在连接这一侧，GitHub 于 2026 年 10 月 28 日开始以公开预览的形式推出 [经 GitHub 验证的 MCP 服务器](https://github.blog/changelog/2026-10-28-connect-your-tools-to-copilot-without-all-the-setup/)，GitHub 也称之为连接器。你只需在 Slack 或 Sentry 这样的服务上登录一次，这个连接就能在 Copilot 应用、Copilot CLI、VS Code、云端的 Copilot 和 GitHub Mobile 中通用。

而且，工具也不只是网络服务。同一天，Google 在 Android Dev Summit 上 [宣布](https://developer.android.com/blog/posts/build-it-your-way-a-next-era-of-android-development)，被它称为 Android 统一工具调用层的 **AppFunctions** 已进入测试版（beta）。通过 Android MCP，手机上的应用可以把创建笔记、发送消息之类的功能，提供给应用自己的设备端智能体或系统级智能体，而不需要任何人打开这个应用。

这又回到了前面提过的一点：**连接器**是产品用语。服务器卡片、验证标识和一次性登录让设置更轻松，也帮助你信任自己连接的是*谁*。但它们不会替你决定授予*什么*。连接哪个账户、允许哪些权限、哪些操作需要等待批准，仍然由你来选。无论是用于发现的元数据还是验证，都不能代替你在工具列出之后，去查看它们实际能做什么。

这里的读取和写入模式属于示例集成。真实权限可能更细。MCP 给双方提供共同协议，但不决定你的账户能否写入项目，也不决定应用是否应该先询问你。**身份验证**确认你是谁；**授权**决定允许的访问范围。单独的批准可以确认某一次操作。远程 HTTP 集成可以使用 [MCP 授权框架](https://modelcontextprotocol.io/specification/latest/basic/authorization)，具体细节取决于集成。

## 如何给有工具的智能体写提示词

告诉智能体要找什么信息、如何使用信息，以及你期待哪些操作。不要假设连接一定存在，也不要假设工具支持服务中的全部操作。

<Compare
  before={{ label: "太多内容需要猜", content: "看看 bug，把所有事情处理好。" }}
  after={{ label: "清晰的结果和边界", content: "搜索已连接项目中与空搜索结果相关的未解决 bug。总结相关问题并附上 ID。如有需要，起草一个后续问题，但在创建前先询问我。如果连接或需要的工具不可用，说明缺少什么。没有成功的工具结果时，不要声称问题已经创建。" }}
/>

可复用的问题分类技能可以补充方法：检查重复项、比较复现步骤、遵循项目的问题模板，以及报告未解决的疑问。工具提供操作，技能说明如何把它用好。

工具输出仍然需要判断。问题评论、文档或搜索结果可能包含错误，或者看起来像指令的文字。把检索到的内容当作数据，不要让它改变用户的请求或应用的规则。支持 MCP 并不意味着服务器或其内容就可信。

如果读取失败，智能体可以报告错误，或尝试合理的替代方案。如果写入超时，应先检查改动是否已经发生，再决定是否重试。否则，重试可能创建重复问题。凭据应放在集成的连接配置中，而不是任务提示词里。当机器人在你离开时按计划使用工具，这些规则就更加重要，详见[常驻机器人](/book/28-persistent-bots)。

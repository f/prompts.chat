## 什么是 AI 智能体？

**AI 智能体**是一个能够自主规划、执行和迭代任务的 AI 系统。与简单的提示-响应交互不同，智能体可以：

- **规划** - 将复杂目标分解为可执行的步骤
- **执行** - 使用工具并在现实世界中采取行动
- **观察** - 处理其行动的反馈
- **适应** - 根据结果调整其方法
- **持久化** - 在交互之间维护上下文和记忆

这些提示词类型叠加在一起形成完整的智能体行为：

### 系统提示词（智能体的身份）

建立智能体是谁以及如何行为的基础提示词：

```markdown
You are a code review assistant. Your role is to:
- Analyze code for bugs, security issues, and performance problems
- Suggest improvements following best practices
- Explain your reasoning clearly
- Be constructive and educational in feedback

You have access to tools for reading files, searching code, and running tests.
```

### 规划提示词（如何思考）

指导智能体推理和规划过程的指令：

```markdown
Before taking action, always:
1. Understand the complete request
2. Break it into smaller, verifiable steps
3. Identify which tools you'll need
4. Consider edge cases and potential issues
5. Execute step by step, validating as you go
```

### 工具使用提示词（如何行动）

关于何时以及如何使用可用工具的指导：

```markdown
When you need to understand a codebase:
- Use grep_search for finding specific patterns
- Use read_file to examine file contents
- Use list_dir to explore directory structure
- Always verify your understanding before making changes
```

### 恢复提示词（如何处理失败）

当事情出错时的指令：

```markdown
If an action fails:
1. Analyze the error message carefully
2. Consider alternative approaches
3. Ask for clarification if the task is ambiguous
4. Never repeat the same failed action without changes
```

<Callout type="info" title="提示词栈">
智能体的行为源于多层提示词的协同工作。系统提示词奠定基础，规划提示词指导推理，工具提示词启用行动，恢复提示词处理失败。它们共同创造出连贯、有能力的行为。
</Callout>

## 什么是技能？

如果提示词是原子，**技能就是分子**——赋予智能体特定能力的可复用构建块。

**技能**是一个全面的、可移植的指令包，为 AI 智能体提供特定领域或任务的专业知识。技能是智能体的可复用模块：你只需构建一次，任何智能体都可以使用它们。

<Callout type="tip" title="技能 = 可复用的智能体模块">
只需编写一次代码审查技能。现在每个编程智能体——无论是用于 Python、JavaScript 还是 Rust——都可以通过加载该技能立即成为专业的代码审查员。技能让你像搭积木一样构建智能体能力。
</Callout>

`SKILL.md` 文件定义整体方法：

```markdown

name: code-review
description: Comprehensive code review with security, performance, and style analysis
---

# Code Review Skill

You are an expert code reviewer. When reviewing code:

## Process
1. **Understand Context** - What does this code do? What problem does it solve?
2. **Check Correctness** - Does it work? Are there logic errors?
3. **Security Scan** - Reference security-checklist.md for common vulnerabilities
4. **Performance Review** - Check performance-tips.md for optimization opportunities
5. **Style & Maintainability** - Is the code readable and maintainable?

## Output Format
Provide feedback in categories:
- 🔴 **Critical** - Must fix before merge
- 🟡 **Suggested** - Recommended improvements
- 🟢 **Nice to have** - Optional enhancements

Always explain *why* something is an issue, not just *what* is wrong.
```

## 构建有效的技能

### 1. 清晰定义专业知识

从清晰描述技能能实现什么开始：

```markdown
---
name: api-design
description: Design RESTful APIs following industry best practices, 
  including versioning, error handling, and documentation standards
---
```

### 2. 层次化组织知识

从通用到具体组织信息：

```markdown
# API Design Skill

## Core Principles
- Resources should be nouns, not verbs
- Use HTTP methods semantically
- Version your APIs from day one

## Detailed Guidelines
[More specific rules...]

## Reference Materials
- See `rest-conventions.md` for naming conventions
- See `error-codes.md` for standard error responses
```

### 3. 包含具体示例

抽象规则通过示例变得清晰：

```markdown
## Endpoint Naming

✅ Good:
- GET /users/{id}
- POST /orders
- DELETE /products/{id}/reviews/{reviewId}

❌ Avoid:
- GET /getUser
- POST /createNewOrder
- DELETE /removeProductReview
```

### 4. 提供决策框架

帮助智能体在模糊情况下做出选择：

```markdown
## When to Use Pagination

Use pagination when:
- Collection could exceed 100 items
- Response size impacts performance
- Client may not need all items

Use full response when:
- Collection is always small (<20 items)
- Client typically needs everything
- Real-time consistency is critical
```

### 5. 添加恢复模式

预见可能出错的情况：

```markdown
## Common Issues

**Problem**: Client needs fields not in standard response
**Solution**: Implement field selection: GET /users?fields=id,name,email

**Problem**: Breaking changes needed
**Solution**: Create new version, deprecate old with timeline
```

    <div className="px-3 py-2 bg-teal-100 dark:bg-teal-900/50 border border-teal-200 dark:border-teal-800 rounded text-center text-sm max-w-40">
      <p className="font-medium text-teal-700 dark:text-teal-300 m-0!">验证</p>
      <p className="text-xs text-teal-600 dark:text-teal-400 m-0! mt-1">检查修改是否合理、是否可能有帮助</p>
    </div>
    <div className="self-center text-muted-foreground">→</div>
    <div className="px-3 py-2 bg-green-100 dark:bg-green-900/50 border border-green-200 dark:border-green-800 rounded text-center text-sm max-w-40">
      <p className="font-medium text-green-700 dark:text-green-300 m-0!">启用</p>
      <p className="text-xs text-green-600 dark:text-green-400 m-0! mt-1">从此改用新版本</p>
    </div>
  </div>
  <div className="text-xs text-muted-foreground flex items-center gap-1">
    <span>↺</span> 每个新版本都会为下一轮积累证据
  </div>
</div>

Perplexity 为 **Brain** 详细描述了这样一个循环。Brain 是支撑其智能体 Computer 的一套能够自我改进的记忆系统（[What is Brain?](https://www.perplexity.ai/help-center/en/articles/19700001-what-is-brain)）。在 2026 年 11 月的一篇文章（[Self-improving skills](https://www.perplexity.ai/hub/blog/self-improving-skills)）中，该公司解释了 Brain 如何借助用户的记忆和会话历史，编写并打磨*个人*技能。在证据阶段，它会找出用过某个技能的过往会话，尤其是技能表现不佳的那些。在反思阶段，一个改进智能体研究这些会话并提出修改。验证阶段检查提案格式是否规范、是否可能改善结果；启用阶段则应用修改，之后的会话又成为下一轮的证据。让这个循环值得信任的，是其中内置的克制。新建一个技能，需要同一种可复用的行为在两次相互独立的场合中出现；而更新已有技能，有时只要一次有据可查的情况就够了。改进智能体从不直接改动技能：它写出一份附带理由和证据的提案，每次运行对每个技能最多只做一处修改，证据不足以支持时就干脆不提。此外，自动创建的技能每位用户最多十个，所以新技能只有在某个旧技能退役后才能加入，而且必须说明这次替换的理由。

Nous Research 的 **Hermes Agent** 则从团队的角度切入同一个想法。随着人们把重复性的工作交给它，Hermes 会把一种行之有效的做法变成可复用的技能：一份书面定义，配上每次都以相同方式执行固定步骤的代码（[Nous Research](https://nousresearch.com/press/hermes-enterprise-in-microsoft-teams)）。它的 Collective Wisdom 插件负责处理技能离开某个人电脑的那一刻。Hermes 可能会建议某个技能值得分享，但决定权仍在作者手里，作者会逐一审阅即将发布到团队技能库的那些文件本身。之后，队友安装的是一个确定的版本，而不是这个技能今天碰巧呈现的样子（[Collective Wisdom](https://github.com/NousResearch/hermes-collective-wisdom)）。[始终在线的机器人](/book/28-persistent-bots)一章还介绍了 Hermes 获得技能的另一种方式：有人带着它一步步走完一项任务。

把两个例子放在一起，得出的是同一个教训。一个会自我改写的技能，仍然是一组智能体将要遵循的指令，因此值得和手写的技能一样用心对待。修改之前先要证据，最好来自不止一次会话。凡是技能从一个人传到其他人手中的地方，都要保留一个人工审核的环节。保存好各个版本，这样出了糟糕的修改就可以直接回滚，而不必争论不休。还要留意漂移：一个被频繁修订的技能，可能会慢慢偏向某一个人的习惯，或者某一次糟糕的会话，直到它描述的与其说是工作本身，不如说是一时的情绪。

门槛该定多高，取决于这个技能会影响到谁。为单个用户学到的个人技能，可以变得快一些，因为出了错也只影响这一个用户，而他恰恰最容易察觉。共享技能或内置技能则会影响每一个加载它的人。Perplexity 也划出了这条线：对每位用户都会收到的内置技能所做的修改，必须先通过成对回放测试和内部人工审核，才能进入正式版本。团队也可以借鉴同样的直觉：让个人技能自由学习，而要求共享技能的每一次修改都名副其实。

想试试这个循环，并不需要一套能自我改进的系统。只要让智能体提出建议而不是直接应用，你也可以手动走一遍：

## 分享和发现技能

技能在分享时最有价值。像 [prompts.chat](https://prompts.chat/skills) 这样的平台允许你：

- **发现**社区为常见任务创建的技能
- **下载**技能直接到你的项目
- **分享**你自己的专业知识作为可复用技能
- **迭代**基于实际使用改进技能

同样的方式也适用于比单个技能更大的单位：带着指令和例行任务的完整机器人，以及彼此交接工作的机器人团队，[Bots](https://prompts.chat/bots) 和 [Teams](https://prompts.chat/bots/teams) 目录就是例子。我们会在[常驻机器人](/book/28-persistent-bots)那一章讨论这两个想法。

在从零开始构建技能之前，检查是否有人已经解决了你的问题。社区技能经过实战检验，通常比从零开始更好。
</Callout>

智能体提供执行框架——规划、工具使用和记忆——而技能提供领域专业知识。这种分离意味着：

- **技能是可移植的** - 同一个技能可以与不同的智能体一起工作
- **智能体是可扩展的** - 通过添加技能来添加新功能
- **专业知识是可分享的** - 领域专家可以贡献技能而无需构建完整的智能体

## 最佳实践

### 构建技能

1. **从具体开始，然后泛化** - 首先为你的确切用例构建技能，然后抽象
2. **包含失败案例** - 记录技能无法做什么以及如何处理
3. **为技能添加版本** - 跟踪更改，以便智能体可以依赖稳定版本
4. **用真实任务测试** - 根据实际工作验证技能，而不仅仅是理论

### 与智能体一起使用技能

1. **先阅读技能** - 在部署之前了解技能的功能
2. **谨慎自定义** - 仅在必要时覆盖技能默认值
3. **监控性能** - 跟踪技能在你的上下文中的表现
4. **贡献改进** - 当你改进技能时，考虑回馈社区

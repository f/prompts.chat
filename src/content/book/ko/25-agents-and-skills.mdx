## AI 에이전트란 무엇인가?

**AI 에이전트**는 자율적으로 계획을 세우고, 실행하며, 작업을 반복할 수 있는 AI 시스템입니다. 단순한 프롬프트-응답 상호작용과 달리, 에이전트는 다음과 같은 작업을 수행할 수 있습니다:

- **계획** - 복잡한 목표를 실행 가능한 단계로 분해
- **실행** - 도구를 사용하고 실제 세계에서 행동 수행

- **적응** - 결과에 따라 접근 방식 조정
- **지속** - 상호작용 전반에 걸쳐 컨텍스트와 메모리 유지

이러한 프롬프트 유형이 함께 쌓여 완전한 에이전트 행동을 형성합니다:

### 시스템 프롬프트 (에이전트의 정체성)

에이전트가 누구이며 어떻게 행동하는지 설정하는 기초 프롬프트입니다:

```markdown
You are a code review assistant. Your role is to:
- Analyze code for bugs, security issues, and performance problems
- Suggest improvements following best practices
- Explain your reasoning clearly
- Be constructive and educational in feedback

You have access to tools for reading files, searching code, and running tests.
```

### 계획 프롬프트 (사고 방식)

에이전트의 추론과 계획 과정을 안내하는 지침입니다:

```markdown
Before taking action, always:
1. Understand the complete request
2. Break it into smaller, verifiable steps
3. Identify which tools you'll need
4. Consider edge cases and potential issues
5. Execute step by step, validating as you go
```

### 도구 사용 프롬프트 (행동 방식)

사용 가능한 도구를 언제, 어떻게 사용할지에 대한 안내입니다:

```markdown
When you need to understand a codebase:
- Use grep_search for finding specific patterns
- Use read_file to examine file contents
- Use list_dir to explore directory structure
- Always verify your understanding before making changes
```

### 복구 프롬프트 (실패 처리 방법)

문제가 발생했을 때의 지침입니다:

```markdown
If an action fails:
1. Analyze the error message carefully
2. Consider alternative approaches
3. Ask for clarification if the task is ambiguous
4. Never repeat the same failed action without changes
```

<Callout type="info" title="프롬프트 스택">
에이전트의 행동은 함께 작동하는 프롬프트 계층에서 나타납니다. 시스템 프롬프트가 기반을 설정하고, 계획 프롬프트가 추론을 안내하며, 도구 프롬프트가 행동을 가능하게 하고, 복구 프롬프트가 실패를 처리합니다. 이 모든 것이 함께 일관되고 유능한 행동을 만들어냅니다.
</Callout>

## 스킬이란 무엇인가?

프롬프트가 원자라면, **스킬은 분자**입니다—에이전트에게 특정 기능을 제공하는 재사용 가능한 구성 요소입니다.

**스킬**은 AI 에이전트에게 특정 도메인이나 작업에 대한 전문 지식을 제공하는 포괄적이고 이식 가능한 지침 패키지입니다. 스킬은 에이전트의 재사용 가능한 블록입니다: 한 번 만들면 어떤 에이전트든 사용할 수 있습니다.

<Callout type="tip" title="스킬 = 재사용 가능한 에이전트 블록">
코드 리뷰 스킬을 한 번 작성하세요. 이제 Python, JavaScript, Rust 등 어떤 코딩 에이전트든 해당 스킬을 로드하여 즉시 전문 코드 리뷰어가 될 수 있습니다. 스킬을 사용하면 레고 블록처럼 에이전트 기능을 구축할 수 있습니다.
</Callout>

```markdown
---
name: code-review
description: Comprehensive code review with security, performance, and style analysis
---

# Code Review Skill

You are an expert code reviewer. When reviewing code:

## Process
1. **Understand Context** - What does this code do? What problem does it solve?
2. **Check Correctness** - Does it work? Are there logic errors?
3. **Security Scan** - Reference security-checklist.md for common vulnerabilities
4. **Performance Review** - Check performance-tips.md for optimization opportunities
5. **Style & Maintainability** - Is the code readable and maintainable?

## Output Format
Provide feedback in categories:
- 🔴 **Critical** - Must fix before merge
- 🟡 **Suggested** - Recommended improvements
- 🟢 **Nice to have** - Optional enhancements

Always explain *why* something is an issue, not just *what* is wrong.
```

## 효과적인 스킬 구축하기

### 1. 전문 지식을 명확하게 정의

스킬이 무엇을 가능하게 하는지 명확한 설명으로 시작합니다:

```markdown
---
name: api-design
description: Design RESTful APIs following industry best practices, 
  including versioning, error handling, and documentation standards
---
```

### 2. 지식을 계층적으로 구조화

정보를 일반에서 구체적으로 정리합니다:

```markdown
# API Design Skill

## Core Principles
- Resources should be nouns, not verbs
- Use HTTP methods semantically
- Version your APIs from day one

## Detailed Guidelines
[More specific rules...]

## Reference Materials
- See `rest-conventions.md` for naming conventions
- See `error-codes.md` for standard error responses
```

### 3. 구체적인 예제 포함

추상적인 규칙은 예제로 명확해집니다:

```markdown
## Endpoint Naming

✅ Good:
- GET /users/{id}
- POST /orders
- DELETE /products/{id}/reviews/{reviewId}

❌ Avoid:
- GET /getUser
- POST /createNewOrder
- DELETE /removeProductReview
```

### 4. 의사결정 프레임워크 제공

모호한 상황에서 에이전트가 선택할 수 있도록 도와줍니다:

```markdown
## When to Use Pagination

Use pagination when:
- Collection could exceed 100 items
- Response size impacts performance
- Client may not need all items

Use full response when:
- Collection is always small (<20 items)
- Client typically needs everything
- Real-time consistency is critical
```

### 5. 복구 패턴 추가

무엇이 잘못될 수 있는지 예상합니다:

```markdown
## Common Issues

**Problem**: Client needs fields not in standard response
**Solution**: Implement field selection: GET /users?fields=id,name,email

**Problem**: Breaking changes needed
**Solution**: Create new version, deprecate old with timeline
```

## 스킬이 경험에서 배울 때

지금까지 이 장에 나온 스킬은 모두 사람이 썼습니다. 누군가 어떤 일이 자꾸 되풀이된다는 걸 알아차리고, 자리에 앉아 그 일을 하는 방법을 글로 옮깁니다. 하지만 날마다 당신과 함께 일하는 에이전트는 그 일이 어떻게 흘러갔는지도 조용히 기록하고 있습니다. 어떤 지시를 따랐는지, 어디서 당신이 끼어들어 바로잡아야 했는지, 어떤 단계를 두 번 해야 했는지 말이지요. 더 새로운 방식은 바로 이 기록을 활용합니다. 누군가 스킬을 써 주기를 기다리는 대신, 에이전트의 시스템이 스스로 자신의 경험을 돌아보고 새 스킬의 초안을 쓰거나 기존 스킬을 고칩니다. 이를 하나의 루프로 그려 볼 수 있습니다. 이 장 첫머리에서 본 에이전트 루프와 많이 닮았지만, 더 느리게 돌고 안쪽을 향합니다.

Perplexity는 자사 에이전트 Computer를 뒷받침하는, 스스로 개선되는 메모리 시스템 **Brain**에서 이 루프를 자세히 설명합니다([What is Brain?](https://www.perplexity.ai/help-center/en/articles/19700001-what-is-brain)). 2026년 11월에 낸 글([Self-improving skills](https://www.perplexity.ai/hub/blog/self-improving-skills))에서 회사는 Brain이 사용자의 메모리와 세션 기록을 바탕으로 *개인* 스킬을 쓰고 다듬는 방식을 소개합니다. 증거 단계에서는 스킬이 쓰였던 지난 세션, 특히 스킬이 제 역할을 못 했던 세션을 찾아냅니다. 성찰 단계에서는 개선 에이전트가 그 세션들을 살펴보고 변경을 제안합니다. 검증은 그 제안이 형식에 맞고 결과를 개선할 가능성이 높은지 확인하고, 활성화는 변경을 적용합니다. 그러면 이어지는 세션들이 다음 회차의 증거가 됩니다. 이 루프를 믿을 만하게 만드는 것은 그 안에 짜 넣은 절제입니다. 새 스킬을 만들려면 똑같은 재사용 가능한 행동이 서로 독립적으로 두 번 나타나야 하지만, 기존 스킬을 고치는 데는 근거가 탄탄한 한 번의 사례로 충분할 수 있습니다. 개선 에이전트는 스킬을 직접 고치지 않습니다. 근거와 증거를 담은 제안서를 쓰고, 한 번 실행할 때 스킬 하나에 많아야 한 가지만 바꾸며, 증거가 변경을 뒷받침하지 못하면 아예 제안하지 않습니다. 게다가 자동으로 만들어지는 스킬은 사용자당 열 개로 제한됩니다. 그래서 새 스킬이 들어오려면 기존 스킬 하나가 물러나야 하고, 그 교체에는 이유가 있어야 합니다.

Nous Research의 **Hermes Agent**는 같은 생각을 팀의 관점에서 다룹니다. 사람이 반복되는 일을 맡길수록 Hermes는 성공한 접근 방식을 재사용 가능한 스킬로 바꿉니다. 글로 쓴 정의에, 안정된 단계를 매번 같은 방식으로 실행하는 코드를 짝지은 것입니다([Nous Research](https://nousresearch.com/press/hermes-enterprise-in-microsoft-teams)). Collective Wisdom 플러그인은 스킬이 한 사람의 컴퓨터를 떠나는 순간을 맡습니다. Hermes가 어떤 스킬이 공유할 만하다고 제안할 수는 있지만, 결정은 그 스킬을 쓴 사람에게 남습니다. 그 사람은 팀 라이브러리에 게시될 파일 자체를 정확히 검토합니다. 그다음 팀원들은 오늘 우연히 그런 모습인 스킬이 아니라, 특정한 버전 하나를 설치합니다([Collective Wisdom](https://github.com/NousResearch/hermes-collective-wisdom)). [항상 켜져 있는 봇](/book/28-persistent-bots) 장에서는 Hermes가 스킬을 익히는 또 다른 방법을 보여 줍니다. 작업을 한 단계씩 직접 보여 주는 방식입니다.

두 사례를 나란히 놓으면 같은 교훈이 보입니다. 스스로를 고쳐 쓰는 스킬도 결국 에이전트가 따를 지시문이므로, 손으로 쓴 스킬만큼 주의를 기울일 가치가 있습니다. 변경하기 전에 증거를 요구하세요. 되도록 여러 세션에서 나온 증거가 좋습니다. 스킬이 한 사람에게서 다른 사람들에게 넘어가는 곳마다 사람이 검토하는 지점을 두세요. 버전을 남겨 두어, 잘못된 변경은 두고두고 논쟁하기보다 되돌릴 수 있게 하세요. 그리고 표류를 경계하세요. 자주 고쳐지는 스킬은 조금씩 한 사람의 습관이나 한 번의 나쁜 세션 쪽으로 기울다가, 결국 일 자체보다 한때의 기분을 묘사하게 될 수 있습니다.

기준을 얼마나 높일지는 그 스킬이 누구에게 닿는지에 달려 있습니다. 한 사용자를 위해 배운 개인 스킬은 빠르게 움직여도 괜찮습니다. 실수가 생겨도 그 사용자에게만 영향을 주고, 그 사람이 가장 알아채기 좋은 위치에 있기 때문입니다. 반면 공유 스킬이나 기본 제공 스킬은 그것을 불러오는 모든 사람에게 영향을 줍니다. Perplexity도 이 선을 긋습니다. 모든 사용자가 받는 기본 제공 스킬의 변경은 공식 버전에 반영되기 전에 짝지은 재실행(paired replay) 테스트와 내부의 사람 검토를 통과해야 합니다. 팀도 같은 감각을 빌려 올 수 있습니다. 개인 스킬은 자유롭게 배우게 두고, 공유 스킬에는 변경 하나하나를 스스로 증명하도록 요구하는 것입니다.

이 루프를 시험해 보는 데 스스로 개선되는 시스템이 꼭 필요하지는 않습니다. 에이전트에게 적용이 아니라 제안을 부탁하기만 하면 손으로도 돌려 볼 수 있습니다.

<TryIt compact prompt={`\${session:어제 주간 매출 보고서를 준비했던} 세션을 다시 살펴봐 줘. \${skill:weekly-report} 스킬을 개선하고 싶은데, 아직은 바꾸지 마.

## 스킬 공유 및 발견

스킬은 공유될 때 가장 가치 있습니다. [prompts.chat](https://prompts.chat/skills)과 같은 플랫폼에서 다음을 수행할 수 있습니다:

- **발견** - 일반적인 작업을 위한 커뮤니티 제작 스킬 찾기
- **다운로드** - 프로젝트에 직접 스킬 다운로드
- **공유** - 자신의 전문 지식을 재사용 가능한 스킬로 공유
- **반복** - 실제 사용에 기반하여 스킬 개선

같은 방식으로 스킬 하나보다 큰 단위도 공유할 수 있습니다. 지시문과 루틴을 갖춘 봇 전체, 그리고 서로 일을 넘겨주는 봇 팀입니다. [Bots](https://prompts.chat/bots)와 [Teams](https://prompts.chat/bots/teams) 카탈로그가 그 예입니다. 두 가지 생각 모두 [항상 켜져 있는 봇](/book/28-persistent-bots) 장에서 다룹니다.

## 모범 사례

### 스킬 구축을 위한

1. **구체적으로 시작하고 일반화하기** - 정확한 사용 사례에 맞는 스킬을 먼저 만든 다음 추상화
2. **실패 사례 포함** - 스킬이 할 수 없는 것과 처리 방법을 문서화
3. **스킬 버전 관리** - 에이전트가 안정적인 버전에 의존할 수 있도록 변경 사항 추적
4. **실제 작업으로 테스트** - 이론이 아닌 실제 작업에 대해 스킬 검증

### 에이전트와 함께 스킬 사용을 위한

1. **스킬을 먼저 읽기** - 배포하기 전에 스킬이 무엇을 하는지 이해
2. **신중하게 사용자 정의** - 필요할 때만 스킬 기본값 재정의
3. **성능 모니터링** - 컨텍스트에서 스킬이 얼마나 잘 수행되는지 추적
4. **개선 사항 기여** - 스킬을 개선하면 다시 공유하는 것을 고려

<Callout type="info" title="미래는 조합 가능합니다">
AI 에이전트가 더 유능해짐에 따라, 스킬을 조합하고, 공유하고, 사용자 정의하는 능력이 핵심 역량이 될 것입니다. 미래의 프롬프트 엔지니어는 단순히 프롬프트를 작성하는 것이 아니라 AI 에이전트를 특정 도메인에서 진정한 전문가로 만드는 스킬 생태계를 설계할 것입니다.
</Callout>
